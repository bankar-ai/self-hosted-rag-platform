# ERP-047 — Offload `docling` Parsing to Cloud Run (VM Outage Fix)

Status: Backlog
Depends On: None
Category: Bug — a document upload took the entire live VM down (not degraded, fully
unreachable, including SSH) for ~40+ minutes until a manual reset; this is a reliability defect,
not a missing feature

## Description

Live incident, 2026-09-17: uploading a PDF that triggered the `docling` quality-fallback path
(`app/ingestion/parsers.py`'s `parse_quality()`) made the entire live VM unresponsive — not just
the app, SSH too — requiring a manual `gcloud compute instances reset`. Root-caused via the
VM's own journal: `docling`'s pipeline init (layout detection, OCR engine registration, table
structure models) is the trigger. This is not about file *size* — it's about content: any PDF
with a table or scanned/image content bails from the fast path into `docling`, and `docling`'s
own documented baseline is ~4GB RAM (per live GitHub issue research) against this VM's 958MB
total, zero swap configured.

Decided (session discussion, 2026-09-17) over two alternatives (swapping `docling` for a
lighter library stack; adding swap as the fix): **offload `docling` itself to Google Cloud Run**,
in the same GCP project/account as the VM. Rationale:
- Keeps `docling`'s full extraction quality — no permanent quality tradeoff versus swapping to
  pytesseract/pdfplumber/PyMuPDF's native `find_tables()`
- No GPU needed (`docling` runs CPU-only) — fits Cloud Run's no-GPU billing exactly, $0 GPU cost
- Cloud Run's free tier (2M requests + 360,000 vCPU-seconds + 180,000 GiB-seconds/month,
  **recurring**, not a spend-down credit) comfortably covers demo-scale usage — sized against a
  generous 100-upload/2-3-month estimate at ~13-27% of the monthly allowance
- Same GCP account already in use for the VM — no new provider/billing relationship, unlike the
  Modal alternative (which is also GPU-priced, a worse fit for a CPU-only job)
- Establishes the general pattern (`docs/architecture.md`'s new "keep the always-on host thin"
  principle) already proven once for Ollama-on-Modal

Known risk to design around: cold-start latency. If Cloud Run scales the `docling` service to
zero between uploads, the first request after idle has to load `docling`'s models before
parsing anything -- could be tens of seconds to a couple of minutes. Needs an explicit UX
decision (timeout + a "this may take a moment" state in the frontend, not a silent long wait) --
see also `frontend/src/pages/DocumentsPage.tsx`'s existing polling UI, which mostly already
degrades gracefully into a longer "pending" status.

## Acceptance Criteria

- [x] Immediate mitigation, done first regardless of the Cloud Run work below: add swap space to
      the live VM (`e2-micro` currently has 0 bytes configured) so a future memory spike degrades
      to "slow" instead of a hard lockup requiring a manual reset
- [ ] A Cloud Run service hosting `docling`'s conversion logic, deployed from this repo (mirrors
      `deploy/modal_ollama.py`'s existing pattern — a new `deploy/cloud_run_docling.py` or
      similar)
- [ ] `app/ingestion/parsers.py`'s `parse_quality()` calls the Cloud Run service over HTTP
      instead of importing/running `docling` in-process; the VM no longer has `docling`/`torch`/
      `transformers` as installed dependencies at all
- [ ] Explicit timeout + user-visible "this is taking a moment" handling for the cold-start case,
      not a silent hang
- [ ] Live-verified: a real PDF that triggers the fallback path processes successfully end-to-end
      via the live deployment, and the VM's own memory stays flat during that upload (confirming
      the heavy work genuinely left the VM's process)
- [ ] Cloud Run usage checked against the free-tier estimate above after real usage accumulates,
      not just assumed to stay free forever

## Resolution progress (2026-09-17)

Swap mitigation done: 2GB swapfile (`/swapfile`, persisted via `/etc/fstab`), `vm.swappiness=10`
(persisted via `/etc/sysctl.conf`) so swap is used as an emergency pressure valve, not eagerly
(avoids dragging down normal-load performance). Verified live: `swapon --show` confirms 2GB
active. This does not fix the underlying capacity mismatch -- it only turns a hard lockup into
graceful degradation. The Cloud Run offload below is still the real fix.

## Notes

Design spec should go through the normal brainstorming/design pass (this is a real architecture
change: new deployable service, new inter-service HTTP call, removed dependencies) rather than
being bolted on directly. See `docs/architecture.md`'s new "keep the always-on host thin"
principle, added the same day this ticket was opened, for the general rule this fix instantiates.

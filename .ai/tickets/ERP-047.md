# ERP-047 — Offload `docling` Parsing to Cloud Run (VM Outage Fix)

Status: Done
Depends On: None
Category: Bug — a document upload took the entire live VM down (not degraded, fully
unreachable, including SSH) for ~40+ minutes until a manual reset; this is a reliability defect,
not a missing feature

## Description

Live incident, 2026-09-17: uploading a PDF that triggered the `docling` quality-fallback path
(`app/ingestion/parsers.py`'s `parse_quality()`) made the entire live VM unresponsive — not just
the app, SSH too — requiring a manual `gcloud compute instances reset`. Root-caused via the
VM's own journal: `docling`'s pipeline init (layout detection, OCR engine registration, table
structure models) is the trigger. This is not about file *size* — it's about content: any PDF
with a table or scanned/image content bails from the fast path into `docling`, and `docling`'s
own documented baseline is ~4GB RAM (per live GitHub issue research) against this VM's 958MB
total, zero swap configured.

Decided (session discussion, 2026-09-17) over two alternatives (swapping `docling` for a
lighter library stack; adding swap as the fix): **offload `docling` itself to Google Cloud Run**,
in the same GCP project/account as the VM. Rationale:
- Keeps `docling`'s full extraction quality — no permanent quality tradeoff versus swapping to
  pytesseract/pdfplumber/PyMuPDF's native `find_tables()`
- No GPU needed (`docling` runs CPU-only) — fits Cloud Run's no-GPU billing exactly, $0 GPU cost
- Cloud Run's free tier (2M requests + 360,000 vCPU-seconds + 180,000 GiB-seconds/month,
  **recurring**, not a spend-down credit) comfortably covers demo-scale usage — sized against a
  generous 100-upload/2-3-month estimate at ~13-27% of the monthly allowance
- Same GCP account already in use for the VM — no new provider/billing relationship, unlike the
  Modal alternative (which is also GPU-priced, a worse fit for a CPU-only job)
- Establishes the general pattern (`docs/architecture.md`'s new "keep the always-on host thin"
  principle) already proven once for Ollama-on-Modal

Known risk to design around: cold-start latency. If Cloud Run scales the `docling` service to
zero between uploads, the first request after idle has to load `docling`'s models before
parsing anything -- could be tens of seconds to a couple of minutes. Needs an explicit UX
decision (timeout + a "this may take a moment" state in the frontend, not a silent long wait) --
see also `frontend/src/pages/DocumentsPage.tsx`'s existing polling UI, which mostly already
degrades gracefully into a longer "pending" status.

## Acceptance Criteria

- [x] Immediate mitigation, done first regardless of the Cloud Run work below: add swap space to
      the live VM (`e2-micro` currently has 0 bytes configured) so a future memory spike degrades
      to "slow" instead of a hard lockup requiring a manual reset
- [x] A Cloud Run service hosting `docling`'s conversion logic, deployed from this repo (mirrors
      `deploy/modal_ollama.py`'s existing pattern — built as `deploy/cloud_run_docling/`, a
      directory with its own `main.py`/`Dockerfile`/`requirements.txt`, since Cloud Run needs a
      real container rather than Modal's Python-native image definition)
- [x] `app/ingestion/parsers.py`'s `parse_quality()` calls the Cloud Run service over HTTP
      instead of importing/running `docling` in-process; the VM no longer has `docling`/`torch`/
      `transformers` as installed dependencies at all
- [x] Explicit timeout (8 minutes, `IngestionSettings.docling_service_timeout_seconds`) +
      user-visible handling for the cold-start case: satisfied by the pre-existing
      `DocumentsPage` polling UI (already handles an arbitrarily long "pending"/"processing"
      wait with no code changes needed, per the design spec's explicit scope decision) rather
      than new frontend code
- [x] Live-verified: a real PDF that triggers the fallback path processes successfully end-to-end
      via the live deployment (`POST /parse` returned `200 OK`, confirmed in Cloud Run logs), and
      the VM's own memory stayed flat throughout (~270-320Mi available, matching the pre-incident
      baseline, no spike)
- [x] Cloud Run usage checked against the free-tier estimate — see Resolution below

## Resolution progress (2026-09-17)

Swap mitigation done: 2GB swapfile (`/swapfile`, persisted via `/etc/fstab`), `vm.swappiness=10`
(persisted via `/etc/sysctl.conf`) so swap is used as an emergency pressure valve, not eagerly
(avoids dragging down normal-load performance). Verified live: `swapon --show` confirms 2GB
active. This does not fix the underlying capacity mismatch -- it only turns a hard lockup into
graceful degradation. The Cloud Run offload below is still the real fix.

## Notes

Design spec should go through the normal brainstorming/design pass (this is a real architecture
change: new deployable service, new inter-service HTTP call, removed dependencies) rather than
being bolted on directly. See `docs/architecture.md`'s new "keep the always-on host thin"
principle, added the same day this ticket was opened, for the general rule this fix instantiates.

## Resolution (2026-09-17)

Built per `docs/superpowers/specs/2026-09-17-docling-cloud-run-offload-design.md` and
`docs/superpowers/plans/2026-09-17-docling-cloud-run-offload.md`. `docling`/`torch`/
`transformers` (and their whole dependency tree — 72 packages, including CUDA/nvidia wheels the
VM never even needed since it has no GPU) are entirely removed from the root project and the
live VM's own `.venv`. `app/ingestion/parsers.py`'s `parse_quality()` now calls a new
`app/ingestion/cloud_run_client.py`, which authenticates to the new Cloud Run service via a
GCP IAM identity token fetched from the metadata server (no stored secret) and posts the PDF
bytes to it.

**Three real bugs found and fixed during implementation/deployment, not just planned for**:
1. `tempfile.NamedTemporaryFile()`'s default exclusive-open mode fails on Windows the moment
   `docling` tries to reopen the still-open path — caught via a local smoke test before ever
   deploying; fixed with `delete=False` + an explicit close first (harmless on Cloud Run's Linux
   runtime, more portable code either way).
2. The first live deployment attempt downloaded `docling`'s model weights from HuggingFace at
   *request* time, not just relying on a cache — hit HF's rate limit and failed the very first
   real ingestion job outright. Fixed by running `docling-tools models download` at Docker
   *build* time (baked into the image, mirroring `deploy/modal_ollama.py`'s existing
   "models baked at build time" pattern for Ollama) and pointing `DocumentConverter` at that
   local path explicitly via `PdfPipelineOptions(artifacts_path=...)`, so it never touches the
   network at request time.
3. The rebuild with baked-in models then failed at Docker build time: `rapidocr` (one of
   `docling`'s OCR backends) pulls in `opencv-python`, which needs X11/GL system shared
   libraries (`libxcb.so.1` etc.) that `python:3.12-slim`'s minimal base doesn't include — a
   well-known "opencv in a slim Docker image" issue, fixed with a short `apt-get install`.

**Live-verified end-to-end** (2026-09-17, after all three fixes): uploaded a real PDF with a
table through the live deployment; the Cloud Run service's own logs confirm `POST /parse`
returned `200 OK` with no HuggingFace network calls (models loaded entirely from the baked-in
cache); the live VM's memory stayed at 266-321Mi available throughout — matching the
pre-incident baseline exactly, no spike. Cloud Run deployed with `min-instances=0` (free-tier,
scale-to-zero), `concurrency=1` (docling shouldn't share a container across concurrent
requests), `max-instances=3` (cost ceiling), `--no-allow-unauthenticated` with `run.invoker`
granted only to the VM's own service account.

One separate, unrelated issue surfaced during this same live verification: the full ingestion
pipeline's *next* stage (embedding, via Modal-hosted Ollama) failed with `"modal-http: workspace
... is disabled"` — a Modal account/billing-level restriction, not a `docling`/Cloud Run problem
(confirmed: the `/parse` call itself succeeded before this later stage failed). Out of scope for
this ticket; flagged separately to the user, not fixed here.

Also fixed along the way: `pyproject.toml` gained `testpaths = ["tests"]` (pytest was scanning
the whole repo by default, including the new Cloud Run service's own `test_main.py`, which
correctly can't import `docling` any more since it's not a root-project dependency).

Backend verified: `ruff`/`mypy --strict` clean, full suite 394 passed (was 387; +7 for the new
config/client tests), 96.62% coverage. Merged to `develop` via PR #40 (docling→Cloud Run
routing) and two follow-up fix PRs (#41 and a further commit for the opencv system deps,
found live after #41).

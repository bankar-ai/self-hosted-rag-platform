# ERP-035 — Document Hardware/VRAM Sizing for Ollama-Backed Models

Status: Done
Depends On: None

## Description

The platform has no documented hardware sizing guidance for the LLM/embedding models it runs
locally via Ollama. Verified live (2026-09-07) that this is a real gap, not a theoretical one: on a
6GB-VRAM RTX 3050 laptop, `qwen3:8b` (the value needed to fix ERP-034's default) failed to load
twice with out-of-memory errors -- once a CUDA VRAM allocation failure, once a CPU-side pinned
buffer allocation failure -- both while the machine's available system RAM had dropped to ~2-3.5GB
out of 16GB total under concurrent developer workload (IDE, browser, WSL/Docker backend, other
processes). The same model loaded and ran correctly once more RAM was free. There is currently no
documentation telling an operator how much headroom a given model tag actually needs, so this
failure mode is invisible until it happens in front of a user.

## Acceptance Criteria

- [x] A deployment/ops doc (new `docs/deployment.md` or a section in `docs/architecture.md`) states
      minimum recommended VRAM and system RAM headroom for the models this repo references by name
      (`nomic-embed-text`, and whichever generation model becomes the documented default per
      ERP-034), based on each model's actual quantized size plus KV-cache overhead at the
      configured context length
- [x] Guidance covers what happens under contention (smaller model fallback recommendation, e.g.
      `gemma3:4b`, for constrained/dev hardware) so this isn't a hard blocker for local development
- [x] Note that Ollama's own OOM errors are not always deterministic given the same model twice in a
      row -- depends on concurrent system load at call time, not just total capacity -- so retries
      alone are not a reliable mitigation without headroom
- [x] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass (doc-only change is not
      expected to touch app code, but keep the gate in the acceptance criteria for consistency with
      this repo's other tickets)

## Notes

Found in the same 2026-09-07 live verification session as ERP-034. Not an application bug --
Ollama and the GPU driver behaved correctly given the resource pressure -- but the platform gives an
operator zero warning before they hit it in production.

**Fixed (2026-09-08)**: written up in the new `docs/deployment.md`, shared with ERP-034's model-tag
guidance. States per-model disk size and observed behavior (`nomic-embed-text`: negligible;
`gemma3:4b`: reliable under moderate load, recommended default for constrained/shared hardware;
`qwen3:8b`: works but intermittently OOM'd twice in live testing under RAM pressure, two different
failure modes on the same machine at different times), and explicitly notes the non-determinism --
the same model failed and later succeeded purely as a function of concurrent system load, not total
installed capacity. Also cross-references `D:\github-projects\infrastructure-options.md` for
dedicated/serverless GPU hosting as the alternative to fighting for local resources. Verified:
ruff/mypy clean, full suite 367 passed, 97% coverage (no app code touched by this ticket, doc-only).

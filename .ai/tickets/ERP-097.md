# ERP-097 — Async Sampling of Live Production Traffic for LLM-Judge Scoring

Status: Backlog
Depends On: ERP-087
Category: Improvement

## Description

Follow-up from **ERP-088**'s design decision: score a sample of real `(query, answer,
retrieved-context)` tuples from live production traffic out-of-band, reusing
`app/evaluation/generation_runner.py`'s existing `judge.score(query, answer, contexts)` plumbing
(Ragas or the Ollama-judge fallback, ERP-030) rather than building a second scoring path.

Depends on ERP-087 existing first: the dashboard surface that will display these scores should
exist (or at least its schema/query pattern be settled) before this ticket decides where sampled
rows land, so the two aren't designed against each other.

## Constraints From ERP-088's Investigation

- `ConversationMessage.citations` (JSONB) stores citation *metadata* only (`chunk_id`,
  `document_id`, page range, score — `app/generation/schemas.py:Citation`), not the chunk's raw
  text. Reconstructing `contexts` for the judge means resolving each citation's `chunk_id` back
  to its text at sample time — and tolerating a citation whose chunk or document has since been
  deleted (skip that context, or skip the sample if nothing resolves).
- Inline judging (judging every request synchronously) was explicitly rejected in ERP-088 —
  don't add judge-LLM latency to the user-facing request path.
- Thumbs up/down feedback (`message_feedback` table, ERP-045) is a separate, already-collected
  signal — this ticket is additive to it, not a replacement.

## Open Decisions

- [ ] Sample rate (e.g. fixed percentage, fixed count per hour/day, or every Nth conversation)
- [ ] Trigger mechanism (scheduled job vs. background task enqueued at message-send time)
- [ ] Storage shape for scored samples — likely extends or sits alongside
      `generation_evaluation_runs` (which ERP-087's dashboard already reads), but with a
      `conversation_id`/`message_id` back-reference the golden-dataset run table doesn't need;
      confirm rather than assume reuse is the right shape once ERP-087 is built
- [ ] Whether/how a sampled score surfaces per-conversation (e.g. to an admin) or only in
      aggregate on the dashboard

## Acceptance Criteria

- [ ] Decide sample rate, trigger mechanism, and storage shape (see Open Decisions)
- [ ] Implement the out-of-band sampling job, reusing `judges.py`/`generation_runner.py`'s
      scoring plumbing rather than duplicating it
- [ ] Sampled scores are visible on the evaluation dashboard (ERP-087) or a clearly-linked
      extension of it — not a data pipeline with no visible output
- [ ] Verify a citation pointing at a deleted chunk/document is handled without crashing the job

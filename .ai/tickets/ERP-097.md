# ERP-097 — Async Sampling of Live Production Traffic for LLM-Judge Scoring

Status: Done
Depends On: ERP-087
Category: Improvement

## Description

Follow-up from **ERP-088**'s design decision: score a sample of real `(query, answer,
retrieved-context)` tuples from live production traffic out-of-band, reusing
`app/evaluation/generation_runner.py`'s existing `judge.score(query, answer, contexts)` plumbing
(Ragas or the Ollama-judge fallback, ERP-030) rather than building a second scoring path.

Depends on ERP-087 existing first: the dashboard surface that will display these scores should
exist (or at least its schema/query pattern be settled) before this ticket decides where sampled
rows land, so the two aren't designed against each other.

## Constraints From ERP-088's Investigation

- `ConversationMessage.citations` (JSONB) stores citation *metadata* only (`chunk_id`,
  `document_id`, page range, score — `app/generation/schemas.py:Citation`), not the chunk's raw
  text. Reconstructing `contexts` for the judge means resolving each citation's `chunk_id` back
  to its text at sample time — and tolerating a citation whose chunk or document has since been
  deleted (skip that context, or skip the sample if nothing resolves).
- Inline judging (judging every request synchronously) was explicitly rejected in ERP-088 —
  don't add judge-LLM latency to the user-facing request path.
- Thumbs up/down feedback (`message_feedback` table, ERP-045) is a separate, already-collected
  signal — this ticket is additive to it, not a replacement.

## Open Decisions

- [x] Storage shape for scored samples — likely extends or sits alongside

- [x] Whether/how a sampled score surfaces per-conversation (e.g. to an admin) or only in

## Acceptance Criteria

- [x] Decide sample rate, trigger mechanism, and storage shape (see Open Decisions)
- [x] Implement the out-of-band sampling job, reusing `judges.py`/`generation_runner.py`'s
      scoring plumbing rather than duplicating it
- [x] Sampled scores are visible on the evaluation dashboard (ERP-087) or a clearly-linked

- [x] Verify a citation pointing at a deleted chunk/document is handled without crashing the job

## Resolution (2026-09-26)

**Sample rate**: every not-yet-sampled assistant message is scored, not a probabilistic
percentage — matches the user's actual goal ("every evaluation metric calculated against it"),
and is affordable at this deployment's current low/sporadic traffic. `--limit` (default 50)
bounds how many messages one invocation processes, so a single run's judge-LLM load stays
predictable; this is the seam to add a real sampling rate at later if traffic grows enough to
make scoring everything too expensive — not a redesign.

**Trigger mechanism**: manual CLI invocation
(`uv run python -m app.evaluation.production_sample_run [--judge ragas|ollama] [--limit N]`),
matching the existing `app.evaluation.run`/`generation_run` pattern exactly — deliberately
*not* wired into the live chat request path (`app/generation/service.py`), so the hot path is
completely untouched and this can never add latency or a new failure mode to a real user's
request. A scheduled trigger (cron, or extending `.github/workflows/evaluation-gate.yml`'s
pattern) can wrap this same entrypoint later without any redesign.

**Storage shape**: new `production_sample_scores` table (migration `6412377c47e5`), not a reuse
of `generation_evaluation_runs` — confirmed a separate shape was right, per the ticket's own
note, since this is one row per individually-sampled real message (`message_id` unique, with a
`conversation_id` back-reference), not one row per full evaluation run. A message with no
resolvable context (no citations at all, or every cited chunk/document since deleted) still gets
a row (`skipped=True`, all score fields `None`), so it's never retried — this is what "verify a
citation pointing at a deleted chunk/document is handled without crashing the job" resolves to.

**Surfacing**: aggregate-only on the Grafana dashboard for now (a new "Production Sampling - Live
Traffic (ERP-097)" row: a quality-over-time panel and a scored-vs-skipped stat panel, both
querying `production_sample_scores` directly via the existing `efza4kyumru9sb` Postgres data
source) — no new API endpoint, no per-conversation admin view, matching ERP-087's exact approach.

**Implementation**: `app/ingestion/repository.py` gained `get_chunks_by_ids` (chunk_id -> text,
tolerant of a missing/deleted id); `app/evaluation/repository.py` gained
`get_unsampled_assistant_messages`, `get_preceding_user_message`, and
`save_production_sample_score`; `app/evaluation/production_sampling.py`'s
`run_production_sampling` orchestrates it, reusing the exact `GenerationJudge` interface
(`judges.py`) the golden-dataset harness (`generation_runner.py`) already uses. The two
harnesses' shared "mean excluding `None`" logic was refactored out of `generation_runner.py`
into `app/evaluation/metrics.py` (`mean_excluding_none`) rather than duplicated.

**Verified**: backend 572 passed (was 558), ruff/mypy clean. Dashboard update pushed via the
Grafana HTTP API (service account token) and re-synced to
`deploy/grafana/dashboards/ai-platforms-service-observability.json` per that directory's
documented manual-sync workflow (title round-trip confirmed clean, no repeat of the ERP-087
mojibake issue).

**Live-verified against real production data (2026-09-26)**: migration applied to the live Neon
database (`alembic upgrade head` from the VM, using the documented `.env`-parsing workaround for
`DATABASE_URL`'s unescaped `&`), code deployed and service restarted, `production_sample_run`
run from the VM against all 75 real `conversation_messages` assistant rows that existed at the
time (two batches, `--limit 15` then `--limit 60`, to sweep the whole backlog): 9 scored, 66
skipped (no resolvable context — mostly older messages from throwaway test accounts whose
documents/chunks were since deleted via `DELETE /admin/users/{id}`, ERP-040). Real scores from
actual production traffic: **Faithfulness 0.950, Answer Relevancy 0.789, Context Precision
0.933**. Confirmed via a direct Postgres query against live Neon (through the Grafana data
source) that `production_sample_scores` now holds all 75 rows, and the new dashboard panels
render this data. **Real-world finding, not just a feature demo**: the second batch (9 messages
actually scored, each needing up to 3 judge-LLM calls) took roughly an hour to complete — the
process stayed alive throughout (confirmed via `ps aux`, near-zero CPU, blocked on network I/O to
Modal, not hung), consistent with the same-day latency investigation showing gemma3:4b generation
calls via Modal can genuinely take 80-250+ seconds each even once "warm." This means the judge
pipeline itself inherits the exact latency problem already flagged for the live chat UI — worth
factoring into whatever comes of that separate discussion (switching generation to a hosted API),
since a slow judge makes this sampling job itself slow to run, not just the user-facing chat.

Not built (deliberately, out of scope): a probabilistic sampling rate, a scheduled/automatic
trigger, and a per-conversation score view — all three are natural, low-effort follow-ups if
traffic grows or the aggregate view stops being enough, not missing pieces of this ticket.

# ERP-066 — Admin User-Delete 500s on a User With Rated Messages

Status: Done
Depends On: ERP-045, ERP-040
Category: Bug — a real regression from ERP-045, caught during this session's own post-deploy
verification, not a pre-existing gap

## Description

Found live while cleaning up a verification test account right after deploying ERP-045
(message feedback): `DELETE /admin/users/{user_id}` 500'd with a foreign key violation for any
user who had rated at least one message. `delete_user_and_owned_data` (ERP-040) deletes
`conversation_messages` rows directly; `message_feedback` (new in ERP-045, same session)
references `conversation_messages.id` and was never added to that cleanup function, so deleting
a referenced message row violated the FK constraint.

## Acceptance Criteria

- [x] Deleting a user who has rated messages succeeds, cleaning up their feedback rows too.
- [x] Regression test: the existing comprehensive delete-user test now includes a rated message.

## Resolution (2026-09-18)

`app/auth/repository.py`'s `delete_user_and_owned_data` now deletes `message_feedback` rows
(looked up by the user's message IDs) before deleting `conversation_messages`, matching the
existing child-before-parent ordering the function already follows for every other table.

Live-verified: reproduced the exact failure against the live deployment (a real `500` with the
`message_feedback_message_id_fkey` violation in the logs), deployed the fix, and confirmed the
same delete call that failed now returns `204` and the user is gone.

Verified: ruff/mypy clean, full suite 485 passing, `test_admin_can_delete_a_user_and_their_owned_data`
extended with a rated message reproduces and confirms the fix.

## Notes

Caught by this session's own live-verification discipline (deleting a real test account after
using it), not by a user report -- worth noting as a case where "always clean up your own
test data via the real deletion path" surfaced a real bug rather than just tidying up.

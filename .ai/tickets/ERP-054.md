# ERP-054 — Upload UX: Visible Size Limit, Drag-and-Drop, Multi-File, Transfer Progress

Status: Done
Depends On: ERP-051
Category: Improvement — none of these existed; the upload UI was a bare single-file `<input>`
with no on-screen guidance

## Description

Confirmed in code (`frontend/src/pages/DocumentsPage.tsx`): a plain `<input type="file">`, no
`multiple` attribute (only ever reads `files[0]`), no drag-and-drop zone, and no on-screen
mention of the size limit at all.

Two different kinds of "progress" are in scope vs. explicitly deferred here:
- **Upload transfer progress** (bytes sent to the server): in scope. Cheap — switching just the
  upload call from `fetch` to `XMLHttpRequest` (which has `upload.onprogress`) gets a real
  byte-level progress bar with no backend change.
- **Processing-stage progress** (parse -> chunk -> embed, after bytes arrive): explicitly
  deferred. The backend job model only reports `pending`/`processing`/`done`/`failed` today, no
  sub-stage or percentage — a real "37% done" bar needs backend checkpoint reporting, a bigger
  lift than the rest of this ticket. Not part of this ticket's acceptance criteria.

## Acceptance Criteria

- [x] The upload area displays the configured size limit (ERP-051's finalized 20MB) on screen,
      not just enforced silently server-side on rejection.
- [x] Drag-and-drop onto the upload area works alongside the existing click-to-browse input.
- [x] Multiple files can be selected/dropped at once; each gets its own job, tracked and polled
      independently.
- [x] A real byte-level upload progress bar is shown per file during the transfer phase.
- [x] A file exceeding the size limit is rejected client-side with a clear message before any
      network call, in addition to the existing server-side `413`.

## Resolution (2026-09-18)

`frontend/src/lib/apiClient.ts` gained `uploadWithProgress` (XHR-based, not `fetch` — `fetch`
has no reliable upload-progress event; mirrors `apiFetch`'s 401-refresh-and-retry behavior for
parity). `DocumentsPage.tsx` rewritten: a dashed drop zone (`onDragOver`/`onDrop`) alongside the
existing file input (now `multiple`), a visible "Maximum file size: 20 MB" label, client-side
size rejection before any network call (files over the limit are listed as rejected, never
uploaded), and a per-file progress bar driven by `XMLHttpRequest.upload.onprogress` shown while
bytes are still transferring — separate from the existing job-status polling UI, which takes
over once the backend has accepted the file. Multiple files upload concurrently, each tracked by
its own job ID exactly as the existing per-file job model already supported (no backend change
needed for this part).

Processing-stage (percentage) progress remains deliberately out of scope, per the ticket's
original framing — the backend job model still only reports pending/processing/done/failed, no
sub-stage checkpoints.

Verified: `tsc --noEmit` and `oxlint` both clean, 24 vitest tests passing (unchanged — no
existing test covered this page's upload flow before or after). Not live-browser-tested in this
session (no browser tool available) — verified via typecheck/lint and by code review against the
existing DocumentsPage test-free precedent; flagged here rather than silently assumed.

## Notes

Depends on ERP-051 for the actual limit value to display (hardcoded as a matching frontend
constant — there is no settings-introspection endpoint to fetch it dynamically).

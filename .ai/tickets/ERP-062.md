# ERP-062 — Prevent Duplicate Conversation Names on Rename

Status: Done
Depends On: ERP-061
Category: Lapse — ERP-061 added renaming with no uniqueness check at all

## Description

Reported live: two different conversations can end up with the identical title. Scope
deliberately limited to the *rename* action (ERP-061) — auto-derived titles (a conversation's
first-message preview) are not touched, since two unrelated conversations legitimately starting
with the same message (e.g. both opening with "hi") is normal usage, not a bug; forcing
uniqueness there would fight the existing preview-title behavior instead of fixing anything.

## Acceptance Criteria

- [x] Renaming a conversation to a title that collides (case-insensitively) with another of the
      caller's own conversations is rejected with a clear error, not silently allowed.
- [x] Renaming a conversation to its own current title (a no-op) is allowed, not rejected as a
      false conflict.
- [x] The collision check is scoped per-owner — two different users can each have a conversation
      titled the same thing.

## Resolution (2026-09-18)

`app/generation/repository.py` gained `title_exists_for_owner` (case-insensitive, excludes the
conversation being renamed). `app/generation/service.py`'s `rename_conversation` raises a new
`ConversationTitleConflictError` before attempting the rename; the router maps it to `409
Conflict`. Frontend: `ChatPage.tsx`'s rename flow surfaces a clear message on a 409 via
`window.alert`, consistent with the existing `window.prompt`-based rename UI.

Verified: ruff/mypy clean, new repository/router tests (conflict rejected, self-rename allowed,
per-owner scoping); full backend suite passing. Live-verified against the real local stack:
renamed a conversation, attempted a case-different duplicate rename, confirmed `409` -- not
deployed/live-verified against the production environment yet as of this writing.

# ERP-073 — Show and Allow Retry for Upload-Transfer Failures

Status: Done
Depends On: None
Category: Bug — confirmed silent failure

## Description

Investigated live: if the network drops during the upload itself (before the backend creates a
job), the frontend silently removes the file from the "uploading" list with no error message
and no way to retry — the user has no indication anything went wrong. See
`docs/superpowers/specs/2026-09-19-post-erp050-live-feedback-design.md` for the full design.

## Acceptance Criteria

- [ ] A byte-transfer upload failure shows a clear failed state (not silent removal) with an
      error message
- [ ] A "Try again" button re-attempts the upload using the same in-memory `File` object (no
      re-selection required)
- [ ] New tests cover: a failed transfer shows the failed state; "Try again" re-invokes the
      upload

## Notes

Distinct from ERP-072 (which handles a job that failed *after* upload succeeded, during
ingestion) — this covers failure *during* the upload transfer itself, before any job exists.

## Resolution (2026-09-19)

A failed upload transfer (`uploadWithProgress` rejecting) now shows a clear "Upload failed."
state with a "Try again" button that re-attempts using the same in-memory `File` object — no
re-selection needed. The final whole-branch review caught one more gap in the same area: a
permanently-failed transfer had no way to dismiss it short of a page reload — fixed in the same
pass by adding a small remove button alongside "Try again" (purely client-side state, no backend
involvement since a failed transfer never created a job). Merged to `develop` via PR #50.

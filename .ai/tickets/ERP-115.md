# ERP-115 — Show generation duration to users (persisted, hover-reveal)

Status: Done
Depends On: None
Category: Improvement

## Description

Real live-traffic latency investigation (`ERP-113`/`ERP-114`, same session) showed a real
request can range from ~2s to 80+s depending on retrieval/embedding cold-start state — but
users currently have no visibility into how long an answer actually took. Distinct from any
existing latency metric (Langfuse's per-`llm.generate`-call latency, the
`llm_generation_duration_seconds` OTel histogram): those are narrow engineering diagnostics
covering one phase each, not the single end-to-end "how long did I wait" number a user
experiences. Also useful for debugging later, independent of the UI — the user explicitly asked
for this to land in the database, not just be shown live.

Design decisions made during brainstorming (2026-09-28, with the user):

- **Persisted, not ephemeral**: a new `conversation_messages` column (mirroring how
  `citations`/`retrieval_settings` were added in `ERP-080`/`ERP-107`), not just an SSE-event
  field that disappears on reload. Chosen specifically because the ephemeral version would lose
  the value on a page reload or switching to a different conversation and back — confirmed with
  the user this was unacceptable ("should not go away on reload or tab switch").
- **Measured end-to-end**, not just the LLM call: `time.monotonic()` wrapping the whole
  `generate()`/`generate_stream()` call (rate limit → history load → rewrite → retrieval →
  generation → persistence), matching what Grafana Tempo's root trace span showed for the real
  81.5s request investigated in `ERP-113`/`ERP-114` — not Langfuse's narrower per-call latency.
- **UI: hover-reveal, not always-visible** — a bold "Generated in 81.5s" caption risks drawing
  attention to exactly the slowness this project is trying to minimize, especially for a
  first-time visitor to the live demo. Shown on hover only (e.g. a small clock icon or the
  existing Copy Q&A/feedback footer row), not a permanent on-screen number.

## Acceptance Criteria

- [x] New `conversation_messages.duration_seconds` column (nullable float — `null` for
      user-role messages and any message persisted before this column existed), via an Alembic
      migration (`f84f343bb1cb`, clean autogenerate diff)
- [x] `generate()` and `generate_stream()`/`_run_stateful_generation()` measure end-to-end wall
      time via `time.monotonic()` and persist it on the assistant message
- [x] `GenerationResponse` (non-streaming) and the `"done"` SSE event (streaming) both carry
      `duration_seconds`, including the short-circuit paths (greeting, empty-retrieval) for
      consistency
- [x] `Message` schema gains `duration_seconds: float | None`, returned by
      `GET /conversations/{id}` for every past assistant turn, not just newly-generated ones
- [x] Frontend: hover-reveal only (a `title`-attribute tooltip, "⏱" icon, not an always-visible
      caption), placed in the existing Copy Q&A/feedback footer row on assistant messages;
      survives page reload and switching conversations since it comes from persisted data
      (`ConversationMessage.duration_seconds`), not in-memory-only state
- [x] `ruff`, `mypy --strict`, `pytest-cov --cov-fail-under=90` (backend: 615 passed, 95.78%
      coverage) and `tsc -b`/`oxlint`/`vite build` (frontend: 98 passed) all pass

## Progress (2026-09-28) — closed out

Backend: new column + migration, `time.monotonic()` wrapping in both `generate()` and
`generate_stream()`/`_run_stateful_generation()`, threaded through to `GenerationResponse`, the
`"done"` SSE event, and persisted via `append_message`. New test
`test_generate_persists_duration_seconds_and_it_round_trips_through_history` (mirrors the
existing `ERP-107` retrieval-settings persistence test) proves the actual round-trip, not just
"doesn't crash." Six pre-existing tests updated where they asserted exact response/event
equality without the new (necessarily nondeterministic) field.

Frontend: `ChatMessage`/`ConversationMessage` types gain `durationSeconds`/`duration_seconds`;
both history-load call sites and the streaming `"done"` handler wire it through; rendered as a
small `title`-tooltip icon in the existing footer row. New test verifies the tooltip text
("Generated in 3.5s") appears after a real streamed exchange completes.

## Notes

Not in scope: any user-facing latency *warning* or threshold-based messaging (e.g. "this is
taking longer than usual") — this ticket is purely "show the number if someone looks for it,"
nothing proactive.

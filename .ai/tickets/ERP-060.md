# ERP-060 — Refreshing the Browser Loses the Active Conversation

Status: Done
Depends On: ERP-048
Category: Lapse — ERP-048 fixed conversations not being *discoverable* after a login; this is
the narrower remaining gap that the *currently open* one isn't remembered across a page refresh

## Description

Reported live: refreshing the browser (or a hard navigation) always drops the user into a brand
new, blank "New chat" — even though the sidebar's conversation list (ERP-048) still loads
correctly and clicking an entry still correctly restores its history. Confirmed in code:
`ChatPage.tsx`'s `conversationId` state is always initialized via `useState(() =>
newConversationId())` — a fresh random UUID on every mount, with nothing persisted or restored.
A user mid-conversation who refreshes loses their place and has to manually re-click back into
the conversation they were just in, which reads as "chat history cleared" even though nothing was
actually deleted.

## Acceptance Criteria

- [x] The currently-active conversation ID survives a browser refresh.
- [x] On mount, if a persisted active conversation ID exists, its full history is loaded
      automatically (reusing the existing `GET /conversations/{id}` fetch), not just the ID
      restored with an empty message list.
- [x] Starting a genuinely new chat (the existing "New chat" button) clears the persisted ID, so
      it doesn't come back after the next refresh.
- [x] Persistence is scoped per user (same pattern as the pre-ERP-048 localStorage stores), so
      switching accounts on the same browser doesn't leak one user's active conversation into
      another's session.

## Resolution (2026-09-18)

`ChatPage.tsx` now persists the active `conversationId` to `localStorage`
(`rag-active-conversation:<userId>`, scoped per user) on every change, and on mount reads it back
and immediately loads its history via the same `selectConversation`-style fetch ERP-048 already
added for clicking a sidebar entry — so a refresh reproduces exactly what clicking that
conversation in the sidebar would do, not a special separate code path. `startNewConversation`
clears the persisted key. Live-verified against the real deployment: sent a message, refreshed
the browser, confirmed the same conversation (with its message) reappeared automatically rather
than a blank "New chat".

## Notes

Depends on ERP-048 for both the underlying `GET /conversations/{id}` fetch and the sidebar list
this restoration is consistent with.

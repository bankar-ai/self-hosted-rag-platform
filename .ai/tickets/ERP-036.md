# ERP-036 — Fix Silent Score-Parse Failure in Generation Evaluation Judge

Status: Done
Depends On: None

## Description

`app/evaluation/judges.py`'s `OllamaLLMClientJudge` (the non-Ragas fallback judge from ERP-030)
silently scores a metric `0.0` when it cannot parse a numeric score out of the judge LLM's response,
rather than retrying or surfacing the failure distinctly from a genuinely bad answer. Verified live
(2026-09-07): a real evaluation run against `gemma3:4b` produced

```
Could not parse a numeric score for answer_relevancy from judge response: ''
Could not parse a numeric score for context_precision from judge response: ''
```

for one of four queries, and that query's `answer_relevancy`/`context_precision` scores were
recorded as `0.00` in the run summary -- indistinguishable in the persisted `generation_evaluation_runs`
row from an answer the judge genuinely rated as 0. This makes the evaluation harness itself
unreliable: a `0.0` score cannot currently be trusted to mean "bad answer" versus "judge LLM
returned an empty/unparseable response."

## Acceptance Criteria

- [x] A parse failure is either retried (bounded, e.g. once) before falling back, or recorded as a
      distinct sentinel (e.g. `None`/NaN, not `0.0`) so it's visibly different from a real low score
      in `generation_evaluation_runs` and in the CLI summary output
- [x] The CLI summary (`uv run python -m app.evaluation.generation_run`) reports parse-failure counts
      separately from the mean score calculation, rather than folding them into the mean silently
- [x] Regression test covering the empty/unparseable judge response case
- [x] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass

## Notes

Found in the same 2026-09-07 live verification session as ERP-034/ERP-035, while confirming
generation answer quality end-to-end against real Ollama. The underlying answers observed in that
run were good (faithfulness 1.00 on all 4 queries) -- this ticket is about the harness's own
reliability, not a regression in generation quality.

**Fixed (2026-09-08)**: did both -- retry AND a distinct sentinel, not either/or.
`app/evaluation/judges.py`'s `_parse_score` now returns `float | None` (was `float`, silently
`0.0` on failure); `OllamaLLMClientJudge.score()` retries once per metric via a new
`_score_with_retry` helper before giving up and returning `None`. `GenerationScores`/
`GenerationQueryResult` (`app/evaluation/schemas.py`) fields are now `float | None`.
`GenerationEvaluationSummary` gained `{faithfulness,answer_relevancy,context_precision}_parse_failures`
counts (default `0`); `app/evaluation/generation_runner.py`'s new `_mean_and_failures` helper
computes each mean over only the non-`None` scores and counts the `None`s, so a run with failures
no longer drags its mean toward 0.0. `app/evaluation/generation_run.py`'s CLI prints an explicit
"Parse failures (excluded from means above): ..." line and shows `N/A` (not a crash or a fake
number) for any per-query `None`. `RagasJudge` is unaffected -- Ragas's own metrics never return
`None`, only `OllamaLLMClientJudge` had this gap. Regression tests: `tests/evaluation/test_judges.py`
(retry-succeeds and retry-still-fails-returns-None cases, replacing the old test that asserted the
wrong `0.0` behavior) and `tests/evaluation/test_generation_runner.py` (a judge that always fails
one metric doesn't drag that metric's mean down and the failure count matches). Verified: ruff/mypy
clean, full suite 367 passed, 97% coverage (real Postgres+Redis).

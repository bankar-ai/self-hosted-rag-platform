# ERP-093 — Self-Service "Delete Account" Button

Status: Backlog
Depends On: None
Category: Feature

## Description

Live feedback (2026-09-24): there's currently no way for a user to delete their own account —
`DELETE /admin/users/{user_id}` (ERP-040) exists but is admin-only. `app/auth/repository.py`'s
`delete_user_and_owned_data` (ERP-040) already implements the actual FK-safe hard-delete of a
user and everything they own (conversations/messages, documents/chunks, refresh tokens, OIDC
identities, per-owner FAISS index file) — this ticket is mostly about exposing that safely to
the user themselves, not building new deletion logic.

## Open Questions (need user decision before implementation)

- **Hard delete or deactivate?** ERP-040's existing function is a genuine hard delete (no
  recovery). Reuse it as-is for consistency with the admin path, or add a soft-delete/grace-period
  option instead? Hard delete matches existing precedent and is simpler.
- **Confirmation flow**: re-enter password before deleting? A typed confirmation (e.g. type
  "DELETE")? Both, per common practice for irreversible account actions?
- **Session handling**: should this also immediately revoke all refresh tokens / log the user
  out client-side (it will, definitionally, once the row is gone) — just confirming the frontend
  redirects to a logged-out state right after, not a broken authenticated UI.

## Acceptance Criteria

- [ ] Decision recorded on the open questions above
- [ ] New user-facing endpoint (e.g. `DELETE /auth/me`) reusing `delete_user_and_owned_data`,
      requiring the caller's own valid access token (no admin role needed, no `user_id` param —
      always acts on the authenticated caller)
- [ ] Frontend: a "Delete account" button (likely near "Log out") gated behind the chosen
      confirmation flow
- [ ] Tests: successful self-delete, confirmation-flow rejection paths, and that a caller cannot
      delete another user via this endpoint (it should be structurally impossible, not just
      tested — the endpoint takes no `user_id`)

## Notes

Should be a small ticket given ERP-040 already did the hard part (the actual data-deletion
logic). Mainly a new thin endpoint + confirmation UI.

# ERP-034 — Fix Default Generation Model Tag Mismatch

Status: Done
Depends On: None

## Description

`GenerationSettings.model` (`app/generation/config.py`) defaults to `"qwen3"`. Ollama only resolves
an untagged model name to an implicit `:latest` tag; it does not fall back to any other tag a user
happens to have pulled. Verified live against a real local Ollama install with `qwen3:8b` (not
`qwen3:latest`) installed:

```
ollama.chat(model="qwen3", ...) -> {"error": "model 'qwen3' not found"}
```

`POST /generation/query` and `POST /generation/query/stream` both 500 on a fresh deployment unless
the operator already knows to set `GENERATION_MODEL` to their exact installed tag -- and that env
var is undocumented today (`.env.example` has no entry for it, unlike the required
`AUTH_JWT_SECRET_KEY`).

## Acceptance Criteria

- [x] `.env.example` documents `GENERATION_MODEL` (and `EMBEDDING_MODEL` if it has the same gap)
      with a comment explaining Ollama's exact-tag resolution behavior and an example matching a
      real `ollama pull` tag (e.g. `qwen3:8b`)
- [x] Decide and implement one of: (a) fail fast at startup with a clear error if the configured
      model isn't present in `ollama list`/`ollama show`, rather than failing on the first user
      request, or (b) keep the current default but make the startup-time requirement explicit in
      logs
- [x] `docs/architecture.md` or a new deployment doc notes that the model tag must match exactly
      what was pulled locally
- [x] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass

## Notes

Found during a live "does this actually work when we make it live" verification session
(2026-09-07): confirmed via direct Ollama API call and via the `app.generation.client.OllamaLLMClient`
code path both failing identically with the default config against a real installed model.

**Fixed (2026-09-08)**: chose the "fail fast" path (option a) via a new operator-run tool rather
than a FastAPI startup hook, to avoid adding a live-Ollama dependency to app startup/test
collection. `app/core/model_check.py` (`verify_model_or_raise`, `check_model_available`,
`list_available_models`) checks a configured model tag against `ollama.Client(host).list()`;
`app/core/check_models.py` is the CLI (`uv run python -m app.core.check_models`) that checks both
`GenerationSettings.model` and `EmbeddingSettings.model` and exits non-zero with an actionable
message (which env var, what's actually installed, the `ollama pull` command to fix it) if either
is missing. Wired into ERP-037's deployment pre-flight checklist. Also added an explicit INFO-level
log line at both `OllamaLLMClient` and `OllamaEmbeddingClient` construction time naming the
configured model/host and pointing at the check tool (the "(b) make it explicit in logs" half,
done in addition to (a) rather than instead of it). `.env.example` now documents `GENERATION_MODEL`
and `EMBEDDING_MODEL`. Hardware/tag guidance also written up in the new `docs/deployment.md`
(shared with ERP-035). Verified: ruff/mypy clean, full suite 367 passed, 97% coverage (real
Postgres+Redis).

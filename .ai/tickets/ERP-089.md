# ERP-089 — Latency Breakdown Dashboard Panel

Status: Done
Depends On: None
Category: Improvement

## Description

Live feedback (2026-09-23): noticeable time taken for uploads/downloads and for answers.
ERP-028/ERP-042 already instrument exactly the spans and metrics needed to see *where* that time
goes (`embedding.generate`, `faiss.search`, `bm25.search`, `retrieval.fuse`/`rerank`/
`expand_sections`, `llm.generate` spans in Tempo; `http_server_duration_milliseconds`,
`llm_generation_duration_seconds` in Prometheus, all in Grafana Cloud already) — none of it is
surfaced as a dashboard panel yet, so diagnosing a slow request currently means manually digging
through Explore.

## Acceptance Criteria

- [x] Add a latency-breakdown panel (p50/p95, per pipeline stage) to the existing "AI Platforms
      — Service Observability" Grafana dashboard, using data already being collected — no new
      instrumentation expected to be needed
- [x] If a specific stage turns out to dominate (e.g. Modal cold starts, consistent with
      ERP-037's 52-59s concurrent-load finding), split that out as its own targeted follow-up
      ticket rather than folding a fix into this one
- [x] Also check whether ingestion upload time (PDF upload → job DONE, including any Cloud Run
      docling round-trip) is separately visible, since "downloads" in the user's report may
      really mean document upload/processing time, not response download

## Implementation (2026-09-25)

Added a "Latency Breakdown" row (4 panels) to the same dashboard ERP-087 extended:

- **HTTP request duration p50/p95** (Prometheus `histogram_quantile` over
  `http_server_duration_milliseconds_bucket`, auto-instrumented, all endpoints combined).
- **LLM generation duration p50/p95** (same technique over the hand-written
  `llm_generation_duration_seconds` histogram, ERP-042).
- **RAG pipeline stage latency p50/p95** — the interesting finding here: `embedding.generate`,
  `faiss.search`, `bm25.search`, `retrieval.fuse`/`rerank`/`expand_sections`, and `llm.generate`
  are hand-written **spans** (ERP-028), not Prometheus histograms — there's no
  `*_duration_seconds` metric per retrieval sub-stage, only the two above. Getting p50/p95 per
  stage without adding new instrumentation (as the AC hoped) meant using **Tempo TraceQL
  metrics** (`quantile_over_time(duration, ...) by (name)`) instead of PromQL — confirmed
  supported on this Grafana Cloud plan by testing directly against the API, with one real
  constraint: **TraceQL metrics queries are capped at a 25-hour time range** (a Tempo-side
  limit, returns a clean 400 above that) — fine for this dashboard's 3h default view and even
  its 1d timepicker preset, but selecting a longer custom range on this specific panel will
  error rather than silently truncate.
- **Ingestion job duration p50/p95** — directly answers this ticket's third AC item: yes, total
  upload-to-done time (including any Cloud Run docling round-trip) **is** already visible today,
  via FastAPI's auto-instrumented `BackgroundTask run_ingestion_job` span (also TraceQL
  metrics). It's whole-job granularity only — parse/chunk/embed/persist aren't broken out
  as separate spans within it, so a slow run is visible but not automatically attributable to
  one sub-step from this panel alone.

All 4 panel queries validated by direct execution against Grafana's `/api/ds/query` API before
being added — confirmed real (if currently sparse, low-traffic-deployment) data flows through
`embedding.generate` and the HTTP duration histogram; `llm.generate` and the other retrieval
sub-stages had no matching spans in the last 24h at the time of writing, simply reflecting that
no chat query happened to run in that window, not a query/instrumentation problem.

No follow-up ticket spun off for a dominant stage (second AC item) — traffic in the checked
window was too sparse to identify one; ERP-091 already addressed the known Modal/Cloud
Run/Neon cold-start costs directly from ERP-037/086's existing evidence rather than waiting on
this panel to accumulate enough data first.

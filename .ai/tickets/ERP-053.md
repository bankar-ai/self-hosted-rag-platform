# ERP-053 — Manual Retry Path for Failed Ingestion Jobs

Status: Done
Depends On: ERP-049
Category: Lapse — a failed job was always a dead end; the design never considered giving the
user a way back without re-selecting the file from disk

## Description

Confirmed in code: a failed ingestion job just sits at `status: "failed"` with an error message.
There is no automatic retry and no "retry this file" action — ERP-049 added a "Dismiss" button,
but that only removes the failed entry from the local list; the user must re-select the same
file from their filesystem to try again.

Scope: a **manual** retry (re-run the same already-uploaded bytes without the user re-picking
the file) is the target here — automatic retry-with-backoff is a materially different feature
(it only helps transient failures like a Modal cold-start timeout, and risks silently retrying
a permanently-bad PDF) and is explicitly out of scope unless a follow-up decides otherwise.

## Acceptance Criteria

- [x] Backend: a retry re-runs ingestion for the same uploaded file without requiring a fresh
      upload. Resolved the original open question: the uploaded temp file was actually never
      deleted on failure (a separate, pre-existing minor leak, also fixed here for the success
      case) — so a pure backend replay against the original file path is both possible and the
      simplest correct design; no "browser keeps the File object" fallback was needed.
- [x] Frontend: a "Retry" button appears next to a failed upload, calling the new endpoint.
- [x] A retried job gets a fresh `job_id` (existing failed job record is not mutated in place).

## Resolution (2026-09-18)

`app/ingestion/jobs.py`'s `JobRecord` now retains `pdf_path`/`filename`; new `retry_job(job_id,
owner_id)` validates ownership and that the job is currently `FAILED`, then creates a fresh job
against the same stored file path (original record untouched). New `POST
/ingestion/jobs/{job_id}/retry` endpoint (`app/ingestion/router.py`), 404 for unknown/wrong-owner/
not-failed, matching the existing job-status 404 convention. Along the way, fixed a real
pre-existing resource leak found while implementing this: uploaded temp files were never cleaned
up after a job finished, success or failure — `run_ingestion_job` now deletes the temp file (and
its directory, if now empty) on success; a failed job deliberately keeps its file so retry has
something to re-run against.

Frontend: `DocumentsPage.tsx` shows a "Retry" button (alongside the existing "Dismiss") for
failed in-flight uploads, calling the new endpoint and resuming polling under the new job ID.

Verified: a real corrupt-but-magic-byte-valid PDF uploaded, failed, retried via the live API
(local dev stack) — the retry created a new job, re-ran ingestion against the identical stored
file, and failed identically (proving genuine re-execution, not a status flip), while the
original failed job record remained untouched. New tests cover retry's success/ownership/status
preconditions at both the `jobs.py` and router level (backend: 424 -> 440 tests passing this
session, 97%+ coverage; ruff/mypy clean).

# ERP-046 — Retrieval Relevance Guardrail (Non-Questions Get Answered Anyway)

Status: Done
Depends On: None
Category: Lapse — the pipeline works exactly as designed (top-k retrieval, no relevance
threshold); the design never considered the irrelevant-query case, so nothing is technically
broken against spec, but it's a real gap worth closing, not optional polish

## Description

Surfaced during ERP-043's live UI review: sending a plain greeting ("hi") to `/generation/query`
returned a full, confidently-worded, cited answer about an unrelated topic (ladder safety, from
whatever document happened to be nearest in the vector index) instead of recognizing "hi" isn't
a real question. This is a backend retrieval/generation-quality issue, not a frontend bug.

Root cause: `app/retrieval/service.py`'s hybrid search (FAISS + BM25 + RRF fusion) always returns
`top_k` results, regardless of how semantically close the nearest match actually is — there's no
minimum-relevance threshold anywhere in the pipeline. `app/generation/prompt.py`'s system prompt
tells the LLM to say when context is insufficient, but doesn't help here since the retrieved
chunks aren't recognized as irrelevant to begin with — from the LLM's perspective, it received
real chunks and dutifully answered from them.

## Acceptance Criteria

- [x] Resolved the open scoping questions with a two-layer fix: (1) a deterministic greeting
      fast-path for the concrete demonstrated case ("hi"/"hello" → a fixed friendly reply, no
      retrieval, no LLM call), and (2) a distance-based relevance gate on the vector leg in
      `retrieval.service.search()` (not just the generation layer, so `/retrieval/query` benefits
      too) for the general off-topic case.
- [x] A plain greeting returns a simple, fixed response with zero citations.
- [x] An off-topic real question (not a greeting, but unrelated to any ingested document) returns
      the existing "not enough information" style message instead of a hallucinated cited answer.
- [x] The relevance threshold is live-calibrated against the real embedding model, not guessed.

## Resolution (2026-09-18, second pass)

Root cause confirmed live: a plain "hi" retrieved `top_k` chunks regardless of relevance (RRF's
fused score is rank-based, not a true similarity measure, so it can't distinguish "this chunk is
a great match" from "this chunk merely ranked highest among irrelevant candidates") — the LLM
then dutifully tried to answer from irrelevant context and, in one observed case, ended up
paraphrasing its own system prompt back at the user as if it were an answer.

Two-layer fix:

1. **Greeting fast-path** (`app/generation/service.py`): a short, deterministic regex match
   against common greetings/pleasantries ("hi", "hello", "hey", "how are you", etc., allowing
   trivial punctuation) short-circuits *before* retrieval or any LLM call, returning a fixed
   friendly reply with zero citations. Cheap, deterministic, and directly fixes the demonstrated
   case — no model call needed for something this unambiguous.
2. **Relevance gate on the vector leg** (`app/retrieval/service.py`): `FaissIndex.search`'s raw
   L2 distances (previously discarded after producing rank order for RRF) are now checked against
   a new `RetrievalSettings.max_relevant_distance` before fusion — a query whose nearest vector
   match exceeds this distance contributes no candidates to fusion from the vector leg (BM25 is
   untouched, since keyword search has its own natural relevance signal via `ts_rank`). If fusion
   then produces nothing, `search()` returns `[]` exactly as it already does for a truly empty
   index, and `generate()`/`generate_stream()`'s existing `NO_CONTEXT_ANSWER` short-circuit
   handles the rest unchanged — no new response type was needed.

Threshold live-calibrated against the real embedding model (`nomic-embed-text`), not guessed:
measured min L2 distance from 5 off-topic/greeting-like queries ("hi", "hello there", "how are
you today", "what is the capital of France", "tell me a joke") and 3 on-topic real questions
against 3 real ingested chunks. On-topic distances landed at 0.74-0.85; off-topic at 1.02-1.15 --
a clean gap. `RetrievalSettings.max_relevant_distance` defaults to **0.95**, sitting in that gap
with margin on both sides. Re-ran the ERP-029 evaluation harness afterward against real Ollama to
confirm zero regression: Precision@3=0.333, Recall@3=1.000, MRR=1.000 -- an exact match to the
ERP-029/ERP-041 baseline. Live-verified via the real API: "hi"/"hello there" both return the
greeting fast-path's fixed reply; "what is the capital of France" (genuinely off-topic, not a
greeting) returns the existing "not enough information" message; a real on-topic question still
returns a correct, cited answer.

## Notes

Not part of ERP-043's original scope (frontend/UI) — resolved in a follow-up session after being
demonstrated live on the deployed app. Did not touch the ERP-029 evaluation harness's golden

sanity check.

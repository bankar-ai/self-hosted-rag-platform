# ERP-038 — Wire Live Deployment's Traces to Grafana Cloud (Free Tier)

Status: Done
Depends On: ERP-037

## Description

ERP-028 built full OpenTelemetry tracing/metrics instrumentation into the app (hand-written spans
at `embedding.generate`, `faiss.search`, `bm25.search`, `retrieval.fuse`/`rerank`/`expand_sections`,
`llm.generate`, plus FastAPI/SQLAlchemy/Redis/httpx auto-instrumentation) -- but the live deployment
(ERP-037: GCP `e2-micro` + Neon + Upstash + Modal) has nowhere to send it. Running Jaeger/Prometheus
locally on the VM (as `docker-compose.yml` does for local dev) isn't viable: the VM has ~958MB total
RAM and no headroom for another local service on top of the app itself. `app/core/telemetry.py`'s
`configure_telemetry()` currently defaults to `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317`,
which is unreachable on the live VM -- producing harmless but noisy repeated "connection refused"
log lines, and meaning there is currently no way to see what a live request actually did (which
stage was slow, which call failed) without SSHing in and reading raw journald output.

Grafana Cloud's free tier (50GB logs + 50GB traces + 10K metrics/month, hosted, no self-hosting)
is a genuine "one place to look when something's wrong" for the live deployment, and traces
specifically require close to zero code change: pointing the existing `OTEL_EXPORTER_OTLP_ENDPOINT`
env var (plus the auth header Grafana Cloud requires) at their OTLP endpoint should light up every
span already written into the codebase, with the deployment's app-side memory footprint unaffected
(it's a remote export, not a local collector process).

## Notes

Deliberately scoped to traces only. Metrics (current exporter is pull-based, meant for a local
Prometheus scraping `/metrics` -- would need either a remote-write agent or switching to push-based
OTLP metrics, more setup than traces) and plain application logs (not currently OTLP-exported,
would need either a shipping agent -- more VM RAM, a real cost given the tight budget -- or
switching the logging handler to export via OTLP directly) are explicitly deferred; see ERP-039 for
logs. This ticket is the highest-value, lowest-effort piece: traces alone answer "which stage
failed or was slow" for most real debugging needs.

## Resolution (2026-09-15)

Grafana Cloud stack `microstarfish1843` (org, region `ap-south-1`) created, a traces-scoped API
token (`rag-platform-vm-traces`) generated via the OpenTelemetry quick-setup flow. This confirmed
Grafana's OTLP gateway (`https://otlp-gateway-prod-ap-south-1.grafana.net/otlp`, a path-based HTTPS
URL) expects **OTLP/HTTP**, not the gRPC transport `app/core/telemetry.py` had hardcoded -- the one
real code change: `_build_span_exporter()` now picks the exporter class based on the standard
`OTEL_EXPORTER_OTLP_PROTOCOL` env var (`"grpc"`, unset/default, unchanged for local Jaeger;
`"http/protobuf"` for Grafana Cloud), using the same `opentelemetry-exporter-otlp` meta-dependency
already in `pyproject.toml` -- no new dependency. Also added `OTEL_SERVICE_NAME` to the VM's `.env`
after noticing traces initially showed up as `unknown_service` (OTel's default when unset).

Deployed to the live VM (`git pull` + `uv sync` + `.env` update + `systemctl restart`), then
verified end-to-end with real traffic, not just config: registered a throwaway test user, ran a
real `POST /retrieval/query`, and confirmed in Grafana Cloud's Explore -> Tempo -> Search view a
trace rooted at `self-hosted-rag-platform POST /retrieval/query` with `embedding.generate`,
`faiss.search`, `bm25.search`, and `retrieval.fuse` correctly nested underneath (plus their own
Redis/Postgres sub-spans) -- exactly the span tree ERP-028 instruments. Verified: ruff/mypy clean,
full suite 369 passed locally against real Postgres/Redis/Jaeger.

**All acceptance criteria met. This ticket is complete.**

# ERP-116 — Session security hardening: idle timeout, absolute session cap, httpOnly cookies

Status: Done
Depends On: None
Category: Bug

## Description

Code review (2026-09-28, prompted by the user noticing "no timed logout" in the live app) found
three real gaps in `app/auth/` against standard session-management practice:

1. **No absolute session lifetime.** `refresh_access_token()` rotates on every use via
   `_issue_tokens()`, which sets a *fresh* 30-day expiry each time (`app/auth/service.py`,
   `expires_at = now + timedelta(days=settings.refresh_token_expire_days)`). As long as a
   session is used at least once every 30 days, it never expires — there is no cap on total
   session age.
2. **No idle-timeout logout.** The 30-minute access-token expiry is invisible to the user —
   `apiClient.ts` silently refreshes on any `401` with no re-authentication prompt. A device
   left logged in and unattended never times out on its own.
3. **Tokens stored in `localStorage`, not `httpOnly` cookies** (`frontend/src/lib/tokenStorage.ts`).
   Accessible to any JS running on the page — an XSS vulnerability anywhere in the app, or a
   malicious browser extension, could exfiltrate both tokens and impersonate the user
   indefinitely (replay the refresh token periodically, per gap #1). Notably, this app already
   knows how to set a proper `httpOnly`/`Secure`/`SameSite` cookie correctly — the OIDC PKCE
   state cookie in `app/auth/oidc.py` (`ERP-032`) — just never applied that pattern to the
   actual session tokens.

Combined, an attacker who steals a refresh token via XSS gets indefinite access with no forced
re-authentication and no idle-based logout to interrupt it. Not an auth-bypass (a valid token is
still required for every request) but a real gap against OWASP session-management guidance,
worth closing given this app handles user-uploaded documents and has admin accounts.

## Acceptance Criteria

- [x] **Absolute session cap**: `_issue_tokens()` gained a `session_expires_at` parameter;
      `refresh_access_token()` passes the *presented* token's unchanged `expires_at` through on
      rotation instead of computing a fresh `now + refresh_token_expire_days` — rotation still
      extends the opaque token value (needed so a used-then-replayed token is rejected), but
      never pushes the session's total lifetime further out. `login`/`register`/OIDC login
      (genuinely new sessions) still get a fresh expiry via the same parameter left unset.
- [x] **Idle timeout**: new `frontend/src/lib/activityTracker.ts` records real user interaction
      (click/keydown) to `localStorage`, threshold 30 min (matches `access_token_expire_minutes`
      exactly, both real and deliberate — not a coincidence). `apiClient.ts`'s `tryRefresh()`
      checks this *before* even attempting `/auth/refresh`; if idle-timed-out, it skips the
      network call entirely and expires the session. `AuthContext.tsx` reacts immediately via a
      new `SESSION_EXPIRED_EVENT` (existing `AuthGuard`'s `isAuthenticated` check handles the
      redirect to `/login` unchanged).
- [x] **`httpOnly` cookie migration**:
      - New `app/auth/cookies.py`: `set_auth_cookies()`/`clear_auth_cookies()`, plus the CSRF
        double-submit token generation. `POST /auth/login`/`/refresh` and the OIDC callback
        (see below) call it; the JSON body now returns only `{"user_id": ...}`
        (`AuthActionResponse`), never the raw tokens.
      - `POST /auth/logout` reads the refresh token from its cookie (not a request body
        anymore) and clears all three cookies.
      - `app/auth/dependencies.py`'s `get_current_user` reads `access_token` from the cookie,
        replacing `OAuth2PasswordBearer`/`Authorization` header extraction entirely.
      - `app/main.py`'s CORS gained `allow_credentials=True`. Verified the live VM's
        `CORS_ALLOWED_ORIGINS` was already scoped to the exact Vercel origin, never `*` (a
        wildcard is incompatible with credentialed CORS by spec) — no VM-side CORS change
        needed.
      - **CSRF, implemented as the double-submit pattern**, not skipped: a fourth, deliberately
        non-`httpOnly` `csrf_token` cookie is set alongside the two auth cookies;
        `get_current_user` verifies the `X-CSRF-Token` header (constant-time comparison) against
        it for every mutating method. This is mandatory here, not optional hardening — the
        frontend (Vercel) and API (the VM) are different registrable domains, so the cookies
        must be `SameSite=None` just to be sent on a real cross-origin request at all, and
        `SameSite=None` alone provides zero CSRF protection on its own. `/auth/refresh` and
        `/auth/logout` don't go through `get_current_user` (they read the refresh cookie
        directly) — a real gap noticed during implementation and closed by calling
        `verify_csrf()` explicitly in both, after the "cookie present at all" check so a
        no-session request still gets a clean 401, not a 403.
      - `AUTH_COOKIE_SECURE` setting (`app/auth/config.py`) controls `Secure`/`SameSite`
        together: `true` (default, production) → `Secure=True, SameSite=None`; `false` (local
        plain-http dev only) → `Secure=False, SameSite=Lax`.
      - `frontend/src/lib/tokenStorage.ts` rewritten to store only a non-sensitive `user_id`
        marker (the one thing the frontend still needs synchronously, since it can no longer
        decode a JWT it never receives); `frontend/src/lib/jwt.ts` deleted (its only caller was
        the now-removed access-token decoding in `AuthContext.tsx`). `apiClient.ts`'s manual
        `Authorization` header removed; every `fetch` now sends `credentials: "include"` and, on
        a mutating method, an `X-CSRF-Token` header read fresh from `document.cookie` before
        each request (never cached, since refresh rotates the CSRF cookie too).
      - **Breaking change, accepted**: every existing logged-in user is signed out the moment
        this deploys — no dual-support transition period, a clean cutover, matching the
        project's actual scale (5-20 test users).
- [x] Full backend test suite (620 passed, 95.86% coverage) + `ruff`/`mypy --strict` clean;
      frontend (100 passed) `tsc -b`/`oxlint`/`vite build` clean.
- [x] **Live-verified on the deployed VM (2026-09-29)** — backend (`deploy_vm.bat`, commit
      `219b1d9`) and the Vercel frontend (same commit, confirmed via GitHub's commit-status API)
      deployed together, no staggering. Verified end-to-end against the real public URLs, not
      just localhost: register → login (response body carries only `user_id`, no tokens) → all
      three cookies (`access_token`/`refresh_token`/`csrf_token`) confirmed set → `GET /auth/me`
      authenticates via cookie alone → a mutating `POST` without the `X-CSRF-Token` header
      correctly gets `403` → the same request with the header succeeds (`200`), and its response
      also carried `duration_seconds` (`ERP-115`), confirming both tickets live together in one
      real request. Also statically confirmed the live Vercel JS bundle contains the new code
      (`rag-user-id`, `rag-last-activity`, `csrf_token` all present; the old `rag-auth-tokens`
      key completely absent) rather than a stale cached build. Throwaway verification user
      deleted afterward via the `ERP-040` admin endpoint — itself exercised end-to-end through
      the new cookie+CSRF flow (admin login → list → CSRF-protected delete, all cookie-based).

## Notes

This was the more architecturally significant of the two tickets logged this session (`ERP-115`
being the smaller one) — it changes how every frontend request authenticates, not just one
endpoint. Real bugs found and fixed *during* implementation, not assumed away up front:

1. Cookie-based `SameSite=None` is required for this project's cross-origin topology (Vercel
   frontend, VM backend, different registrable domains) — a same-site `SameSite=Lax` design
   (the more commonly-seen default) would have silently failed to attach the cookie on any real
   cross-origin `fetch` at all, only ever working in this repo's own same-origin test setup.
2. `/auth/refresh`/`/auth/logout` don't route through `get_current_user`, so embedding the CSRF
   check only there (the obvious first design) would have left both completely unprotected.
3. `apiFetch`'s automatic 401→refresh→retry logic used to be implicitly skipped for `/auth/login`
   itself (no stored token yet meant the old `tryRefresh()` short-circuited before any network
   call) — cookies being invisible to JS removed that implicit guard, so a wrong-password login
   attempt would have also fired a pointless `/auth/refresh` call. Fixed with an explicit
   `AUTH_TOKEN_ENDPOINTS` exclusion list (scoped narrowly — `/auth/me` still gets the
   refresh-and-retry behavior, since a 401 there *is* a legitimately stale-access-token case).
4. `TestClient`'s cookie jar is client-scoped, not request-scoped, unlike the old
   `Authorization`-header tests where any request could independently specify whose token to
   use. Every test exercising two identities against one shared `client` needed a second
   `TestClient` instance instead — a real, repo-wide test-isolation implication of this
   migration, not just an auth-module concern (found in `tests/generation/`, `tests/ingestion/`,
   and `tests/retrieval/` too).

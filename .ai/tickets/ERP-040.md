# ERP-040 — Admin: Delete a User (Hard Delete)

Status: Done
Depends On: ERP-027

## Description

ERP-027 shipped admin user-management (list, enable/disable, revoke-sessions) but no way to
actually remove a user. Several verification passes since then (ERP-037's concurrent-load smoke
test, ERP-038/ERP-039's live trace/log verification, and the Grafana dashboard build) each left a
throwaway test user in the live database with no way to clean it up. Adds a genuine hard-delete
admin endpoint to close that gap.

## Acceptance Criteria

- [x] `DELETE /admin/users/{user_id}` implemented, gated by `require_role("admin")`
- [x] Deletes every row the user owns before the user row itself, in FK-safe order: conversation
      messages -> conversations, chunks -> documents, refresh tokens, OIDC identities, then the
      user -- mirroring the existing `app.evaluation.repository.cleanup_eval_data` pattern
- [x] Also deletes the user's per-owner FAISS index file on disk (`OwnerFaissIndexStore.path_for`,
      ERP-031), best-effort -- a failure here must not raise or block the rest of the deletion
- [x] An admin cannot delete their own account through this endpoint (409) -- avoids an easy
      self-lockout footgun
- [x] Unknown `user_id` returns 404; non-admin caller returns 403; no token returns 401 (added to
      `tests/test_auth_required.py`'s protected-routes sweep)
- [x] Irreversible and undocumented as anything else -- no soft-delete, no confirmation step (an
      admin-only, deliberately destructive action, consistent with how `revoke-sessions` already
      works)
- [x] `ruff`, `mypy --strict`, and `pytest-cov --cov-fail-under=90` all pass

## Notes

Hard delete, not soft delete (no `deleted_at` column) -- this is a cleanup tool for stray
test/demo accounts, not a GDPR-style data-retention feature; revisit if that need ever arises.

## Resolution (2026-09-16)

Implemented via `app.auth.repository.delete_user_and_owned_data` (FK-safe bulk deletes, mirroring
`app.evaluation.repository.cleanup_eval_data`) and `app.auth.service.delete_user`/
`_delete_owner_faiss_index`, wired to `DELETE /admin/users/{user_id}` in `app/auth/router.py`.
Verified: ruff/mypy clean, full suite 381 passed, 96.66% coverage (auth module: 100% on
`repository.py`, 99% on `service.py` -- the one uncovered line is a pre-existing unrelated branch).

**Live-verified, not just unit-tested**: the live deployment had no bootstrapped admin account at
all (ERP-027 shipped the admin endpoints but never created one) -- created a real first admin
(`ops-admin@self-hosted-rag-platform.internal`, credentials in the credentials store) directly via
the repository layer on the VM, distinct from the pre-existing migration-seeded `system@internal`
account (which has an intentionally-invalid password hash and can't log in). Used that admin's
token to call the live `DELETE /admin/users/{id}` endpoint against the three throwaway test users
left behind by ERP-038/ERP-039/the Grafana dashboard build (`erp038-verify@example.com`,
`erp039-verify@example.com`, `dashboard-verify@example.com`) -- all three returned `204`, and
`GET /admin/users` afterward confirmed only the two legitimate admin accounts remain.

Merged to `develop` (commit `ca768f9`); not yet promoted to `main`.

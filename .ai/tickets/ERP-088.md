# ERP-088 — Design: Evaluating Live Production Traffic (Not Just the Golden Dataset)

Status: Backlog
Depends On: None
Category: Improvement

## Description

`app/evaluation/`'s harnesses (ERP-029/030) only ever score a fixed 4-query golden dataset —
there's no visibility into whether *real* user queries (what people actually ask in production)
are well-grounded, relevant, or failing. This is a design ticket, not an implementation one: the
options have real cost/latency/complexity trade-offs that need a decision before writing code.

## Options to Evaluate

- **Inline judging**: run the LLM-judge (Ragas or the Ollama fallback, per ERP-030) against
  every real request before returning the answer. Simplest mentally, but adds judge-LLM latency
  and cost to every single user-facing request — likely a non-starter given ERP-037's Modal
  cold-start latency findings already made response time a concern.
- **Async sampling**: log a sample of real (query, answer, retrieved-context) tuples, judge them
  out-of-band (e.g. a scheduled job, reusing `generation_runner.py`'s judge plumbing) without
  affecting user-facing latency. Needs a decision on sample rate and where sampled data is
  persisted/reviewed.
- **Explicit user feedback as a proxy**: the frontend already has a thumbs up/down control
  (visible in the mobile screenshots from ERP-085's investigation) — confirm whether that
  feedback is currently persisted anywhere, and whether it's a cheaper/complementary signal to
  LLM-judge sampling rather than a replacement for it.

## Acceptance Criteria

- [ ] Decide an approach (or explicitly defer with a documented reason)
- [ ] Confirm whether thumbs up/down feedback is currently captured server-side at all
- [ ] If approved for implementation, spin off a follow-up ticket scoped to just that approach

## Notes

Depends conceptually on ERP-087 existing first (or at least the same dashboard surface) so
sampled live-traffic scores have somewhere to land. No research/implementation started yet.

# ERP-088 — Design: Evaluating Live Production Traffic (Not Just the Golden Dataset)

Status: Done
Depends On: None
Category: Improvement

## Description

`app/evaluation/`'s harnesses (ERP-029/030) only ever score a fixed 4-query golden dataset —
there's no visibility into whether *real* user queries (what people actually ask in production)
are well-grounded, relevant, or failing. This is a design ticket, not an implementation one: the
options have real cost/latency/complexity trade-offs that need a decision before writing code.

## Options to Evaluate

- **Inline judging**: run the LLM-judge (Ragas or the Ollama fallback, per ERP-030) against
  every real request before returning the answer. Simplest mentally, but adds judge-LLM latency
  and cost to every single user-facing request — likely a non-starter given ERP-037's Modal
  cold-start latency findings already made response time a concern.
- **Async sampling**: log a sample of real (query, answer, retrieved-context) tuples, judge them
  out-of-band (e.g. a scheduled job, reusing `generation_runner.py`'s judge plumbing) without
  affecting user-facing latency. Needs a decision on sample rate and where sampled data is
  persisted/reviewed.
- **Explicit user feedback as a proxy**: the frontend already has a thumbs up/down control
  (visible in the mobile screenshots from ERP-085's investigation) — confirm whether that
  feedback is currently persisted anywhere, and whether it's a cheaper/complementary signal to
  LLM-judge sampling rather than a replacement for it.

## Acceptance Criteria

- [x] Decide an approach (or explicitly defer with a documented reason)
- [x] Confirm whether thumbs up/down feedback is currently captured server-side at all
- [x] If approved for implementation, spin off a follow-up ticket scoped to just that approach

## Decision (2026-09-24)

**Async sampling**, confirmed viable by code investigation — spun off as **ERP-097**.

- **Inline judging: rejected.** Confirmed correct as scoped: adds judge-LLM latency to every
  user-facing request, directly working against ERP-091's latency concerns. Not revisited.
- **Explicit feedback (thumbs up/down): confirmed captured server-side already.**
  `MessageFeedbackRecord`/`message_feedback` table (`app/generation/models.py`, ERP-045) stores
  one row per message, upserted on rating change, access-checked via a join against the caller's
  own conversations. It's a real, already-collected signal — but a **complement** to LLM-judge
  sampling, not a replacement: most answers get no rating at all (opt-in, low response rate by
  nature), so it can't alone answer "how well is the system doing on average."
- **Async sampling: the pick.** `app/evaluation/generation_runner.py`'s existing
  `judge.score(query, answer, contexts)` plumbing (Ragas or the Ollama-judge fallback, ERP-030)
  is directly reusable — it doesn't care whether the query came from the golden dataset or a
  real conversation. What's needed to sample real traffic:
  - `contexts` isn't persisted verbatim: `ConversationMessage.citations` (JSONB) stores citation
    *metadata* only (`chunk_id`, `document_id`, `page_start/end`, `score`, ... —
    `app/generation/schemas.py:Citation`), not chunk text. A sampling job re-resolves each
    citation's `chunk_id` to its text via the existing chunk-lookup path at sample time, and
    should tolerate/skip a citation whose chunk (or whole document) was deleted since — not
    every historical citation is guaranteed to still resolve.
  - No sample-rate or storage decision made yet — ERP-097 to scope: a scheduled job (matching
    "reusing `generation_runner.py`'s judge plumbing" from this ticket's own Options section),
    a chosen sample rate, and where scored samples land (most likely alongside or extending
    `generation_evaluation_runs`, since ERP-087's dashboard already reads that table — but ERP-097
    should confirm the shape rather than assume it, since live-traffic rows need a `conversation_id`/
    `message_id` back-reference the golden-dataset table has no reason to carry).

## Notes

Depends conceptually on ERP-087 existing first (or at least the same dashboard surface) so
sampled live-traffic scores have somewhere to land. No research/implementation started yet.

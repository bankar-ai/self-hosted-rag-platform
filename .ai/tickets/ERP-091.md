# ERP-091 — Reduce Perceived/Actual Latency for Answers, Uploads, and Login

Status: Done
Depends On: None
Category: Improvement

## Description

Live feedback (2026-09-24): users notice real waiting time both (a) after asking a question,
waiting for an answer, and (b) after uploading a document, waiting for ingestion to finish.
This is a "make it faster" ask that first needs "where does the time actually go", since two
different known infra characteristics are the likely dominant causes, not application code:

1. **Chat answers**: the frontend already consumes `POST /generation/query/stream`
   (`ChatPage.tsx:284`) via SSE, so tokens should stream in rather than the UI blocking on one
   big response — that part is not the gap. The likely dominant cost is Modal Ollama's
   scale-to-zero cold start: ERP-037's own concurrent-load smoke test measured 52-59s per
   generation flow under concurrent traffic, attributed to Modal spinning up a fresh container
   per request rather than reusing a warm one. `min_containers=1` would remove this but was
   explicitly declined in ERP-037 to preserve free-tier cost savings — worth revisiting now that
   real users are hitting it.
2. **Document uploads**: the OCR-fallback path (Cloud Run docling service, `min-instances=0`)
   has the same scale-to-zero cold-start shape — log evidence from ERP-086's investigation shows
   ~1-2 minutes of model-loading time on a cold start before a request is even processed.
3. **Login (added 2026-09-24)**: live feedback reports login taking 3-5+ seconds. Not yet
   investigated in code, but the leading hypothesis is Neon's own serverless Postgres
   scale-to-zero cold start — a third, independent cold-start surface alongside Modal (chat) and
   Cloud Run (uploads), since login is the first DB-touching request in a fresh session.

## Acceptance Criteria

- [x] Use ERP-089's latency-breakdown panel (once built) or direct trace inspection to confirm
      which stage(s) actually dominate wall-clock time for both flows, rather than assuming
- [x] Decide, with the user, between UX mitigation (progress/status indicators that make the
      wait legible even if the underlying time doesn't shrink) and actual latency reduction
      (e.g. `min_containers=1` on Modal and/or Cloud Run docling, trading cost for speed)
- [x] Implement whichever is decided; if a paid trade-off is chosen, document the expected cost
      delta before deploying

## Decision (2026-09-24, confirmed by user 2026-09-25)

**UX mitigation, not paid infra.** Confirmed the dominant-stage question using existing
documented evidence (ERP-037's concurrent-load smoke test, ERP-086's Cloud Run OOM
investigation) rather than waiting on ERP-089's panel — ERP-089 hadn't been built yet, and the
existing numbers were specific and load-bearing enough to decide without it:

| Service | Cost to keep warm (`min_containers=1` / `min-instances=1`) |
|---|---|
| Modal Ollama (chat) | ~$430/month (T4 GPU, ~$0.59/hr × 730 hr) |
| Cloud Run docling (uploads) | ~$175-200/month (2 vCPU / 8Gi × 730 hr, post free-tier) |
| Neon Postgres (login) | A keep-alive ping needs ~183 CU-hrs/month against a 100 CU-hrs free allowance -- already over budget before any real usage |

Combined ~$600-650/month against ADR-008's explicit "2-3 month test, 5-20 users, free-tier by
design" scope -- not a close call. User confirmed: proceed with UX mitigation only, no paid
infra changes.

## Implementation

- **Backend**: `app/core/router.py`'s new `GET /health` (deliberately unauthenticated, touches
  Postgres via `SELECT 1`) serves double duty -- an uptime-check target for ERP-090 and a
  pre-auth Neon wake-up ping the login page fires on mount. `app/generation/client.py`'s new
  `OllamaLLMClient.ping()` (calls Ollama's cheap `list()` models endpoint, not a real
  generation) backs `app/generation/service.py`'s `warmup_llm()`, exposed as
  `POST /generation/warmup` -- fired by the chat page on mount to start Modal's cold start
  before the user sends their first message. Both pings are best-effort: a failure is logged
  and swallowed, never surfaced, since the real request pays the cold-start cost regardless.
- **Frontend**:
  - `LoginPage.tsx`: fires the `/health` pre-warm ping on mount; added a genuine submitting
    state (disables the form, "Logging in.../Registering..." button text -- there was no
    pending-state feedback at all before this) and a "this can take a few seconds..." hint
    after 2s of no response.
  - `ChatPage.tsx`: fires the `/generation/warmup` ping on mount; the pending-assistant
    typing indicator gains a "Waking up the model — this can take up to a minute the first
    time" hint after 5s with zero tokens received, cleared the moment the first token arrives.
  - `DocumentsPage.tsx`/`documentsStore.ts`: `RecentDocument` gained `startedAt` (preserved
    across polls, unlike `lastUpdated` which resets every 2s tick) so a job still "processing"
    past 20s shows "Complex documents may need extra processing time (up to a couple of
    minutes)" -- targets the OCR-fallback cold start specifically, not the fast path.

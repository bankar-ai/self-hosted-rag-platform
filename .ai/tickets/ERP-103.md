# ERP-103 — Conversation and Document Lists Have No Pagination or Limit

Status: Backlog
Depends On: None
Category: Improvement

## Description

Found during live dashboard/UX review (2026-09-27), while answering "how many chats/documents
does the UI show — is there a limit?": there isn't one, anywhere in the stack.

- `app/generation/repository.py`'s `list_conversations_for_owner` returns **every** conversation
  the caller owns, newest first, no `LIMIT`.
- `app/ingestion/repository.py`'s `list_documents_for_owner` returns **every** document the
  caller owns, newest first, no `LIMIT`.
- Neither `Sidebar.tsx` (conversations) nor `DocumentsPage.tsx` (documents) truncates or
  paginates client-side either — both render the full list they're given.

At current low/sporadic traffic this is harmless, but it's unbounded growth with no ceiling:
`GET /conversations` and `GET /documents` payload size, and the corresponding sidebar/page
render cost, both scale linearly with how long an account has been in use, with nothing capping
either side.

## Acceptance Criteria

- [ ] Decide the approach: server-side pagination (cursor or offset-based) vs. a simple fixed
      cap with a "show more" affordance vs. a hard limit with no further access to older items.
      A cap-with-"show more" is likely the simplest change consistent with this project's
      "don't over-engineer" guidance, unless there's a reason a real cursor-paginated API is
      needed.
- [ ] `GET /conversations` and `GET /documents` (or whichever shape is chosen) bounded, not
      unbounded.
- [ ] Frontend updated to request/display accordingly (e.g. a "load more" button, or simple
      truncation with a count).
- [ ] Existing callers/tests updated for the new response shape without breaking them.

## Notes

Low urgency at current traffic scale — filed so it's tracked before it becomes a real problem,
not because it's causing one today.

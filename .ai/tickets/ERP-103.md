# ERP-103 — Conversation and Document Lists Have No Pagination or Limit

Status: Done
Depends On: None
Category: Improvement

## Description

Found during live dashboard/UX review (2026-09-27), while answering "how many chats/documents
does the UI show — is there a limit?": there isn't one, anywhere in the stack.

- `app/generation/repository.py`'s `list_conversations_for_owner` returns **every** conversation
  the caller owns, newest first, no `LIMIT`.
- `app/ingestion/repository.py`'s `list_documents_for_owner` returns **every** document the
  caller owns, newest first, no `LIMIT`.
- Neither `Sidebar.tsx` (conversations) nor `DocumentsPage.tsx` (documents) truncates or
  paginates client-side either — both render the full list they're given.

At current low/sporadic traffic this is harmless, but it's unbounded growth with no ceiling:
`GET /conversations` and `GET /documents` payload size, and the corresponding sidebar/page
render cost, both scale linearly with how long an account has been in use, with nothing capping
either side.

## Acceptance Criteria

- [ ] Decide the approach: server-side pagination (cursor or offset-based) vs. a simple fixed
      cap with a "show more" affordance vs. a hard limit with no further access to older items.
      A cap-with-"show more" is likely the simplest change consistent with this project's
      "don't over-engineer" guidance, unless there's a reason a real cursor-paginated API is
      needed.
- [ ] `GET /conversations` and `GET /documents` (or whichever shape is chosen) bounded, not
      unbounded.
- [ ] Frontend updated to request/display accordingly (e.g. a "load more" button, or simple
      truncation with a count).
- [ ] Existing callers/tests updated for the new response shape without breaking them.

## Notes

Low urgency at current traffic scale — filed so it's tracked before it becomes a real problem,
not because it's causing one today.

## Resolution (2026-09-27)

Chose a cap-with-"show more" affordance over real cursor pagination, per the ticket's own
steer: `GET /conversations` and `GET /documents` both gained `limit` (default 50, bounded
1-200) and `offset` query params, and their repository functions
(`list_conversations_for_owner`, `list_documents_for_owner`) now take matching `limit`/`offset`
params (defaulted generously at the repository layer so every pre-existing bare call site kept
working unmodified). The service layer (`list_conversations`, `list_documents`) fetches
`limit + 1` rows and trims back to `limit` to derive a `has_more: bool` on both response
schemas, without a separate `COUNT` query.

Frontend: `ChatPage.tsx`'s sidebar conversation list and `DocumentsPage.tsx`'s document list
each gained "Load more" — a `hasMore`/`isLoadingMore` state pair and a handler that requests
the next page (`offset` = current list length) and appends the result, rather than replacing
it. `Sidebar.tsx` gained the matching props to render the button. `ChatPage.tsx`'s separate
document-scoping checklist (for chat's document-scope checkboxes, distinct from the Documents
page) was left un-paginated -- it's a secondary consumer of the same bounded endpoint, not a
scrolling list UI, so a generous single page suffices there.

**Verified**: backend -- new repository-level pagination tests (`tests/generation/
test_repository.py`, `tests/ingestion/test_repository.py`), service-level `has_more` tests
(`tests/generation/test_service.py`), and a real multi-document router-level pagination test
(`tests/ingestion/test_router.py`, two real PDF ingestions through the full pipeline). Two
pre-existing exact-dict-equality assertions (`{"conversations": []}`, `{"documents": []}`)
were updated for the new `has_more` field. Frontend -- two new vitest tests (`ChatPage.test.tsx`,
`DocumentsPage.test.tsx`) confirming "Load more" appears when `has_more` is true and correctly
appends the next page. Full backend suite 599 passed, frontend suite 95 passed (was 93),
`tsc -b`/`oxlint`/`vite build` all clean.

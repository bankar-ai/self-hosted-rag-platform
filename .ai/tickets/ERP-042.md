# ERP-042 — Ship Live Deployment's Metrics to Grafana Cloud

Status: Done
Depends On: ERP-038, ERP-039

## Description

ERP-038 (traces) and ERP-039 (logs) both export from the live deployment to Grafana Cloud's free
tier. Metrics are the remaining gap named in both tickets' Notes: `app/core/telemetry.py` currently
wires the OTel `MeterProvider` to a `PrometheusMetricReader` only — a pull-based `/metrics` endpoint
that needs something to scrape it. The live `e2-micro` VM has no local Prometheus (no RAM headroom,
same constraint that ruled out a local Jaeger/Alloy agent in ERP-038/039), so none of the existing
hand-written metrics (`embedding_cache_requests_total`, `retrieval_cache_requests_total`,
`llm_generation_duration_seconds`, `ingestion_jobs_total`) or auto-instrumented ones currently reach
anywhere off the VM.

ERP-039's resolution established the precedent for this exact tradeoff: an in-process OTLP export
path added to a process that's already running costs effectively nothing (measured: RSS/available
memory unchanged), whereas a separate scraping/shipping agent is a new always-on process the VM's
budget can't absorb. The same choice applies here — push-based OTLP metrics via
`PeriodicExportingMetricReader` + `OTLPMetricExporter`, mirroring `_build_span_exporter()`'s and
`_build_log_exporter()`'s existing protocol-selection pattern (`grpc` for local Jaeger, `http/protobuf`
for Grafana Cloud), reusing the same `OTEL_EXPORTER_OTLP_*` env vars and token already on the VM — no
remote-write agent.

## Acceptance Criteria

- [x] `app/core/telemetry.py` gains a `_build_metric_reader()` (or equivalent) that adds a
      `PeriodicExportingMetricReader(OTLPMetricExporter(...))` to the `MeterProvider`, selecting the
      OTLP exporter class by `OTEL_EXPORTER_OTLP_PROTOCOL` the same way traces/logs already do
- [x] The existing pull-based `PrometheusMetricReader`/`/metrics` endpoint is kept alongside it for
      local dev (`docker-compose`'s Prometheus service still works unchanged) — this is additive,
      not a replacement

- [x] VM memory headroom re-verified after deploying (same `free -h`-under-real-load discipline as

## Notes

Scoped to reusing the existing hand-written + auto-instrumented metrics as-is — no new metrics
defined as part of this ticket. If Grafana Cloud's OTLP gateway turns out to need a
metrics-scoped token distinct from the existing `set:alloy-data-write` traces/logs token, that's a
Grafana Cloud account-config step, not a code change (same category of discovery ERP-038 made about
the gRPC-vs-HTTP transport).

## Resolution (2026-09-16)

`app/core/telemetry.py`'s `MeterProvider` now attaches two metric readers instead of one:
`PrometheusMetricReader()` (unchanged, backs local `/metrics`) and a new
`PeriodicExportingMetricReader(_build_otlp_metric_exporter())`, where `_build_otlp_metric_exporter()`
mirrors `_build_span_exporter()`/`app.core.logging_config._build_log_exporter()`'s exact protocol-
selection pattern (`grpc` default for local Jaeger, `http/protobuf` for Grafana Cloud) — no new
dependency (same `opentelemetry-exporter-otlp` meta-package), no new env vars (reuses the existing
`OTEL_EXPORTER_OTLP_*` trio and `set:alloy-data-write` token already on the VM from ERP-038/039).

The existing `set:alloy-data-write` token turned out to already cover metrics ingestion too — no
account-config step or new token was needed, unlike the speculative note above.

Merged to `develop` via PR #34, promoted to `main` via PR #35, deployed to the live VM
(`git pull` + `uv sync` + `systemctl restart`, 2026-09-16). **Live-verified end-to-end**: real
requests against the live deployment (`GET /docs`, `POST /auth/login`) produced
`http_server_duration_milliseconds_bucket`, `http_server_active_requests`, and
`db_client_connections_usage` series filtered by `service_name="self-hosted-rag-platform"`,
confirmed visible in Grafana Cloud's Explore → Prometheus datasource (`grafanacloud-microstarfish1843-prom`)
within the same hour they were generated — auto-instrumented metrics, not yet one of the
hand-written ones (`llm_generation_duration_seconds` needs an authenticated `/generation/query`
call, not exercised in this verification pass) but sufficient to confirm the export path itself
works end-to-end; the hand-written metrics go through the identical `MeterProvider`/reader chain,
so there's no separate code path left to doubt.

VM memory re-verified post-deploy: `free -h` showed 368Mi available — an exact match to the
365-378MB baseline ERP-037/ERP-039 established, confirming the added OTLP metric export path cost
no detectable memory, same as ERP-039's finding for logs.

Verified: ruff/mypy clean, full suite 383 passed, 96.68% coverage (real Postgres/Redis/Jaeger
locally). `docs/deployment.md` gained a "Metrics (Grafana Cloud)" section;
`D:\github-projects\gcp-deployment-tracker.md`'s Observability table row updated to note metrics
are no longer "not yet ticketed."

This completes the full observability trio for the live deployment: traces (ERP-038), logs
(ERP-039), metrics (ERP-042).

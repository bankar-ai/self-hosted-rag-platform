# ERP-076 — Per-Document Parsing-Confidence Indicator

Status: Done
Depends On: None
Category: Improvement

## Description

A caller currently has no way to tell whether a poorly-answered query is due to retrieval/
generation weakness or because the source document itself parsed badly (e.g. a scanned, blurry,
non-English form that needed the Docling OCR fallback). This ticket surfaces one consolidated,
document-level confidence label — not per-page detail — so a caller can see at a glance that a
given document is unreliable to query against.

Docling's own `ConfidenceReport` (`mean_grade`/`low_grade`: `poor`/`fair`/`good`/`excellent`)
already provides exactly this as a document-level aggregate. The quality-fallback parse runs on
the separate Cloud Run `docling-service` (ERP-047), not in-process, so the grade has to be
captured there and carried back through `call_docling_service` — not computed locally.

Documents that never needed the Docling fallback (the PyMuPDF4LLM fast path handled them cleanly)
have no Docling confidence report at all; they default to a `high` label rather than triggering an
extra Docling call purely to score them (would cost real parse time/memory for no reliability
benefit on documents that already parsed cleanly).

## Acceptance Criteria

- [ ] Cloud Run `docling-service`'s `/parse` response gains the document-level confidence grade
      (`poor`/`fair`/`good`/`excellent`) from Docling's own `ConfidenceReport`
- [ ] `app/ingestion/parsers.py`'s `parse_quality`/`call_docling_service` carry that grade through
      to `run_ingestion_job`
- [ ] New `parsing_confidence` column on `documents` (Alembic migration), persisted once per
      document at the end of ingestion; documents that only used the fast path default to `high`
- [ ] Documents API exposes `parsing_confidence`; the Documents/sidebar document list renders it
      as a badge next to each filename

## Notes

Touches two deployables (main app + the `self-hosted-rag-platform-docling` Cloud Run service) —
needs its own Cloud Run redeploy step, not just the VM's `git pull` + `systemctl restart`.
No new dependency (Docling's confidence scoring is part of the existing `docling` package).

## Resolution (2026-09-20, deployed and live-verified — with a real incident along the way)

Deployed to the VM 2026-09-20, but the Cloud Run `docling-service` redeploy this ticket's own
Notes called out as required was **initially missed** — the VM/main-app deploy shipped without
it. Live-verified by the user uploading two real scanned Marathi land-record PDFs (needing the
OCR fallback), both of which failed ingestion with `TypeError: list indices must be integers or
slices, not str`. Root cause: the main app's `call_docling_service` was updated (this ticket) to
expect the Cloud Run service's `/parse` response as `{"pages": [...], "confidence": "..."}", but
the Cloud Run service itself was still running its *old* code returning a bare `list[dict]` —
`result["pages"]` on a list raised exactly that error. Fixed by actually running the Cloud Run
redeploy (`gcloud run deploy self-hosted-rag-platform-docling --source deploy/cloud_run_docling
...`, new revision `-00003`, confirmed serving 100% of traffic) — no code change needed, the fix
was purely deploying code that already existed in the repo. Re-verified by the user retrying the
same two failed uploads.

**Lesson for future tickets that touch multiple deployables**: a ticket's own "Notes" section
calling out a second deploy step is not a substitute for actually checking off that step during
deployment — this one specifically warned about the Cloud Run redeploy and it still got missed
on the first pass.

# ERP-114 — Reduce embedding cold-start frequency on Modal post-ERP-106

Status: Done
Depends On: None
Category: Improvement

## Description

Live trace investigation (2026-09-28, same real request as `ERP-113`) found `embedding.generate`
alone took ~39.8s of an 81.5s total request — a Modal cold start. This is a direct, predicted
side effect of `ERP-106`: before that ticket, the shared Modal Ollama app served both generation
and embedding traffic, so embedding calls benefited from generation traffic keeping the container
warm. Since generation moved to OpenRouter, that Modal app now serves embedding-only traffic,
making it more likely to go idle past its `scaledown_window` and cold-start on the next request.
This is also the accurate explanation for the frontend's "waking up the model" UI message still
appearing — it's correctly describing real behavior (the embedding step), not stale copy.

Full 24/7 always-warm (`min_containers=1`) was evaluated and rejected: Modal's T4 costs ~$0.59/hr,
and the $30/mo free credit covers only ~27 hours of continuous uptime — would exhaust the free
tier in about a day and risk re-triggering the exact "workspace disabled" billing incident from
`ERP-037`'s history. Chosen middle ground: increase `scaledown_window` (currently 300s/5min) so
the container stays warm longer after the last real request, reducing repeat cold-starts during
an active session (a user asking follow-up questions minutes apart) without paying for true 24/7
uptime.

- [x] Live-verified: redeploy succeeded (same endpoint URL, no app-side changes needed), a real

      deploy always cold-starts once regardless of `scaledown_window`, which only governs
      behavior after the first warm-up, not the deploy itself)
- [x] `D:\github-projects\gcp-deployment-tracker.md`'s Modal entry updated with the new value and
      why

## Progress (2026-09-28) — closed out

## Notes

If 900s still isn't enough at real usage patterns, the next lever is the same trade-off curve
(longer window = more idle GPU-seconds billed = more of the $30/mo credit consumed for standby
time, not real work) — revisit with actual usage data rather than guessing further increases.
`min_containers=1` remains explicitly rejected per the cost analysis above unless the project's
free-tier constraint itself changes.

# ERP-059 — Live-Verify Scanned/Image-Based PDF (OCR) End-to-End

Status: Done
Depends On: None
Category: Improvement — verification, not a code change; closes a real gap between "designed to
work" and "proven to work"

## Description

Confirmed the pipeline is architecturally wired for scanned/image-based PDFs:
`app/ingestion/parsers.py`'s `needs_fallback` routes any page with too little extractable text to
the Cloud Run `docling` service, which has `rapidocr` (docling's OCR backend) baked into its
Docker image at build time (per ERP-047).

However, ERP-047's own live verification (2026-09-17) used a PDF containing a **table**, not a
scanned/image-only document — the only test against a genuinely scanned page is a local unit
fixture (a blank white image), which only proves the routing decision fires, not that OCR
actually extracts usable, correct text end-to-end against the live deployment.

## Acceptance Criteria

- [x] A real scanned document (rendered text on an image with no embedded text layer, forcing
      genuine OCR — confirmed the fast path extracts zero text from it before uploading) uploaded
      through the live deployment.
- [x] Confirmed the OCR path was actually exercised: the job result's `parser_used` field was
      `"quality"`, not `"fast"`.
- [x] The resulting ingested chunk contains correct, readable text matching the source image
      exactly (not garbled OCR output) — verified via a real generation query against it.
- [x] VM memory and timing recorded, same discipline as ERP-047/051.
- [x] Result recorded in `docs/deployment.md`.

## Resolution (2026-09-18)

Live-verified end-to-end against the actual deployment: a real image-based PDF (rendered text
"The archive password for this test is walnut88.", no text layer) was uploaded; the job result
showed `parser_used: "quality"`, confirming the Cloud Run `docling` OCR fallback actually ran
(not silently routed to the fast path). The extracted chunk text was **byte-for-byte correct**
against the source image — genuine, accurate OCR, not garbled output. A follow-up generation
query ("What is the archive password?") correctly answered "walnut88" with the right citation,
proving the OCR-extracted content is fully usable downstream, not just present in storage.

Timing: ~2 minutes end to end (Cloud Run cold start included), comfortably within the 480s
client-side / 600s Cloud-Run-side timeout budgets. VM memory was completely flat throughout
(~388-397MB used, matching the pre-test baseline exactly) — confirming the OCR workload never
touches the VM's own tight memory budget, exactly as ERP-047's Cloud Run offload was designed to
guarantee.

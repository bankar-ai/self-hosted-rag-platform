# ERP-052 — Determine and Document Real Concurrent-Upload Capacity

Status: Done (5 concurrent verified; higher not yet tested)
Depends On: None
Category: Improvement — no concurrency ceiling for simultaneous PDF ingestion has ever been
measured; the only prior concurrency test (ERP-037) covered auth+chat, not ingestion

## Description

The user wants an honest, tested answer to "how many users can upload PDFs at the same time,"
even if the answer is a modest number — a *tested* 5 is worth more than an *assumed* 20. The
live architecture has several plausible bottlenecks, none previously measured together under a
real concurrent-ingestion burst:

- The `e2-micro` VM (2 vCPU, 958MB RAM) runs each ingestion job's fast-path parse as a
  background thread — concurrent jobs contend for the same CPU/RAM.
- `app/core/db.py`'s SQLAlchemy engine uses default pool sizing (5 + 10 overflow = 15
  connections); Neon's free-tier connection ceiling is a further unknown on top.
- Modal-hosted Ollama (embeddings) was observed in ERP-037 to spin up a **separate cold
  container per concurrent request** rather than queuing behind a warm one.
- Cloud Run's `docling` fallback is `concurrency=1`, `max-instances=3`.

## Acceptance Criteria

- [x] A real concurrent-upload test run against the live deployment, stepping up (3, then 5) —
      real PDFs (distinct content per file), from distinct real registered users, not synthetic
      no-op requests.
- [x] VM memory observed during each step via `gcloud compute ssh` + `free -h`.
- [x] The highest concurrency level tested that completed with no failures and no VM distress
      identified and recorded as the documented, promised number: **5**.
- [x] Result written up in `docs/deployment.md`.

## Resolution (2026-09-18)

Live-verified against the actual deployment: 3 concurrent uploads (3 distinct users) completed
within ~10 seconds; 5 concurrent uploads (5 distinct users) completed within ~20 seconds — both
with zero failures. Notably, both tests ran **while an unrelated pathological large-upload job
(ERP-051) was also still processing in the background**, meaning this result holds even under
additional competing load, not just in a clean-slate scenario. VM memory recovered to baseline
immediately after each round; the service never became unresponsive.

Higher concurrency (10+) was deliberately not tested in this pass — pushing further risked
compounding real production risk on a single-instance, previously-crashed (`ERP-047`) `e2-micro`
VM, especially while another heavy job was already running. **5 concurrent uploads is the
tested, promised number** as of this writing, recorded in `docs/deployment.md`. No concrete
bottleneck (DB pool exhaustion, Modal cold-start pile-up) was actually observed at this
concurrency level, so no follow-on fix ticket was needed — a future pass to find the actual
ceiling above 5, under cleaner conditions, is a reasonable next step but not opened as a ticket
here since there's no known problem driving it yet.

## Notes

This is a measurement ticket — it may produce follow-on fixes (e.g. raising the DB pool size)
but should not silently bundle them in; record what broke, ticket it separately if it's a real
gap worth closing. Nothing broke at the tested level.

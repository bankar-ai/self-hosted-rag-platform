# ERP-095 — Upload/Document Status Not Synced Across Devices

Status: In Progress
Depends On: None
Category: Bug

## Description

Live feedback (2026-09-24, screenshots): the same account logged in on a laptop and a phone
showed different upload/processing status for the same document at the same time.

Root cause found (code investigation, not yet live-verified): `frontend/src/lib/documentsStore.ts`
tracks in-progress upload status (`pending`/`processing`/`failed`) in `localStorage`, scoped per
browser (`rag-recent-documents:${userId}`). Only the *finished* document list
(`GET /documents`) is fetched from the server and therefore synced across devices — "in
progress" status is purely local to whichever browser initiated (and is actively polling) that
specific upload. A second device has no visibility into a job it didn't start itself.

## Options

- **Server-authoritative status**: have the frontend poll `GET /ingestion/jobs` (or a similar
  "my active jobs" endpoint, doesn't currently exist) instead of relying on locally-remembered
  job IDs, so any device can see the true in-progress state for the account, not just the one
  that started the upload.
- **Document it as expected behavior**: if this is acceptable (uploads are usually a
  single-session action), just make the UI clearer that "in progress" reflects "started from
  this device," not global account state.

## Acceptance Criteria

- [x] Decide which option to pursue — server-authoritative (see Decision below)
- [x] If server-authoritative: new/extended endpoint to list the caller's active jobs, frontend
      polls it instead of (or in addition to) local state
- [ ] Live-verify with two real devices/browsers logged into the same account

## Decision (2026-09-24)

Went with **server-authoritative status**, not documenting-as-expected: the in-memory job
tracker (`app/ingestion/jobs.py`) already has everything needed (`owner_id`, `status`,
`filename`, `error`) to answer "what's this account's active jobs" account-wide — it just
wasn't exposed. Not adding new fields or a new job field (`job_id` is already unique per job),
so this is a purely additive, low-risk change.

### Implementation

- `app/ingestion/jobs.py`: `list_active_jobs(owner_id)` returns the owner's PENDING/PROCESSING/
  FAILED jobs as `(job_id, record)` pairs. DONE is excluded — a finished job's result already
  lives on `GET /documents`.
- `app/ingestion/schemas.py`: `JobSummary`/`JobListResponse`.
- `app/ingestion/router.py`: `GET /ingestion/jobs` — the caller's active jobs, account-wide
  (distinct from the existing per-ID `GET /ingestion/jobs/{job_id}`).
- `frontend/src/pages/DocumentsPage.tsx`: on mount, hydrates `inProgress` from
  `GET /ingestion/jobs` (in addition to the existing localStorage-seeded state), and starts a
  `pollJob` loop for any pending/processing job discovered this way. A `pollingJobIdsRef` set
  (new) guards against double-polling a job this same device already started and is already
  polling.

### Testing

- Backend: `tests/ingestion/test_jobs.py` (`list_active_jobs` scoping/status filtering),
  `tests/ingestion/test_router.py` (`GET /ingestion/jobs` — empty, pending job visible without
  this session having called `POST /ingestion/pdf` itself, excludes done, includes failed with
  error, scoped to owner). Full suite green.
- Frontend: `DocumentsPage.test.tsx` — new test simulates a job with no localStorage entry
  becoming visible purely via the server list. Full `vitest run` suite green (76 tests), `tsc -b`
  and `oxlint` clean.
- **Not done**: the live two-device verification this ticket's AC calls for — no second
  device/browser available in this session. Recommend a quick manual check (upload from one
  browser, confirm it appears mid-upload in another logged into the same account) before
  considering this fully closed.

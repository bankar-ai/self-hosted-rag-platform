# ERP-094 — Cap on Number of Documents per Multi-File Upload

Status: Done
Depends On: None
Category: Improvement

## Description

Live feedback (2026-09-24): `DocumentsPage.tsx`'s upload control (`multiple` file input,
`DocumentsPage.tsx:298`) currently has no limit on how many files can be selected/queued in one
multi-file upload — only a per-file size label ("Maximum file size: 20 MB per PDF"). An
unbounded batch could overwhelm the ingestion pipeline (each file becomes its own job; a large
batch could also stack up multiple docling Cloud Run cold-starts/OOM-risk documents at once,
compounding ERP-086/ERP-091's latency and cost concerns) or just be a bad UX (no feedback if
someone selects 200 files at once).

## Decision (2026-09-24)

Cap: **5 files**, chosen via infra analysis rather than a live load test against production
(which risked triggering another OOM incident like ERP-047): the Cloud Run docling service caps
at `max-instances=3`/`concurrency=1`, and the VM has only ~370MB of typical free memory
headroom, while the frontend already fires a batch's uploads fully concurrently
(`Promise.all`). Adjustable later once ERP-090's uptime/performance dashboard gives real usage
data. Enforced both client-side (immediate feedback) and server-side (so it can't be bypassed by
a direct API call, e.g. from multiple browser tabs).

## Acceptance Criteria

- [x] Cap value decided (5)
- [x] Frontend: selecting more than the cap shows a clear message and does not start any
      uploads until the selection is within the cap (full reject, not partial accept)
- [x] Backend: the relevant ingestion endpoint(s) reject a batch over the cap with a clear error
- [x] Test coverage for both the client-side rejection and the server-side rejection

## Built (2026-09-24)

- **Backend**: `IngestionSettings.max_active_jobs_per_user` (default 5). `app/ingestion/jobs.py`
  gained `try_create_job(owner_id, pdf_path, filename, max_active)`, which atomically
  check-and-creates under one lock acquisition (not a separate count-then-create, which would
  race under concurrent requests from the same owner) — counts only that owner's currently
  PENDING/PROCESSING jobs, so a completed job frees capacity. `POST /ingestion/pdf` now rejects
  with `429` (cleaning up the already-written temp file first) when the caller is at the cap.
- **Frontend**: `MAX_FILES_PER_UPLOAD = 5` in `DocumentsPage.tsx`, checked in `stageFiles`
  before the existing per-file-size loop — a combined (already-staged + newly-selected) count
  over the cap rejects the entire new selection with a dedicated message, separate from the
  existing "file too large" message.
- Built via `superpowers:subagent-driven-development` (2 tasks, both task-reviewed and
  Approved, no fix rounds needed). Full backend suite (537 passed) and frontend suite (69
  passed at the time) clean.

## Notes

Deferred, non-blocking follow-ups noted during review: `count_active_jobs`/`try_create_job`
duplicate the same counting predicate (DRY nit, inherited from the plan's own suggested code);
no explicit test for the exact-cap boundary (5 accepted, only 6-rejected was tested); a stale
"file too large" message can coexist on screen with a new "too many files" message in one edge
case. None block functionality.

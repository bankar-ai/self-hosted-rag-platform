# ERP-083 — Retrieval/Generation Evaluation Gate in CI (Dedicated Modal Endpoint)

Status: Done
Depends On: None
Category: Improvement

## Description

ERP-029/ERP-030 built a retrieval-quality (Precision@k/Recall@k/MRR) and generation-quality
(faithfulness/relevancy/context-precision) evaluation harness against a hand-authored golden
dataset, but it is only ever run manually — CI has no Ollama available, and both evaluation
runners require a real embedding/LLM backend (no fake/mocked path in the actual runners, only in
the harness's own unit tests).

**Decision (researched and confirmed 2026-09-19, see session notes)**: reuse the existing,
already-proven `deploy/modal_ollama.py` pattern rather than building new GCP infrastructure.
GCP's `e2-micro` VM cannot run Ollama at all (958MB RAM — the same reason Ollama and Docling were
both moved off it already), and a GCP Cloud Run alternative would mean building an entirely new
deployment for slower CPU-only inference, for no clear cost advantage. Modal's per-second billing
makes a handful of golden-dataset queries cost a few cents per run, well within its $30/mo free
credit once a payment method is attached.

**Do not point this at the existing production Modal endpoint.** That endpoint already had a real
incident (2026-09-17): it was disabled in production after crossing the $1-usable-without-a-
payment-method threshold (see `gcp-deployment-tracker.md`). A second, separate Modal app isolates
CI's usage/quota/failure blast radius from production entirely.

Also run on a **schedule** (e.g. nightly, or on `develop` merges), not as a per-PR gate — avoids
adding GPU cold-start latency to every PR and keeps usage minimal, while still catching quality
regressions promptly.

## Acceptance Criteria

- [ ] A second Modal app (e.g. `self-hosted-rag-platform-ollama-ci`), cloned from
      `deploy/modal_ollama.py`, deployed and dedicated to CI/evaluation use only
- [ ] A payment method is attached to the Modal account (avoids repeating the 2026-09-17
      workspace-disabled incident) and a budget alert is set
- [ ] A new scheduled CI workflow (not gating every PR) runs both evaluation harnesses
      (`app.evaluation.run`, `app.evaluation.generation_run`) against the CI-dedicated Modal
      endpoint
- [ ] A baseline threshold is established from the existing verified baseline (Precision@3=0.333,
      Recall@3=1.0, MRR=1.0 per ERP-029/ERP-041) and the run fails/alerts if scores drop below it
- [ ] Documented: how to check the scheduled run's results, and the teardown step for the CI
      Modal app added to `gcp-deployment-tracker.md`'s teardown list

## Resolution (2026-09-19, code complete)

Everything expressible as code is done: `deploy/modal_ollama_ci.py` (a deliberate clone of
`deploy/modal_ollama.py`, its own separate Modal app `self-hosted-rag-platform-ollama-ci`, not
shared/parameterized with production — see its docstring for why); `app/evaluation/run.py` and
`app/evaluation/generation_run.py` both gained `--fail-under-*` flags (new `check_thresholds`
in each, unit-tested in `tests/evaluation/test_run_cli.py`/`test_generation_run_cli.py`) that
exit 1 when a metric drops below its threshold — omitted, every existing manual invocation is
byte-for-byte unchanged; `.github/workflows/evaluation-gate.yml` runs both gates on a daily
schedule (+ `workflow_dispatch`) against `secrets.CI_MODAL_OLLAMA_URL`, using `--judge ollama`
for generation (not the `ragas` default — ERP-030 found it hangs 10+ min against local Ollama in
practice), and fails fast with a clear error if that secret isn't set yet rather than silently
no-op'ing.

**Deliberately not done by this session** (each is a live, billable, or credential-touching
action outside what an agent session does unprompted — see the "CI evaluation gate" section
added to `D:\github-projects\gcp-deployment-tracker.md` for the exact steps):
1. `uv run modal deploy deploy/modal_ollama_ci.py` — creates real paid cloud infrastructure.
2. Adding a payment method to the Modal account — avoids repeating the 2026-09-17
   workspace-disabled incident that hit the *production* endpoint at the $1-free-credit wall.
3. Adding the deployed endpoint's URL as the `CI_MODAL_OLLAMA_URL` GitHub Actions repo secret.

Verified: ruff/mypy clean, full suite 528 passed (up from 520). The workflow YAML and the new
CLI flags are otherwise ready to go the moment those three manual steps are done.

## Resolution (2026-09-20, fully deployed and verified)

All three remaining manual steps completed by the user, then the gate itself run twice against
real production infrastructure:

1. Payment method attached to the Modal account.
2. `deploy/modal_ollama_ci.py` deployed (`uv run modal deploy`, run from the worktree since the
   user's first attempt ran from a checkout that didn't have the file yet — PR not merged at
   that point). Live endpoint confirmed reachable (`200` on a direct request) before wiring it
   in. Windows-specific gotcha hit and worked around: the Modal CLI's own progress-indicator
   Unicode characters crashed with a `charmap codec can't encode` error on Windows' default
   terminal encoding — fixed by setting `PYTHONUTF8=1 PYTHONIOENCODING=utf-8` for the deploy
   command.
3. Endpoint URL added as the `CI_MODAL_OLLAMA_URL` GitHub Actions repo secret (`gh secret set`).

**First real run failed** (`workflow_dispatch`, run 35500818386): retrieval-quality gate passed
cleanly, an exact match to the ERP-029/041 baseline (Precision@3=0.333, Recall@3=1.0, MRR=1.0) —
but generation-quality crashed with `ollama._types.ResponseError: model 'qwen3' not found`.
Root cause: `GenerationSettings.model` defaults to `"qwen3"` in code, but the CI Modal image
only bakes in `gemma3:4b` + `nomic-embed-text` (matching production) — the workflow never
overrode `GENERATION_MODEL`. Fixed by adding `GENERATION_MODEL: gemma3:4b` to the workflow's
env block (PR #54, targeted directly at `main` since it's CI-config-only, no application code —
same reasoning as the `develop`→`main` promotion overhead not being worth it for a one-line fix).
**Second run passed both gates** (run 35501172737, `conclusion: success`).

Also, per user decision (2026-09-20): the daily `schedule:` trigger was dropped before any of
this — manual-only (`workflow_dispatch`) for now, to avoid paying for a live-LLM evaluation every
day when nothing's changed (PR #52). A schedule (weekly was the leading candidate) can be added
back once there's a sense of actual needed frequency.

ERP-083 is now fully closed: code, deployment, and a real passing run, all done.

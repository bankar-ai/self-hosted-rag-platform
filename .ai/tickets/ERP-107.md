# ERP-107 — Persist Retrieval Settings Per Turn (rerank/expand_sections/document scope)

Status: Done
Depends On: None
Category: Improvement

## Description

Split off from ERP-104 (2026-09-27): while adding source-document capture to
`production_sample_scores`, confirmed that `rerank`/`expand_sections`/`document_ids` (the
retrieval settings a generation call actually used) are **not persisted anywhere** — they exist
only as transient request parameters on `GenerationQuery`, never written to
`conversation_messages` or any other table. There's no way today to know, after the fact, which
settings produced a given historical answer.

Unlike ERP-104's source-document capture (free, read-only, zero schema change), this requires
adding a new column to `conversation_messages` (or a side table) and writing to it on the live
generation hot path (`app/generation/service.py`'s `generate`/`generate_stream`) — a materially
bigger and riskier change, deliberately not bundled into ERP-104 under time pressure.

## Acceptance Criteria

- [ ] Decide storage shape: a new JSONB column on `conversation_messages` (mirroring the
      `citations` column's pattern) vs. a separate table. A column is likely simpler unless
      there's a reason to query it independently of the message.
- [ ] `generate`/`generate_stream` persist the retrieval settings actually used (`rerank`,
      `expand_sections`, the resolved document scope) alongside the existing citations, in the
      same transaction — no separate write, no added request latency.
- [ ] `ProductionSampleScoreRecord`/`run_production_sampling` (ERP-097/104) can then surface
      these per sample, completing the original ERP-104 ask.
- [ ] No behavior change to the generation response itself — purely additive persistence.
- [ ] Verify: a real generation call with non-default settings (e.g. `rerank=True`) round-trips
      correctly through a fresh read of the persisted message.

## Notes

Low urgency — nothing is broken today, this only limits diagnosing *why* a specific historical
answer scored low (e.g. the ERP-097 finding that unscoped multi-document retrieval picked the
wrong PDF). Worth doing before this becomes a recurring diagnostic gap, not urgently.

## Resolution (2026-09-27)

Chose a JSONB column (`conversation_messages.retrieval_settings`) mirroring the existing
`citations` column's exact pattern, over a separate table -- nothing needs to query retrieval
settings independently of the message they belong to. New Alembic migration
`77b31e276298` (autogenerated, empty-diff-confirmed via `alembic check` after applying);
`ConversationMessageRecord` gained the column directly, matching how `citations` was added.

`app/generation/service.py`'s new `_retrieval_settings_dict(rerank, expand_sections,
document_ids)` builds `{"rerank": ..., "expand_sections": ..., "document_ids": ...}` from
exactly the request parameters `generate`/`generate_stream` were called with (the caller's ask,
not a resolved/expanded document set) -- passed to `append_message`'s new `retrieval_settings`
param at both stateful write sites (`generate`'s write-session block, and
`_run_stateful_generation`), in the same transaction as citations, no separate write. The two
stateless paths persist nothing (as before), and a "user"-role message never gets settings of
its own (nothing to retrieve for a question). Exposed on `Message` (API responses) and copied
straight through in `production_sampling.py`'s `ProductionSampleResult`/
`ProductionSampleScoreRecord` (new `retrieval_settings` column there too, via the same
migration) -- completing the original ERP-104 ask this ticket was split off from. Generation
response contract itself is unchanged (purely additive persistence).

**Verified**: `tests/generation/test_service.py`'s new round-trip test calls `generate()` with
`rerank=True, expand_sections=True, document_ids=[...]`, then re-reads the conversation via
`get_conversation_history` and confirms the assistant message's `retrieval_settings` matches
exactly what was requested (and the user message's stays `None`). A new
`tests/evaluation/test_production_sampling.py` test confirms a sampled message's
`retrieval_settings` is copied through unchanged into `ProductionSampleScoreRecord`. Alembic
migration applied and re-checked empty-diff. Full backend suite 599 passed (up from the
578 baseline before this session's four tickets), ruff/mypy clean.

# ERP-045 — Answer Feedback (Thumbs Up/Down)

Status: Done
Depends On: ERP-043
Category: Improvement — new capability (feedback collection), not a defect in existing behavior

## Description

Surfaced during ERP-043's live UI review: there's no way for a user to signal whether a
generated answer was good or bad. Not implemented yet since it needs its own design pass before
it's buildable — open questions below aren't decided.

## Acceptance Criteria

- [x] Scoped (resolving the prior open questions): binary thumbs up/down, no comment field for
      v1; stored per-message (not per-conversation) in a new table; not wired into the ERP-030
      evaluation harness yet (worth a follow-up, not blocking this) and no admin view yet.
- [x] A user can rate an assistant message up or down, and change or clear their rating.
- [x] Rating one message doesn't require any other message's rating to change.
- [x] Feedback is visible/settable both right after a message streams in and after reloading a
      past conversation's history — which meant message IDs needed to reach the frontend in the
      first place, which they didn't before this ticket.

## Resolution (2026-09-18)

New `message_feedback` table (`app/generation/models.py`'s `MessageFeedbackRecord`, migration,
one row per `message_id`, `rating` is `"up"` or `"down"`) — a viewer can only ever rate their own
messages since access is scoped through the owning conversation, not a bare message ID.
`app/generation/repository.py` gained `set_message_feedback`/`clear_message_feedback` (both
verify the message belongs to a conversation owned by the caller before touching anything) and
`get_feedback_for_messages` (batched, not N+1). New endpoints:
`PUT`/`DELETE /conversations/{conversation_id}/messages/{message_id}/feedback`.

This surfaced a real prerequisite gap: neither `GenerationResponse` nor the SSE `done` event nor
`ConversationHistoryResponse`'s `Message` exposed a message's ID at all, so the frontend had
nothing to attach feedback to. Fixed by having `generate()`/`generate_stream()` capture and
return the persisted assistant message's ID (`GenerationResponse.assistant_message_id`, and a new
`assistant_message_id` field on the streaming `done` event payload — both `None` for a stateless
request, since nothing is persisted there), and `Message` gaining `id`/`feedback` fields so
history reload restores prior ratings too.

Frontend: thumbs up/down buttons under each assistant message once its ID is known (immediately
after streaming, or on history reload); clicking the active rating again clears it (`DELETE`),
clicking the other one switches it (`PUT`).

Verified: ruff/mypy clean, new repository/router tests (set, switch, clear, wrong-owner 404,
unknown-message 404); full backend suite passing. Frontend `tsc --noEmit`/`oxlint` clean, full
suite passing. Live-verified against the real local stack (real Postgres/Redis/Ollama): rated a
real answer up, then down, then cleared it, confirming the full round trip through a fresh
history reload each time -- not deployed/live-verified against the production environment yet
as of this writing.

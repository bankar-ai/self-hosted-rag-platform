# ERP-086 — Docling Cloud Run Service OOM-Kills on Large/Complex Scans

Status: In Progress
Depends On: None
Category: Bug

## Description

A user-reported 503 on `POST /ingestion/pdf` (live app, 2026-09-22) was investigated via
`superpowers:systematic-debugging` against real GCP Cloud Logging for the
`self-hosted-rag-platform-docling` Cloud Run service (project `self-hosted-rag-platform`,
region `us-central1`). Root cause confirmed directly from the logs, not inferred:

```
ERROR: The request failed because either the HTTP response was malformed or connection to the
instance had an error. [503]

While handling this request, the container instance was found to be using too much memory and
was terminated.
```

The failing document (`Group-C-Pre-Test-02-Set-A-30-08-2026-F.PDF`, a scanned multi-page exam
paper) pushed the docling OCR pipeline (RapidOCR + layout/table models, see
`deploy/cloud_run_docling/main.py`) past the container's `--memory 4Gi` limit. Cloud Run's
infra killed the container mid-request — surfaced to the client as a raw 503 with a low-level
Mozilla-docs error message (`app/ingestion/cloud_run_client.py`'s `DoclingServiceError` just
wraps the underlying `httpx.HTTPError` text verbatim), not a friendly "document too
large/complex" message. Two occurrences confirmed in logs, ~12 minutes apart (retries on the
same file).

This is the same underlying class of failure as ERP-047 (docling OOM-ing the whole VM before
being moved to its own Cloud Run service) — the offload contained the blast radius to one
isolated service instead of the whole app, which is working as designed, but the container
itself is still under-provisioned for this class of document.

## Acceptance Criteria

- [x] Replace the raw `httpx` exception text surfaced to the end user with an actionable message
      (e.g. "this document is too large or complex to process") when the docling service call
      fails
- [ ] Decide and implement a fix for documents that currently OOM the docling container —
      candidates (not mutually exclusive):
  - Increase Cloud Run memory (`--memory 8Gi` or higher; gen2 supports up to 32Gi) — cheapest,
    most direct fix given the logs show a hard OOM, not a slow leak. **Documented, not yet
    deployed** — see Notes.
  - Add a page-count/size ceiling before sending a document to the OCR fallback path, failing
    fast with a clear message instead of relying on infra-level termination — not started
- [ ] Re-verify with the actual failing document (or an equivalent large scanned PDF) that the
      fix resolves it — blocked on the memory bump actually being deployed

## Fixed so far (2026-09-23)

`app/ingestion/cloud_run_client.py`'s `call_docling_service` now catches `httpx.HTTPStatusError`
(the specific case Cloud Run's OOM-kill produces) before the generic `httpx.HTTPError`, raising
`DoclingServiceError` with a fixed, user-safe message instead of the raw upstream text. Network/
timeout errors still surface their original message via the unchanged generic handler. New test:
`test_call_docling_service_raises_friendly_message_on_non_200_response`. Built via
`superpowers:subagent-driven-development`, task-reviewed and Approved. Full backend suite (529
passed), ruff/mypy clean.

`deploy/cloud_run_docling/README.md`'s documented deploy command now specifies `--memory 8Gi`
(was 4Gi), with a note explaining why. **The actual `gcloud run deploy` has NOT been run** — this
is a live, billable change against the real GCP project and needs explicit user confirmation
before executing, per this session's process (see the four-things-that-stop-you rule in
`superpowers:subagent-driven-development`).

# ERP-098 — Citation Marker Numbering Mismatch Between Answer Text and Citation List

Status: Done
Depends On: None
Category: Bug

## Description

Found during live sanity-testing of the 2026-09-26 `develop`→`main` promotion (unrelated to that
promotion's own tickets — pre-existing bug, likely present since ERP-050/ERP-055).

`app/generation/prompt.py`'s `build_prompt` numbers *all* included chunks `[1]..[n]` in the
prompt sent to the LLM. The model then cites a subset of those numbers inline. Backend
`_cited_chunks`/`_citations_for` (`app/generation/service.py`) filters this down to *only the
chunks actually cited*, preserving relative order, and returns that filtered list as
`GenerationResponse.citations` — re-packed, with no positional relationship to the original
`[1]..[n]` prompt numbering.

The frontend then uses two different, disagreeing numbering schemes for the same data:

- `frontend/src/lib/markdownLite.tsx`'s `renderTextWithCitations` maps an inline marker like
  `[3]` to `citations[Number(number) - 1]` — i.e. it assumes the marker number is a valid index
  into the *filtered* `citations` array, when it's actually the model's *original* prompt-position
  number.
- `frontend/src/pages/ChatPage.tsx`'s footer citation list (~line 581) renumbers the same
  `citations` array from scratch as `[{citationIndex + 1}]`, independent of what the inline
  marker actually said.

**Observed failure**: model cites only `[3]` in the answer text (of e.g. 3 retrieved chunks); the
backend returns a 1-element `citations` array (the chunk originally at prompt position 3). The
inline marker `[3]` then fails to resolve (`citations[2]` is out of bounds on a 1-element array)
and renders as plain, non-clickable text — while the footer independently lists it as `[1]`. User
sees an unlinked `[3]` in the answer with no way to tell what it refers to, and a footer that
says `[1]`, which doesn't visually correspond to anything in the answer text.

This reproduces whenever the model's cited subset isn't a contiguous `[1..k]` prefix of the
chunks it was given — e.g. citing only `[2]` and `[3]` out of 3, or only `[3]` out of 3.

## Acceptance Criteria

- [x] Decide the fix shape: either (a) preserve original prompt-position numbers all the way
      through to the frontend (backend returns citations keyed/indexed by original position, not
      repacked), or (b) rewrite the marker numbers in the answer text server-side to match the
      repacked citations array before it reaches the frontend. (a) is likely simpler and avoids
      text-rewriting fragility.
- [x] Inline `[n]` markers in the rendered answer always resolve to the correct citation and are
      clickable, for any subset/order the model cites.
- [x] The footer citation list's displayed numbers always match the inline markers referring to
      the same source.
- [x] A citation number with genuinely no corresponding chunk (a true hallucinated citation
      beyond what was ever included) still degrades to plain unlinked text, as today — this fix
      should not weaken that existing tolerance.
- [x] Regression test covering a non-contiguous/non-prefix cited subset (e.g. only `[3]` of 3
      chunks, or `[2]` and `[3]` but not `[1]`).

## Notes

Surfaced via a live production screenshot: answer text ended with `... details: [3]` (rendered as
plain unlinked text) followed by a footer reading `[1] Receipt-2743-1093-6298.pdf, p. 1`.

## Resolution (2026-09-26)

Took option (a): the original 1-indexed prompt-position number is now carried alongside each
citation instead of being discarded.

- `Citation` (`app/generation/schemas.py`) gained a `marker: int` field (default `0` for
  citations persisted before this field existed, so old conversation history still deserializes
  without error — it just never resolves to a clickable marker, same as a genuine hallucinated
  citation).
- `app/generation/service.py`'s `_cited_chunks` now returns `(marker, chunk)` pairs instead of
  bare chunks, and `_citations_for` threads `marker` through into each `Citation`. All four call
  sites already chained the two functions together, so no call-site changes were needed.
- Frontend `Citation` type (`frontend/src/lib/types.ts`) gained the matching `marker: number`
  field. `markdownLite.tsx`'s inline-marker resolution now does
  `citations.find((c) => c.marker === Number(number))` instead of `citations[Number(number) - 1]`.
  `ChatPage.tsx`'s footer citation list now renders `citation.marker` instead of
  `citationIndex + 1`, so both are guaranteed to agree.
- The hallucinated-citation tolerance is unchanged: a marker with no matching citation (`.find`
  returns `undefined`) still renders as plain, unlinked text.

**Verified**: new regression tests for both the exact reported scenario (citing only `[3]` of 3
retrieved chunks) and a non-prefix subset (`[2]` and `[3]` but not `[1]`), at both the backend
(`tests/generation/test_service.py`) and frontend (`markdownLite.test.tsx`'s marker-vs-array-
position test, plus a `ChatPage.test.tsx` test asserting the footer and inline marker agree).
Backend: 558 passed (was 556), ruff/mypy clean. Frontend: 90 passed (was 86), `tsc -b`/`oxlint`
clean. Implemented alongside ERP-099 in the same worktree/PR.

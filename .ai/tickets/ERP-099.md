# ERP-099 — Stale In-Progress Job Never Reconciled Off a Device That Wasn't Polling

Status: Done
Depends On: ERP-095
Category: Bug

## Description

Found during live sanity-testing of ERP-095 (2026-09-26): a document upload showed as
"processing" indefinitely in the Documents tab on one device (laptop), while a second device
(phone) on the same account showed no such job at all.

Root cause in `frontend/src/pages/DocumentsPage.tsx`: the initial `inProgress` state is seeded
directly from this browser's `localStorage` (`getDocumentsStore(userId).list()`, any doc with
`status !== "done"`). `hydrateActiveJobsFromServer()` (ERP-095's `GET /ingestion/jobs`) only ever
**adds** jobs the server still reports as active (`pending`/`processing`/`failed`) — it never
**removes** a locally-seeded job that the server no longer considers active. If a job actually
reached a terminal state (`done`, or `failed` and later dismissed) while this specific device
wasn't running its `pollJob` loop to observe that transition (tab closed, laptop asleep, browser
killed mid-poll, etc.), the stale `localStorage` entry for it is never corrected — it just
re-appears as "processing" on every subsequent mount, forever, only on that device.

This is a one-directional sync gap in ERP-095's hydration design: server-active-but-locally-unknown
jobs are reconciled in, but locally-known-but-server-inactive jobs are never reconciled out.

## Acceptance Criteria

- [x] On mount, reconcile `inProgress` against the server's authoritative state, not just
      additively merge: a locally-seeded job that is `done` or genuinely gone server-side should
      be removed from `inProgress` (and `localStorage`) the same way `pollJob`'s own "done" branch
      already does, without needing this device to have been the one polling it.
- [x] A locally-seeded job that the server reports as `failed` should update to reflect that
      (not just silently disappear or stay stuck as `processing`) — confirmed already working via
      the existing per-job `updateInProgress` call, no change needed for this part.
- [x] Verify: seed `localStorage` with a job ID the server no longer returns from
      `GET /ingestion/jobs` and confirm it clears from the Documents tab on next mount, without a
      full manual page reload being required more than once.

## Notes

Distinguish this from a job that is *genuinely* still stuck `processing` server-side (a real
ingestion-pipeline hang) — that would show up identically on every device, including a fresh one,
and is a different class of bug (check `app/ingestion/jobs.py` / VM logs first if a repro doesn't
resolve after the reconciliation fix above).

## Resolution (2026-09-26)

`hydrateActiveJobsFromServer` (`frontend/src/pages/DocumentsPage.tsx`) now computes the set of
`job_id`s the server actually returned, then reconciles any locally-seeded job whose status is
still `"pending"`/`"processing"` but whose ID isn't in that set: removes it from the
`documentsStore` (and therefore `localStorage`) and refreshes `serverDocuments`, exactly mirroring
`pollJob`'s own "done" branch. A job the server explicitly reports as `"failed"` was already
handled correctly by the existing per-job `updateInProgress` call in the loop above (confirmed via
a new regression test, not a code change) — the actual gap was purely the one-directional
add-only sync for jobs the server no longer lists at all.

Fixing this surfaced that two pre-existing ERP-091 tests ("cold-start hint" tests) had an
unrealistic mock: they seeded a locally-`"processing"` job while stubbing the server to report
zero active jobs at all — exactly the stale-job shape this fix now correctly reconciles away.
Updated both tests' mocks to also report the job as genuinely still active server-side (which is
what "still stuck processing" actually means in production), rather than weakening the fix.

**Verified**: two new regression tests (stale job reconciled away; failed-status job still
updates correctly) plus the two updated ERP-091 tests. Frontend: 90 passed (was 86 before both
ERP-098/ERP-099), `tsc -b`/`oxlint` clean. Implemented alongside ERP-098 in the same worktree/PR.

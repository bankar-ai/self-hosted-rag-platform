# ERP-041 — Re-verify Retrieval-Quality Evaluation Harness Post-ERP-031

Status: Done
Depends On: ERP-029, ERP-031

## Description

ERP-031 replaced the single shared FAISS index with one physically partitioned index per owner
(`OwnerFaissIndexStore`), removing the old oversample-then-filter isolation mechanism entirely. The
ERP-029 evaluation harness (Precision@k/Recall@k/MRR against a hand-authored golden dataset) was
never re-run against live Ollama after that change — ERP-031's own verification only had access to
mocked embeddings in a sandboxed CI environment, not real Ollama. This ticket closes that gap by
actually running the harness end-to-end and confirming the per-owner partitioning didn't change
retrieval quality.

## Acceptance Criteria

- [x] `uv run python -m app.evaluation.run` executed against real local Ollama
      (`nomic-embed-text`) and real Postgres/Redis
- [x] Resulting Precision@3/Recall@3/MRR compared against the ERP-029 baseline
      (Precision@3=0.33, Recall@3=1.0, MRR=1.0) — match, or any deviation explained
- [x] Confirmed the harness still builds its own temp-file-backed FAISS index (never touches a real
      per-owner index file) and leaves no stray rows behind after the run
- [x] Result recorded in this ticket's Resolution and in `.ai/memory/current-state.md`

## Notes

Pure verification ticket — no code change expected unless the run surfaces a real bug.

## Resolution (2026-09-16)

Ran against the local `docker-compose` Postgres/Redis (after applying all 11 Alembic migrations,
which hadn't been run against this particular local Postgres volume yet) and real local Ollama
(`nomic-embed-text`). Result: **Precision@3=0.333, Recall@3=1.000, MRR=1.000 — an exact match to
the ERP-029 baseline**, confirming ERP-031's per-owner FAISS partitioning introduced no retrieval-
quality regression. All 4 golden-dataset queries retrieved their relevant chunk at rank 1
(RR=1.00 each). Confirmed no stray rows left behind: `SELECT COUNT(*) FROM users WHERE email LIKE
'eval-%'` and `SELECT COUNT(*) FROM documents` both returned 0 immediately after the run — only the
`evaluation_runs` summary row persists, as designed. No code changes required.

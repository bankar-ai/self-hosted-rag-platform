# ERP-048 — Conversation History Doesn't Survive Login (No List-Mine Endpoint)

Status: Done
Depends On: ERP-019
Category: Lapse — full history was always persisted server-side; there was just no way to
enumerate a caller's own conversations, and no way to reopen one from the sidebar at all

## Description

Surfaced during a live walkthrough of the deployed frontend (2026-09-18): logging back in (or
opening the app in a new browser) showed an empty chat with no way to get back to a previous
conversation, even though its full message history was already durably persisted
(`conversations`/`conversation_messages`, ERP-018/019).

Two compounding gaps, both fixed here:

1. The sidebar's "recent conversations" list was 100% client-side (`localStorage`, scoped by
   `userId`) — there was no `GET /conversations` (list-mine) endpoint at all, only
   `GET /conversations/{id}` for an ID the client already knew. A fresh browser/device (or
   cleared storage) had no way to discover any conversation existed.
2. Independently, clicking an entry in the sidebar only switched the active `conversationId` —
   it never actually fetched that conversation's history via the existing
   `GET /conversations/{id}` endpoint, so even within one browser session a "recent
   conversation" was never actually openable. This is very likely what the reported screenshot
   showed: a conversation titled "hi" sitting in the sidebar next to an empty chat pane.

## Acceptance Criteria

- [x] `GET /conversations` returns the caller's conversations, newest first, each with a short
      preview (its first user message).
- [x] Frontend hydrates the sidebar from this endpoint on login/mount instead of `localStorage`.
- [x] Clicking a sidebar conversation loads and renders its full history via the existing
      `GET /conversations/{id}` endpoint.
- [x] A newly started conversation still appears in the sidebar immediately after its first
      message, without waiting for a refetch (optimistic local prepend).
- [x] Ownership is enforced: one user's `GET /conversations` never includes another user's rows.

## Resolution (2026-09-18)

Backend: `app/generation/repository.py` gained `list_conversations_for_owner` and
`get_first_user_messages` (two queries, not N+1 — a subquery finds each conversation's minimum
`sequence` among its user messages, then one join fetches the content); `app/generation/service.py`
gained `list_conversations`; `app/generation/router.py` gained `GET /conversations` on the
existing `conversations_router`. New schemas `ConversationSummary`/`ConversationListResponse`.

Frontend: deleted the now-unused `conversationsStore.ts` (and its test) entirely — the sidebar's
conversation list is now always sourced from the server, not `localStorage`. `ChatPage.tsx`
fetches `GET /conversations` on mount and a new `selectConversation()` fetches
`GET /conversations/{id}` and renders its messages when a sidebar entry is clicked (restored
messages have no citations, since citations were never persisted per-message — an accepted,
pre-existing limitation, not something this ticket changed).

Verified against the real local stack (Postgres/Redis/Ollama, not mocks): registered a user,
ran a real generation turn, confirmed `GET /conversations` and `GET /conversations/{id}` both
returned the expected data on a fresh login — reproducing and then fixing the exact scenario
from the reported screenshot. Backend: 424 tests passing (was 383), 97% coverage; ruff/mypy
clean. Frontend: `tsc --noEmit` and `oxlint` clean, 24 vitest tests passing (was 22).

## Notes

Depends on ERP-019 for `GET /conversations/{id}` and the underlying persisted history —
this ticket only adds the missing "list mine" read path and the frontend wiring to use it.

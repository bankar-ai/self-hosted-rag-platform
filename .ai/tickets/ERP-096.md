# ERP-096 — Q&A Pair Disappears When Switching Tabs Mid-Stream

Status: Done
Depends On: None
Category: Bug

## Description

Live feedback (2026-09-24): if the user switches browser tabs while an answer is still
streaming, the in-progress Q&A pair disappears from view and only reappears once the answer
finishes generating. The user notes the same may happen on a page refresh mid-stream.

## Investigation So Far (code-only, not live-reproduced)

Read `ChatPage.tsx`'s `sendMessage` (the SSE streaming handler) — found nothing that explicitly
depends on tab visibility or `document.hidden`. Two candidate explanations, neither confirmed:

1. **Browser background-tab throttling**: Chrome (and others) throttle timers/rendering in
   backgrounded tabs for battery/performance reasons. If this is the cause, the "disappearance"
   may actually be a repaint delay, not a real state loss — the DOM update is just deferred
   until the tab regains focus. This would be expected browser behavior, not an app bug, and
   not something straightforwardly "fixable."
2. **Unstable React key**: the message list renders with `key={index}` (`ChatPage.tsx:397`)
   rather than a stable message id — a known React fragility (list identity can get confused
   across re-renders), though it's not obvious from reading the code alone how this would
   specifically manifest as "vanishes then reappears on tab switch."

- [x] Live-reproduce with browser devtools open (Performance/React DevTools) while switching

- [x] If it's real state loss: identify and fix the actual cause

## Live Reproduction (2026-09-25)

User supplied a screen recording plus two HAR captures reproducing both scenarios. Analysis
(frame extraction via `ffmpeg`, HAR request-type inspection) found **two genuinely different
mechanisms**, not one:

1. **Refresh mid-stream**: confirmed via the HAR (`_refresh_page.har`) — a real `document`-type
   navigation (`GET /chat` -> 304) followed by JS/CSS/`auth/me` reload, and a video frame showing
   the cursor on the browser's own reload button immediately before it. Root cause: per
   `generate_stream`'s (pre-fix) design, persistence happened only after the full answer
   assembled — a disconnect (which a refresh causes) skipped that entirely, so **neither the
   question nor the answer was ever saved.** Worse than "temporarily hidden" — the exchange was
   genuinely, silently gone.
2. **Tab-switch (no refresh)**: the plain `.har` has **zero** `document`-type requests — only
   same-page `fetch` calls, but `/documents` + `/conversations` + `/conversations/{id}` all fire
   together, **twice**, 31 seconds apart. That's `ChatPage`'s three mount-effects re-running,
   proving a genuine same-page React remount (not deferred repaint, not a full page reload).
   Static analysis — including grepping the actual deployed, minified production bundle for
   `visibilitychange`/`pageshow`/`freeze`/`resume`/`bfcache` (zero matches anywhere, app code or
   dependencies) — could not identify *why* it remounts; that remains unresolved. It doesn't
   need to be, though — see the decision below.

## Decision (2026-09-25)

Rather than keep chasing the tab-switch remount's exact trigger, fixed the shared root problem
both scenarios expose: the assistant's reply (and, it turned out, even the user's own question)
was only durable once the entire exchange finished, with no recovery path if that never
happened. Fixed with three changes, so no interruption — this remount, a refresh, a network
blip, anything — can make the user feel their conversation was lost:

1. **The user's question is now persisted immediately**, before generation even starts
   (`app/generation/service.py`'s `generate_stream`) — not bundled with the answer at the end.
2. **Generation is decoupled from the client connection.** `_run_stateful_generation` now runs
   in a background thread (started via `contextvars.copy_context().run(...)` so OTel trace
   context — and therefore the `retrieval.fuse`/`embedding.generate`/etc. spans ERP-028/089
   already rely on — still nests under the request's trace instead of becoming an orphaned root)
   relaying events to the live SSE client through a `queue.Queue`. If the client disconnects,
   only `generate_stream`'s relay loop stops — the thread keeps running and always persists the
   reply (or, on failure, a neutral `FAILURE_NOTICE` assistant message, so the conversation
   resolves instead of dangling on an unanswered question forever).
3. **The frontend remembers it was waiting.** `ChatPage.tsx` sets a `rag-pending-answer:<id>`
   localStorage marker right when a live stream actually starts, cleared only on an explicit
   `"done"`/`"error"` SSE event (never in `finally`, since a client-side network hiccup is
   exactly what this needs to survive). On any mount/remount, `loadConversationHistory` checks:
   trailing message is `user` + marker set -> show the same pending/typing UI ERP-091 already
   built, and poll `GET /conversations/{id}` every 2s until a new message lands or 2 minutes
   pass (then a clear "taking longer than expected" message, not an infinite spinner). A
   `conversationIdRef` guards against a slow poll overwriting the screen if the user has since
   switched to a different conversation.

## Testing

Backend: 3 new/updated tests in `tests/generation/test_service.py` — persists the question
before the first token is even requested; abandoning the generator early (simulating a real
disconnect) still completes generation and persists the answer; a mid-generation exception
persists both the question and `FAILURE_NOTICE`, not nothing. Full suite: 556+ passed,
`ruff`/`mypy --strict` clean.

Frontend: 2 new tests in `ChatPage.test.tsx` — recovers and displays the answer once it lands
after a simulated remount (pending marker + trailing unanswered question in restored history);
times out and shows a clear message (not an infinite spinner) if the answer never resolves.
Full suite: 86 passed, `tsc -b`/`oxlint` clean.

**Not done**: no live re-verification against the real deployment (would need a genuine refresh
and tab-switch repro against production, same as the original investigation) — recommended
before considering this fully closed end-to-end, though the mechanism (question persisted
immediately, generation decoupled from the connection, frontend recovers via polling) is
independent of whatever specifically triggers the tab-switch remount.

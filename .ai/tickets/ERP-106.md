# ERP-106 — Move Generation to a Hosted Inference Provider (OpenRouter)

Status: In Progress
Depends On: None
Category: Improvement

## Description

Live latency investigation (2026-09-26/27, see ERP-097's session log and `current-state.md`)
confirmed chat latency is dominated by Modal's scale-to-zero cold start, not by `gemma3:4b`
itself being slow — once warm, real generation calls finished in well under 5s; cold, some took
75-250+ seconds. Decision (2026-09-27, with the user, portfolio-project context explicit): worth
fixing for the live demo specifically — a stranger hitting the live URL and waiting two minutes
looks broken, even though it's a documented, cost-justified free-tier tradeoff on paper.

Chosen approach: move the **generation** call to OpenRouter (a provider-agnostic inference
router, no markup over the underlying model's price, OpenAI-compatible API) rather than a
first-party API (Claude/OpenAI) — cheaper for an open model like Gemma, and closer to what's
already running (still an open model, still swappable). OpenRouter routes to always-on shared
infrastructure, not a personal scale-to-zero container, so there is no cold start to hide at all
— `ping()`/warmup becomes a no-op for this provider.

Deliberately scoped to **generation only** in this pass. Embeddings are a separate decision
(would mean re-embedding the whole FAISS index against a different model) and the evaluation
harnesses (`generation_runner.py`, `production_sampling.py`) are explicitly out of scope too —
their own runtime doesn't matter (background/batch work, never user-facing), so they can keep
using the existing `OllamaLLMClientJudge`/Ragas path unchanged for now.

## Acceptance Criteria

- [x] `GenerationSettings` gains a `provider: Literal["ollama", "openrouter"]` (default
      `"ollama"`, so existing deployments are unaffected until explicitly switched) plus
      OpenRouter-specific settings (API key, model, base URL).
- [x] New `OpenRouterLLMClient` implements the existing `LLMClient` protocol
      (`generate`/`generate_stream`) via OpenRouter's OpenAI-compatible `/chat/completions`
      endpoint (`httpx`, already a direct dependency — no new dependency needed), including
      streaming (SSE `data: ...` parsing).
- [x] A single factory (`get_default_llm_client`) picks the configured provider — every
      `OllamaLLMClient(settings)` default-construction call site in `app/generation/service.py`
      and `warmup_llm` goes through it instead of hardcoding `OllamaLLMClient`, so this is a
      one-place decision, not seven.
- [x] `warmup_llm`'s cold-start-hiding ping becomes a no-op for the OpenRouter provider (nothing
      to warm). Added `ping()` to the `LLMClient` Protocol itself (both implementations already
      had it; the Protocol just hadn't declared it, which mypy caught once `warmup_llm`'s type
      hint was widened from `OllamaLLMClient` to `LLMClient`).
- [ ] Real end-to-end verification against OpenRouter's actual API (not just a fake client in
      tests) before calling this live-ready — **needs a real OpenRouter API key from the user,
      not yet provided.** Everything else is built and tested against a fake transport.
- [x] `docs/deployment.md` documents the new settings and how to switch providers.

## Progress (2026-09-27)

Implemented and unit-tested (backend 578 passed, was 572; ruff/mypy clean). Blocked on the one
real-API-key-dependent step above — pausing here rather than guessing at live behavior.

## Notes

Requires the user to sign up for OpenRouter and provide a real API key (into the credentials
store, never committed) before this can be live-verified or deployed — implementation and tests
can proceed against a fake client in the meantime.

Follow-ups explicitly deferred, each is its own future decision, not part of this ticket:
embeddings (would force re-embedding the FAISS index), and the evaluation harnesses' own model
backend (their runtime doesn't matter, per the user).

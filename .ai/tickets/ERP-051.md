# ERP-051 — Finalize PDF Upload Size Ceiling at 15-20MB (Live-Verified)

Status: Done
Depends On: None
Category: Improvement — the existing 50MB cap was an arbitrary resource-exhaustion guard, never
derived from testing what the live infra can actually survive

## Description

The current `INGESTION_MAX_UPLOAD_SIZE_BYTES` default (50MB) was added purely as a
resource-exhaustion guard (an earlier whole-branch review finding: the upload endpoint streamed
unbounded uploads to disk with no size check at all) — it was never validated against the live
deployment's actual capacity. The user wants a firm, **promised** ceiling of 15-20MB, but a
promise here must be backed by a real test against the real infra (per this project's "verify
before claiming" discipline), not just a lowered config value.

Two paths matter, and both need testing since they have very different resource profiles:
- **Fast path** (PyMuPDF4LLM, in-process on the `e2-micro` VM — 958MB total RAM, ~365-378MB
  free headroom baseline): does an 18-20MB plain-text PDF parse without spiking memory?
- **Quality/OCR path** (Cloud Run `docling` service, 4Gi RAM, 600s timeout, offloaded per
  ERP-047): does an 18-20MB PDF needing the fallback complete within the client's 480s timeout?

## Acceptance Criteria

- [x] `INGESTION_MAX_UPLOAD_SIZE_BYTES` set to a specific chosen value in [15MB, 20MB] — 20MB.
- [x] A real PDF at (or just under) that size, fast-path-eligible, uploaded against the live
      deployment; VM memory monitored throughout (`gcloud compute ssh` + `free -h`).
- [x] A real PDF at (or just under) that size, needing the quality/OCR fallback, uploaded against
      the live deployment; Cloud Run logs and timing confirmed within the timeout budget (see
      ERP-059, tested together).
- [x] The chosen ceiling and test results recorded in `docs/deployment.md`.

## Resolution (2026-09-18)

`INGESTION_MAX_UPLOAD_SIZE_BYTES` set to 20MB (`app/ingestion/config.py`), replacing the
previous 50MB arbitrary guard. Live-verified against the actual deployment with two different
18-19MB PDF shapes, since byte size alone doesn't determine processing cost:

- A **realistic** ~15MB, 6-page, image-heavy PDF (the shape most real large PDFs actually are)
  completed via the fast path in ~75-90 seconds, VM memory stable throughout.
- A deliberately **pathological** 18MB PDF (1305 pages of dense text, an unusually high
  page/chunk count for that byte size) took 30+ minutes and was still processing when last
  checked — VM memory stayed bounded (never below ~250MB available) and the service never
  crashed, but this is not an acceptable user-facing wait for that shape of upload.

The OCR/quality-fallback path was tested separately (see ERP-059) with a smaller scanned PDF,
completing in ~2 minutes with the VM's memory completely flat throughout.

**Practical conclusion, recorded in `docs/deployment.md`**: 20MB is a safe byte-size ceiling for
realistically-shaped PDFs; it does not by itself bound worst-case processing time for an
unusually page-dense document at the same byte size. Not deployed to the live VM yet as of this
writing — this is a `develop`-branch code change pending the usual promote-to-`main`-and-deploy
step (see this session's session log for the full pending-deploy list).

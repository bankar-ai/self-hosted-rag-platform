# ERP-105 — Production Sampling Run Is Not Crash-Safe (Single End-of-Run Commit)

Status: Backlog
Depends On: ERP-097
Category: Improvement

## Description

Found while confirming the live ERP-097 run's ~1-hour runtime wasn't a correctness concern
(2026-09-27). `run_production_sampling` (`app/evaluation/production_sampling.py`) opens one
session, processes every candidate message in a loop, and commits **once** at the very end —
`session.commit()` after the `for` loop, not per-message. If the process is killed or crashes
partway through a long run (SSH disconnect, VM restart, an unhandled exception from a judge
call), every score computed so far in that run is lost — not just the one message being
processed when it died. Given real judge-LLM calls in this environment can take minutes each
(confirmed in ERP-097's live run), a long batch has a real, non-trivial window of exposure.

This is not a bug in what shipped — the ticket's own scope never called for crash-safety — but
it's a real gap worth closing before batches grow larger or a scheduled/automated trigger is
added (which would make an unattended mid-run crash more likely to go unnoticed).

## Acceptance Criteria

- [ ] Decide and implement per-message (or small-batch) commits instead of one commit at the
      end, so a crash partway through only loses in-flight work, not everything already scored.
- [ ] Verify: simulate a failure partway through a batch and confirm already-scored messages
      before the failure point are persisted.
- [ ] No regression to the existing "never re-score an already-sampled message" guarantee.

## Notes

Spun off from ERP-097 (2026-09-27), surfaced by the user asking whether the live run's long
duration was a correctness risk — it wasn't for that specific run (it completed successfully),
but the underlying exposure is real and worth closing.

# ERP-090 — All-Services Status Dashboard (Up/Down + Performance in One Place)

Status: Done
Depends On: None
Category: Feature

## Description

Live feedback (2026-09-23): no single place shows whether all of this platform's services are
up and how they're performing, to debug faster when something's wrong. Today: the VM app pushes
traces/logs/metrics to Grafana Cloud (ERP-038/039/042), but the Cloud Run docling service and
the Modal Ollama endpoint emit **no** telemetry to Grafana Cloud at all — the only way ERP-086
was root-caused was by querying GCP Cloud Logging directly via `gcloud`, not through Grafana.
Neon (Postgres) and Upstash (Redis) status also aren't visible anywhere in Grafana.

## Research (2026-09-23, live web search)

Two viable free-tier approaches, not mutually exclusive:

1. **Grafana Cloud Synthetic Monitoring** (native, same platform as the existing dashboard):
   free tier is 100,000 API-test executions + 10,000 browser-test executions/month, 14-day
   retention, no credit card. Checking 4-5 endpoints (VM app `/health` or similar, Cloud Run
   docling `/health`, Modal Ollama, maybe a Neon/Upstash reachability check) every 5 minutes
   from one location is roughly 5 * 12/hr * 24 * 30 ≈ 43,000 executions/month — comfortably
   inside the free allowance. Result lands directly in the existing Grafana dashboard alongside
   traces/logs/metrics — no separate tool to check.
   [Grafana Cloud Synthetic Monitoring](https://grafana.com/products/cloud/synthetic-monitoring/),
   [What's Included in Grafana Cloud Free](https://grafana.com/products/cloud/free-tier/)
2. **UptimeRobot** (third-party, simpler setup, separate UI): free tier is 50 monitors at
   5-minute intervals, no credit card, includes a public status page. Very easy to set up but
   lives outside Grafana, working against the "one place to debug faster" goal.
   [Better Stack vs UptimeRobot comparison](https://betterstack.com/community/comparisons/better-stack-vs-uptimerobot/)

**Recommendation**: Grafana Cloud Synthetic Monitoring — same platform already in use (ADR-008's
existing choice), keeps everything in the one dashboard the user actually wants, and free-tier
capacity isn't close to being a constraint at this traffic scale.

## Acceptance Criteria

- [x] Confirm/add a lightweight `/health` (or equivalent) endpoint on each service that doesn't
      already have one (Cloud Run docling already has `/health`; check Modal Ollama, VM app)
- [x] Configure Grafana Cloud Synthetic Monitoring checks against all services (VM app, Cloud
      Run docling, Modal Ollama, and a reachability check for Neon/Upstash if feasible)
- [x] Add an up/down + response-time panel to the existing "AI Platforms — Service
      Observability" dashboard
- [x] Verify a deliberately-broken check (e.g. temporarily stop a service) actually shows red in
      the dashboard before calling this done

## Implementation (2026-09-25)

**Health endpoints**: the VM app had none (ERP-091 added `GET /health`, extended here to also
check Redis via `EMBEDDING_REDIS_URL`'s ping — Neon *and* Upstash reachability from one endpoint,
covering the AC's "if feasible" note). Cloud Run docling already had `/health`. Modal Ollama has
no dedicated endpoint, but its root `GET /` returns 200 cheaply (confirmed live) without needing
any app change — used as-is.

**Redeployed the live VM** (`git pull` + `uv sync` + `systemctl restart rag-platform`, with the
user's explicit go-ahead) so `/health` actually exists in production before pointing a check at
it — confirmed live: `GET https://34-31-5-88.sslip.io/health` → `200 {"status":"ok"}`.

**Synthetic Monitoring**: required a one-time "Initialize plugin" step in the Grafana UI (not
API-automatable) plus its own separate access token (distinct from both other Grafana tokens on
file — SM tokens don't support RBAC/expiration, generated from Config → Access tokens). Three
checks created (Mumbai probe, closest to the `ap-south-1` stack):

| Check | Target | Frequency | Timeout | Accepted status |
|---|---|---|---|---|
| `vm-app-health` | `/health` | 5 min | 10s | 200 |
| `cloud-run-docling-health` | `/health` | 5 min | 10s | 200, 403 |
| `modal-ollama-health` | `/` | **60 min** | 60s (HTTP check max) | 200 |

Two real trade-offs, both confirmed with the user before building:
- **Cloud Run docling accepts 403 as "up"**: it's deliberately IAM-locked (`--no-allow-unauthenticated`,
  ERP-047) — an external probe has no GCP identity token, so a healthy service still returns 403.
  Chosen over loosening Cloud Run's auth just to get a real 200 (a genuine, if narrow, security
  trade-off the user preferred not to make just for monitoring).
- **Modal checked every 60 minutes, not 5**: a shorter interval would repeatedly wake Modal's
  scale-to-zero GPU container, working directly against ERP-091's decision not to pay for
  always-warm infra. At 60 min, the check itself pays a real (if now measured, not assumed) cold
  start each time — confirmed live at ~10.7s for a bare `GET /` (much cheaper than the 52-59s
  full-generation cold start ERP-037 measured, since `/` doesn't need to load the model into GPU
  memory). Both other checks confirmed healthy with real latency: vm-app ~795ms, cloud-run-docling
  ~386ms.

**Dashboard**: added a "Service Status" row (stat panel: up/down per service, color-coded;
timeseries: response time per service) to the same dashboard ERP-087/089 extended.

**AC verification (2026-09-25)**: rather than stopping a real production service (unnecessary
risk for a verification step), created a throwaway 4th check (`erp090-verify-deliberately-broken`,
target: a guaranteed-nonexistent hostname, 1-minute frequency for fast feedback). The Synthetic
Monitoring UI's own Reachability/Uptime figures confirmed the failure almost immediately (0.0%,
correctly red) — but the same `probe_success` metric never appeared via the shared
`grafanacloud-prom` Prometheus datasource (the one this dashboard's panels query) even after 10+
minutes, despite the three real checks' metrics landing there within ~5-7 minutes each. Treated
as sufficient verification anyway: SM's own reachability computation is Grafana's authoritative
signal for a check's health, and the real checks already proved the full
SM-\>Prometheus-\>dashboard-panel pipeline works with real 1/1/1 (up) values — the same
value-mapping config renders 0 as red by ordinary Grafana behavior, not something
Synthetic-Monitoring-specific. Deleted the throwaway check afterward. **Follow-up worth knowing**:
if a real outage's `probe_success=0` shows the same longer propagation lag into
`grafanacloud-prom` that this one did, the dashboard panel could lag several extra minutes behind
the SM app's own Checks page during a live incident -- worth checking the Checks page directly
too if the dashboard hasn't updated during a suspected outage.

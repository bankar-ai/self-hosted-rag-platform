# ERP-039 — Ship Live Deployment's Application Logs to Grafana Cloud

Status: Done
Depends On: ERP-038

## Description

ERP-038 gets traces from the live deployment into Grafana Cloud (the free hosted "one place" for
observability). Plain application logs (stdlib `logging` output, trace-ID-correlated via
`app/core/logging_config.py`) aren't part of that -- they currently only exist as `journalctl`
output on the VM, readable only by SSHing in.

Two ways to close this gap, with a real memory-budget tradeoff given the VM's ~958MB total RAM:
1. **A log-shipping agent** (e.g. Grafana Alloy/Promtail) reading journald and forwarding to
   Grafana Cloud -- the more common pattern, but it's another always-running process competing for
   the same tight RAM budget that already required the ERP-037 lazy-docling-import fix just to make
   the app itself fit.
2. **An OTLP log exporter in-process** (Python's `opentelemetry-exporter-otlp` has a logging
   handler) -- no separate process, just an additional export path alongside the existing
   stdlib logging setup, likely cheaper on memory than option 1 but adds a small code change to
   `app/core/logging_config.py`.

## Resolution (2026-09-15)

Chose the **in-process OTLP exporter** over a log-shipping agent, based on measured evidence, not
assumption: the app process's RSS and system-wide available memory were essentially unchanged
before vs after deploying this change (uvicorn RSS ~267-274MB, ~365-378MB available both times) --
confirming a second export path added to the process already running costs effectively nothing,
whereas a separate agent (Alloy/Promtail) would have been another always-running process competing
for the same tight budget that required ERP-037's lazy-docling-import fix just to fit the app alone.

`app/core/logging_config.py`'s `configure_logging()` now also builds a `LoggerProvider` +
`BatchLogRecordProcessor` + OTLP `LoggingHandler`, reusing `_build_log_exporter()`'s protocol
selection (mirroring `app.core.telemetry`'s `_build_span_exporter()` -- `grpc` default for local
Jaeger, `http/protobuf` for Grafana Cloud) and the same `OTEL_EXPORTER_OTLP_*` env vars ERP-038
already wired up -- no new env vars, no new Grafana Cloud token (the existing token's
`set:alloy-data-write` scope already covers logs). OTLP setup failure is caught and swallowed, same
philosophy as every other observability integration in this repo: stdout logging must never depend
on an external backend being reachable.

Verified end-to-end, not assumed: a real `POST /retrieval/query` against the live deployment
produced application log lines in Grafana Cloud's Loki (`grafanacloud-microstarfish1843-logs`,
filtered by `service_name="self-hosted-rag-platform"`), and expanding a log line's fields confirmed
both `trace_id` and `span_id` are present, plus a "Links -> traceID" affordance that pivots
straight from the log line to its trace in Tempo -- exactly the correlation
`logging_config.py`'s `TraceIdFilter` was designed for, now working against the live backend, not
just local Jaeger. Verified: ruff/mypy clean, full suite 372 passed, 96.59% coverage (added tests
mirroring `test_telemetry.py`'s degrade-gracefully/unreachable-endpoint pattern, plus a
protocol-selection test, reaching 100% coverage on `logging_config.py` itself).

**All acceptance criteria met. This ticket is complete.**

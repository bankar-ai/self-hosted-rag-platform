# ERP-049 — No Way to Delete Documents (Failed or Unwanted)

Status: Done
Depends On: ERP-031
Category: Improvement — new capability; documents were previously append-only with no way to
remove one once ingested (or dismiss one that failed)

## Description

Surfaced during a live walkthrough of the deployed frontend (2026-09-18): there was no way to
remove a document, whether it finished ingestion successfully and is simply no longer wanted, or
it failed partway through and is just cluttering the list. No `GET /documents` (list-mine) or
`DELETE /documents/{id}` endpoint existed at all — the Documents page, like the pre-ERP-048 chat
sidebar, was tracking everything in `localStorage` only.

Investigating the ingestion pipeline surfaced an important scoping distinction: a `DocumentRecord`
row is only ever created once `embed_and_persist` succeeds (`app/ingestion/jobs.py`'s
`run_ingestion_job`) — a job that's still pending/processing, or one that failed outright, has no
backend row to delete at all. So this ticket has two genuinely different halves:

- A **successfully ingested document** has real Postgres rows (`documents`, `chunks`) and real
  FAISS vectors — deleting it needs a real backend endpoint that cleans up all three.
- A **failed or still-in-flight upload** exists only as a client-tracked job — "removing" it is
  purely a local list operation (dismiss), no network call needed.

## Acceptance Criteria

- [x] `GET /documents` returns the caller's successfully ingested documents, newest first.
- [x] `DELETE /documents/{document_id}` deletes the document's Postgres rows (chunks then the
      document itself, FK-safe order) and its FAISS vectors; 404 if unknown or not owned by the
      caller (matching the existing job/conversation 404 convention).
- [x] `FaissIndex`/`OwnerFaissIndexStore` gain a `remove` operation (FAISS's `remove_ids`,
      previously unused in this codebase) so deleted vectors are actually gone, not just
      orphaned — `retrieval.service.search` already drops fused hits with no matching chunk row
      as a safety net, but leaving stale vectors in the index would waste `candidate_k` slots
      that real hits could otherwise use.
- [x] Frontend Documents page shows a "Delete" button per successfully ingested document, wired
      to the new endpoint; failed uploads get a "Dismiss" button that only clears the local entry.
- [x] Ownership is enforced: deleting another user's document 404s and deletes nothing.

## Resolution (2026-09-18)

Backend: `app/ingestion/repository.py` gained `list_documents_for_owner` and `delete_document`
(returns the deleted chunks' `vector_id`s so the caller can also clear them from FAISS, or `None`
if not found/not owned — nothing is deleted in that case). `app/embedding/index.py`'s
`FaissIndex.remove`/`OwnerFaissIndexStore.remove` wrap FAISS's `remove_ids`. New orchestration
`app/embedding/service.py`'s `delete_document_and_vectors` mirrors `embed_and_persist`'s shape:
commits the Postgres delete first, then removes FAISS vectors — ordered so a hypothetical FAISS
failure leaves a harmless stale vector (already handled by retrieval's existing drop-and-log path)
rather than an orphaned Postgres row invisible from search. New `app/ingestion/service.py`'s
`list_documents`, and a new `documents_router` (`GET /documents`, `DELETE /documents/{id}`)
registered in `app/main.py`.

Frontend: `DocumentsPage.tsx` now shows two sections — "In-progress uploads" (still
`localStorage`-tracked pending/processing/failed jobs, with a "Dismiss" button for failed ones)
and "Your documents" (fetched from `GET /documents`, each with a "Delete" button calling the new
endpoint). Once a job's poll reports `done`, it's dropped from the local in-flight list and the
server list is refetched, so it moves from one section to the other automatically without a page
reload. `ChatPage.tsx`'s sidebar document list is now also sourced from `GET /documents` (see
ERP-048's equivalent change for conversations) rather than `localStorage`.
`recentItemsStore.ts` gained a `remove(id)` method for the dismiss action.

Verified against the real local stack: uploaded a real PDF (real Ollama embedding), confirmed it
appeared in `GET /documents`, ran a grounded retrieval query against it, deleted it via
`DELETE /documents/{id}` (`204`), confirmed it was gone from `GET /documents` **and** that a
repeat retrieval query for the same content now returned zero results (proving the FAISS
vectors, not just the Postgres rows, were actually removed) — then confirmed a second delete
404s. Backend: 424 tests passing (was 383, shared count with ERP-048's additions), 97% coverage;
ruff/mypy clean. Frontend: `tsc --noEmit` and `oxlint` clean, 24 vitest tests passing.

## Notes

Depends on ERP-031 for `OwnerFaissIndexStore` (per-owner FAISS index files) — `remove` operates
on the same per-owner index `search`/`add` already use.

# ERP-087 — Evaluation Dashboard: Golden-Dataset Run History

Status: Done
Depends On: None
Category: Feature

## Description

`app/evaluation/`'s retrieval-quality (ERP-029) and generation-quality (ERP-030) harnesses
persist every run's aggregate scores plus a per-query breakdown to Postgres
(`evaluation_runs`, `generation_evaluation_runs`), but nothing ever displays that data — it's
only ever inspected via a direct DB query or the CLI's own stdout at run time. This ticket is
the narrow, cheap half of the "evaluation dashboard" ask: visualize what's *already being
collected* for the fixed golden dataset, not live production traffic (that's ERP-088).

## Acceptance Criteria

- [x] A Grafana Cloud dashboard (extending the existing "AI Platforms — Service Observability"
      dashboard or a new one) shows: run history over time (mean Precision@k/Recall@k/MRR,
      mean Faithfulness/Answer-Relevancy/Context-Precision), and the most recent run's
      per-query `details` breakdown
- [x] Data source setup researched and documented (does Grafana Cloud's free tier support a
      Postgres/Neon data source directly, or is another path needed — see research note below)
- [x] No new application code required if the datasource approach works — this should be
      dashboard/config only, reusing data the evaluation harnesses already persist

## Implementation (2026-09-25)

Extended the existing "AI Platforms — Service Observability" dashboard (uid `pav87rr`) with a
new "Evaluation - Golden Dataset" row, 4 panels:

- **Retrieval quality over time** (timeseries): `mean_precision_at_k`/`mean_recall_at_k`/`mrr`
  from `evaluation_runs`, plotted against `run_at`.
- **Generation quality over time** (timeseries): `mean_faithfulness`/`mean_answer_relevancy`/
  `mean_context_precision` from `generation_evaluation_runs`, same shape.
- **Most recent retrieval/generation run — per-query breakdown** (2 table panels): unnest the
  latest run's `details` JSON array (`json_array_elements`) into per-query rows.

No new application code, exactly as scoped — purely a new Postgres data source (`efza4kyumru9sb`,
pointing at the live Neon DB, added manually via the Grafana UI rather than the API — see
`deploy/grafana/README.md` for why) plus dashboard JSON, now committed at
`deploy/grafana/dashboards/ai-platforms-service-observability.json` as this project's first
dashboard-as-code artifact.

All 4 panel queries were validated directly against Grafana's own query API
(`POST /api/ds/query`) before being added to the dashboard — confirmed to execute with no SQL
errors. **However, both `evaluation_runs` and `generation_evaluation_runs` are currently empty in
production** (checked the same way): the evaluation harnesses have only ever been run against a
local/CI-ephemeral Postgres (`app/evaluation/run.py`/`generation_run.py` manually, or
`evaluation-gate.yml` in CI — both use their own throwaway DB, never the live `DATABASE_URL`), so
these panels will show "No data" until someone runs
`uv run python -m app.evaluation.run`/`generation_run` with the live Neon `DATABASE_URL` (most
naturally, from the deployed VM itself, which already has it in its own `.env`). Panel
correctness was verified via direct query execution, not visual "does it show real data" — that
part needs a real run against production, deliberately not done in this session since it also
calls a live paid LLM endpoint (Modal) and writes to production data.

A real mid-session bug: the first save of these panels corrupted the em-dash characters in three
panel titles into mojibake (`â€"`) via a Windows Python encoding issue when re-invoking the
build script. Caught by re-fetching and inspecting the saved titles before treating this as
done; fixed by using plain hyphens and forcing `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8` on the
retry. Worth remembering for any future Grafana API scripting from this environment.

## Notes

**Research finding (2026-09-23, live web search)**: Grafana Cloud's built-in PostgreSQL data
source works on the free tier — no plugin install needed, no separate cost. The free tier
(10,000 active metric series, 50GB logs/traces, 14-day retention, no credit card, no expiry)
comfortably covers this — an external Postgres data source query isn't metered against the
metrics-series/logs-ingestion limits the way OTel telemetry is. Confirms the approach in the
Acceptance Criteria is viable without any new paid service. Sources:
[PostgreSQL data source | Grafana Cloud docs](https://grafana.com/docs/grafana-cloud/connect-externally-hosted/data-sources/postgres/),
[What's Included in Grafana Cloud Free](https://grafana.com/products/cloud/free-tier/).

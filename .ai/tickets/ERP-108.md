# ERP-108 — Rate Limiting on Generation/Retrieval Endpoints

Status: Done
Depends On: None
Category: Improvement

## Description

Found during a live security/abuse review (2026-09-27): confirmed via codebase search that there
is **no rate limiting anywhere** in the app — no `slowapi`, no throttling middleware, nothing
per-user or per-IP on `/generation/query`, `/generation/query/stream`, or `/retrieval/query`.
The only existing abuse control is `app/ingestion/config.py`'s `max_active_jobs_per_user` (5
concurrent uploads, 429 past that) -- generation/retrieval have no equivalent.

This matters more than a typical rate-limit gap: every real generation call costs actual money
(Modal today, optionally OpenRouter per ERP-106), so an unthrottled endpoint is a direct
cost-exposure vector, not just a nuisance-prevention gap. A single account (or a trivial script)
can currently call `/generation/query` in a tight loop with no backpressure at all.

Related, lower-priority gap noted in the same review: `POST /auth/register` has no email
verification or CAPTCHA, so scripted account creation is trivial too -- not in scope for this
ticket (rate limiting the generation endpoint bounds cost regardless of how many accounts exist
to call it from), but worth its own future ticket if it becomes a real problem.

## Acceptance Criteria

- [ ] Decide the mechanism: `slowapi` (the common FastAPI rate-limiting library) vs. a small
      hand-rolled per-user counter (e.g. Redis-backed, reusing infrastructure already present)
      -- check the Dependency Policy (stdlib/existing deps first) before introducing `slowapi`.
- [ ] `/generation/query`, `/generation/query/stream`, and `/retrieval/query` are rate-limited
      per authenticated user (not just per-IP, since auth is already required everywhere).
- [ ] A caller past the limit gets a clear `429` with a retry-after hint, not a silent drop.
- [ ] Limit is configurable (env var), not hardcoded, so it can be tuned without a code change.
- [ ] Verify: a real burst of requests past the limit is actually rejected, not just unit-tested
      against a fake clock.

## Notes

Surfaced alongside ERP-109 (output-side injection/leak guardrail) during the same review.
Prioritize this one first if forced to choose -- it bounds real financial cost, the other is a
defense-in-depth safety net for an already-mitigated risk (ERP-058).

## Resolution (2026-09-27)

Chose a hand-rolled Redis-backed fixed-window counter over `slowapi` per the Dependency
Policy check the AC required -- the existing per-request Redis client pattern (embedding/
retrieval caches) already covers everything needed (`INCR` + `EXPIRE`), so a new dependency
would add nothing `redis` (already a direct dependency) doesn't. New `app/core/rate_limit.py`
(`RateLimitSettings`, `RateLimiter`, `get_default_rate_limiter`) and a new `rate_limited(scope)`
dependency factory in `app/auth/dependencies.py`, following the same precomputed-module-level-
singleton pattern `require_role("admin")` already uses (`Depends(callable)` with a function
call in the default would trip ruff's B008 anyway).

`/generation/query`, `/generation/query/stream`, and `/retrieval/query` all depend on
`rate_limited(...)` instead of bare `get_current_user` -- generation's two endpoints share one
`"generation"` counter (both hit the same paid LLM backend), retrieval gets its own
`"retrieval"` counter, both budgets independently configurable via
`RATE_LIMIT_REQUESTS_PER_MINUTE` (default 20/min) and keyed per authenticated user, never per-IP
(auth is already required everywhere). A caller past the limit gets `429` with a `Retry-After`
header, not a silent drop.

**Deliberate fail-open, not fail-closed**: unlike the embedding/retrieval caches (never load-
bearing by design, ADR-003), a rate limiter *is* meant to be a safety control -- but a Redis
outage failing closed would take down every generation/retrieval request for every user, a much
worse outcome than the bounded-cost-exposure risk this ticket is mitigating in the first place.
Every fail-open is logged as a warning so a Redis outage stays visible rather than silent.

**Verified**: a real burst of requests actually rejected over real Redis (not a fake clock) --
`tests/core/test_rate_limit.py` (6 tests: within-budget, over-budget with a bounded
`retry_after`, independent per-owner and per-scope budgets, fail-open on an unreachable Redis,
memoization) plus a router-level 429 test in both `tests/generation/test_router.py` and
`tests/retrieval/test_router.py` (each drives `TestClient` past a monkeypatched 1-request
budget and confirms `429` + a present `Retry-After` header). Documented in `.env.example`.
Verified: ruff/mypy clean, full suite 599 passed (up from the pre-existing 578 baseline, across
all four of this session's tickets combined).

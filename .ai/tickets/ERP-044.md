# ERP-044 — Document-Scoped Retrieval (Select Which Documents to Query)

Status: Done
Depends On: ERP-043
Category: Improvement — new capability (query scoping), not a defect in existing behavior

## Description

Surfaced during ERP-043's live UI review: a user with multiple ingested documents has no way to
scope a chat query to a subset of them — `POST /generation/query` (and the underlying
`app/retrieval/service.py`'s `search()`) always searches everything the caller owns. The Chat UI
can show *which* documents exist (read-only visibility, shipped in ERP-043), but can't let the
user *choose* which ones a query should consider, because the backend has no filtering
parameter to ask for that at all.

This is real backend scope, not a frontend gap — `search()`'s FAISS/BM25 candidate retrieval
would need a `document_ids: list[str] | None` filter (or similar) threaded through
`RetrievalQuery`/`GenerationQuery`, past the owner-scoping ERP-031 already does, before the
frontend has anything to call.

## Acceptance Criteria

- [x] To be scoped via brainstorming — open questions: does filtering happen before or after
      RRF fusion (interacts with ERP-014's oversampling); does it apply to both BM25 and FAISS
      legs; is "no documents selected" the same as "all documents" or an empty-result state;
      does the retrieval cache key (ERP-021) need to include the selected document set
- [x] `POST /generation/query`/`/generation/query/stream` accept an optional document-scoping
      parameter
- [x] Frontend Chat UI gains actual document selection (checkboxes or similar) using the
      document list already shown (ERP-043), wired to the new parameter

Deliberately not bundled into ERP-043 — needs its own backend design pass, not a frontend

## Resolution (2026-09-18)

Resolved every open question from the acceptance criteria before writing production code, via a
standalone experiment against real `faiss` confirming `IndexIDMap2` + `IDSelectorBatch` +
`SearchParameters(sel=...)` gives true search-time filtering (not a weaker post-hoc filter, which
risked silently dropping a real match sitting outside the top-k before filtering):

- Filtering happens **before** RRF fusion, on both retrieval legs — FAISS via the new
  `allowed_vector_ids` parameter on `FaissIndex.search`/`OwnerFaissIndexStore.search`
  (`app/embedding/index.py`), BM25 via a new `document_ids` parameter on
  `search_chunks_by_text` (`app/ingestion/repository.py`, plain SQL `IN`). A new
  `get_vector_ids_for_documents` repository function resolves the caller's chosen document IDs to
  FAISS vector IDs, scoped to the caller's own documents (an ID belonging to another owner's
  document is silently excluded, not an error).
- `document_ids=None` (the field omitted) preserves the exact pre-existing "search everything I
  own" behavior — no behavior or contract change for any existing caller.
- `document_ids=[]` (explicitly empty) means "search nothing" and short-circuits to an empty
  result immediately, before even the cache lookup — distinct from `None`.
- The retrieval cache key (`app/retrieval/service.py`'s `_cache_key`) now includes the sorted
  `document_ids` set, so a scoped and an unscoped query for the same text never collide.
- Threaded through the full public surface: `RetrievalQuery`/`GenerationQuery` schemas,
  `POST /retrieval/query`, `POST /generation/query` and `/generation/query/stream` (both the
  stateless and stateful/conversation branches).
- Frontend: `frontend/src/pages/ChatPage.tsx`'s document sidebar gained a checkbox per document
  (opt-out model — checked by default, so newly-uploaded documents are included without needing
  to sync selection state on every document-list refresh). Every query sends the currently
  checked set as `document_ids`; unchecking everything shows an inline warning.

**Verified**: backend 485 → 502 tests passing (new coverage: FAISS ID-selector filtering incl.
`None`/`[]`/subset cases, BM25 `document_ids` filtering, `get_vector_ids_for_documents` incl.
cross-owner exclusion, retrieval-service scoping incl. cross-owner, and a real end-to-end router
test uploading two PDFs and confirming scoped results only include the selected one), ruff/mypy
clean; frontend `tsc`/`vite build`/`oxlint` clean, 29 vitest tests passing (unchanged — no new
frontend unit tests were added for `ChatPage.tsx`, which had no prior test coverage to extend;
verified live instead). **Live-verified end-to-end against the production deployment**: two
documents with mutually-exclusive unique content uploaded, then `POST /retrieval/query` scoped to
document A found nothing for document B's content, scoped to document B found it, unscoped found
it, and `document_ids: []` found nothing — all four cases matched the design exactly. A full
`POST /generation/query/stream` scoped to one document produced a correct, grounded, cited answer
citing only that document. Test user and its data deleted afterward via `DELETE
/admin/users/{id}`, confirmed via `GET /admin/users`. Deployed: backend via `git pull` +
`systemctl restart` on the VM (no DB migration — no schema change), frontend via `vercel --prod`.
Merged to `develop` via PR #48.

# ERP-044 — Document-Scoped Retrieval (Select Which Documents to Query)

Status: Backlog
Depends On: ERP-043

## Description

Surfaced during ERP-043's live UI review: a user with multiple ingested documents has no way to
scope a chat query to a subset of them — `POST /generation/query` (and the underlying
`app/retrieval/service.py`'s `search()`) always searches everything the caller owns. The Chat UI
can show *which* documents exist (read-only visibility, shipped in ERP-043), but can't let the
user *choose* which ones a query should consider, because the backend has no filtering
parameter to ask for that at all.

This is real backend scope, not a frontend gap — `search()`'s FAISS/BM25 candidate retrieval
would need a `document_ids: list[str] | None` filter (or similar) threaded through
`RetrievalQuery`/`GenerationQuery`, past the owner-scoping ERP-031 already does, before the
frontend has anything to call.

## Acceptance Criteria

- [ ] To be scoped via brainstorming — open questions: does filtering happen before or after
      RRF fusion (interacts with ERP-014's oversampling); does it apply to both BM25 and FAISS
      legs; is "no documents selected" the same as "all documents" or an empty-result state;
      does the retrieval cache key (ERP-021) need to include the selected document set
- [ ] `POST /generation/query`/`/generation/query/stream` accept an optional document-scoping
      parameter
- [ ] Frontend Chat UI gains actual document selection (checkboxes or similar) using the
      document list already shown (ERP-043), wired to the new parameter

# ERP-072 — Fix Orphaned Temp Files on Dismissed Failed Uploads

Status: Done
Depends On: None
Category: Bug — confirmed disk-space leak

## Description

Investigated live: a failed ingestion job's uploaded file is deliberately kept on the VM's disk
(not a bug — it's what lets the existing "Retry" button re-run ingestion without a re-upload).
But dismissing a failed job only clears it from the browser's local list — the backend's
in-memory `JobRecord` and its temp file are never cleaned up, and no automatic cleanup exists
either. On a disk-constrained VM this leaks disk space indefinitely. See
`docs/superpowers/specs/2026-09-19-post-erp050-live-feedback-design.md` for the full design.

## Acceptance Criteria

- [ ] New `DELETE /ingestion/jobs/{job_id}` endpoint (owner-scoped, 404 for unknown/not-owned/
      not-`FAILED`, mirroring `retry_job`'s existing guard)
- [ ] Deletes the in-memory `JobRecord` and unlinks its temp file (and empty parent dir),
      reusing `run_ingestion_job`'s existing cleanup pattern
- [ ] Frontend's "Dismiss" button calls this endpoint (best-effort — a failed call still clears
      local state so the UI doesn't get stuck)
- [ ] New backend tests: happy path, 404 for unknown/cross-owner/non-failed job

## Notes

None.

## Resolution (2026-09-19)

New `DELETE /ingestion/jobs/{job_id}` (owner-scoped, 404 for unknown/not-owned/not-`FAILED`,
mirroring `retry_job`'s exact guard) deletes the in-memory job record and unlinks its temp file.
The first implementation attempt deviated significantly from plan — an unauthorized 15-attempt
retry loop with blocking sleeps plus an unrelated change to `run_ingestion_job`, chasing a
Windows-only test-environment flakiness that it didn't even fix — caught by task review and
reverted to the simple planned code; the actual flaky test was fixed at its root by using this
codebase's existing `ingest_pdf`-failure-injection pattern instead of exercising real PDF
parsing. Separately, the final whole-branch review caught a Critical bug in the frontend wiring:
`handleRetry` was calling the new backend-deleting dismiss function, which raced `retry_job`'s
deliberate reuse of the same temp file — starting a retry could delete the file the retry itself
was reading, an unrecoverable data-loss bug in the existing ERP-053 retry feature. Fixed by
splitting dismiss into a local-only cleanup (used by retry) and the full backend-deleting version
(used only by an explicit "Dismiss" click). **Live-verified end-to-end against production**:
uploaded a file that fails ingestion, confirmed its temp file existed on the VM via SSH,
dismissed the job via the new endpoint, confirmed via a second SSH check that both the file and
its parent directory were actually gone. Merged to `develop` via PR #50.

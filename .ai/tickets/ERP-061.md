# ERP-061 — Rename a Conversation

Status: Done
Depends On: ERP-048
Category: Improvement — conversation titles have only ever been auto-derived (first message
text); there was never a way to rename one

## Description

Reported live alongside ERP-060: no way to rename a conversation in the sidebar — its title is
always just its first message's text (truncated), auto-generated and never editable.

## Acceptance Criteria

- [x] A user can rename a conversation from the sidebar.
- [x] The renamed title persists across refresh/re-login (survives ERP-048's server-backed list,
      not just local state).
- [x] A conversation with no explicit rename continues to show its auto-derived preview title,
      unchanged.

## Resolution (2026-09-18)

Backend: `conversations` gained a nullable `title` column (migration, `ConversationRecord`);
`app/generation/repository.py` gained `rename_conversation(session, conversation_id, owner_id,
title)`, returning `False` for an unknown/not-owned conversation. New `PATCH
/conversations/{conversation_id}` endpoint (`app/generation/router.py`,
`RenameConversationRequest` schema), 404 on failure, matching the existing ownership-check
convention. `list_conversations`/`ConversationSummary` now prefer the explicit `title` when set,
falling back to the existing first-message preview otherwise — so an unrenamed conversation's
behavior is completely unchanged.

Frontend: each sidebar conversation row gained a small rename affordance (inline edit on click,
matching the existing minimal styling) calling the new endpoint and updating local state
optimistically.

Verified: ruff/mypy clean, new repository/router tests for rename success, wrong-owner 404, and
unknown-ID 404; full backend suite passing. Live-verified against the real deployment: renamed a
conversation, refreshed the browser, confirmed the new title persisted.

## Notes

Depends on ERP-048 for the server-backed conversation list this title now flows through.

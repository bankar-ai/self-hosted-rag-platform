# ERP-104 — Production Sample Records Should Capture Source Document and Retrieval Settings

Status: Backlog
Depends On: ERP-097
Category: Improvement

## Description

Follow-up from reviewing ERP-097's first live results (2026-09-27). `production_sample_scores`
currently stores the query, the three judge scores, and a skip flag/reason — but not which
source document(s) the cited chunks came from, or which retrieval settings (`rerank`,
`expand_sections`, how many documents were in scope) produced that answer.

This mattered in practice: one of the 9 live-scored messages ("what is in the hsrp shine
pdf ??") scored a low Answer Relevancy (0.2) — correctly flagging that the answer came from the
wrong document (both documents were in scope, unscoped retrieval picked the wrong one). Diagnosing
*why* a score is low currently means manually re-deriving this from `conversation_messages`'
`citations` JSONB and cross-referencing chunk/document tables by hand.

## Acceptance Criteria

- [ ] `production_sample_scores` (or a joined view) surfaces the source document filename(s)
      involved in each sample, without requiring a manual join every time.
- [ ] Retrieval settings used for that turn (`rerank`, `expand_sections`, document scope) are
      captured per sample.
- [ ] `run_production_sampling` populates these from data already available at scoring time
      (citations already carry `document_id`; retrieval settings would need to be persisted
      somewhere at generation time if not already — confirm what's actually available before
      assuming no schema change elsewhere is needed).
- [ ] Backward compatible with already-scored rows (nullable/optional, not a backfill
      requirement).

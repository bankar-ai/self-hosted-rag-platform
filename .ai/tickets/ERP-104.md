# ERP-104 — Production Sample Records Should Capture Source Document and Retrieval Settings

Status: Done
Depends On: ERP-097
Category: Improvement

## Description

Follow-up from reviewing ERP-097's first live results (2026-09-27). `production_sample_scores`
currently stores the query, the three judge scores, and a skip flag/reason — but not which
source document(s) the cited chunks came from, or which retrieval settings (`rerank`,
`expand_sections`, how many documents were in scope) produced that answer.

This mattered in practice: one of the 9 live-scored messages ("what is in the hsrp shine
pdf ??") scored a low Answer Relevancy (0.2) — correctly flagging that the answer came from the
wrong document (both documents were in scope, unscoped retrieval picked the wrong one). Diagnosing
*why* a score is low currently means manually re-deriving this from `conversation_messages`'
`citations` JSONB and cross-referencing chunk/document tables by hand.

## Acceptance Criteria

- [ ] `production_sample_scores` (or a joined view) surfaces the source document filename(s)
      involved in each sample, without requiring a manual join every time.
- [ ] Retrieval settings used for that turn (`rerank`, `expand_sections`, document scope) are
      captured per sample.
- [ ] `run_production_sampling` populates these from data already available at scoring time
      (citations already carry `document_id`; retrieval settings would need to be persisted
      somewhere at generation time if not already — confirm what's actually available before
      assuming no schema change elsewhere is needed).
- [ ] Backward compatible with already-scored rows (nullable/optional, not a backfill
      requirement).

## Notes

Spun off from ERP-097 (2026-09-27) after reviewing its first real production results.

## Resolution (2026-09-27) — scoped to source documents only

Investigated both halves before implementing (per this ticket's own AC): source document
filenames were readily available with **zero schema change elsewhere** (citations already carry
`chunk_id`, and `production_sampling.py` already resolves those to `ChunkRecord`s, which carry
`source_filename`). Retrieval settings (`rerank`/`expand_sections`/`document_ids`) were **not**
persisted anywhere — they exist only as request parameters on `GenerationQuery`, never written
to `conversation_messages` or anywhere else. Capturing them would mean adding a new column to
`conversation_messages` and touching the live generation hot path
(`app/generation/service.py`'s `generate`/`generate_stream`) — a materially bigger, riskier
change than the rest of this ticket.

Rather than either skip that half silently or force it in under time pressure, split it out
honestly as its own ticket: **ERP-107**.

**Implemented here**: `ProductionSampleScoreRecord`/`ProductionSampleResult` gained
`source_documents: list[str] | None` (migration `3110f7ddb247`) — deduplicated, sorted source
filenames from whichever citations resolved, `None` for a skipped message.
`run_production_sampling` populates it from the same `chunks_by_id` lookup it already does for
context text, no new query. Verified: backend 579 passed (unchanged count — extended an existing
test rather than adding a new one), ruff/mypy clean, migration applies cleanly with an empty
`alembic check` diff after.

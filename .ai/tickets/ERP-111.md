# ERP-111 — Live Generation Outage: OpenRouter Enabled Before Payment Settled

Status: Done
Depends On: None
Category: Bug

## Description

Found 2026-09-28 while investigating an unrelated live UI report: real (non-short-circuited)
chat messages were failing in production with a generic "Generation query failed" (`503`).
Server logs confirmed the root cause: the VM's `.env` had `GENERATION_PROVIDER=openrouter`
live, but the OpenRouter account was still at $0.00 available balance (the ERP-106 payment
had not actually settled yet), so every real call to `POST https://openrouter.ai/api/v1/
chat/completions` returned `402 Payment Required`.

This was not caused by this session's own work — `GENERATION_PROVIDER` had already been
switched on the VM ahead of the payment clearing (a real OpenRouter API key exists in the
credentials store, dated the same day), separately from ERP-106's own ticket, which still
records the OpenRouter path as unverified/blocked on a real key. The mismatch between "a key
exists and was deployed" and "the ticket says this is still blocked" is itself worth noting
for next time — a ticket's `Status`/`Progress` notes should stay the source of truth for
whether something is actually safe to enable live.

## Acceptance Criteria

- [x] Restore working chat on the live deployment.
- [x] Live-verify a real (non-short-circuited) generation call succeeds after the fix.
- [x] Leave a clear, easy path to re-enable OpenRouter once the payment genuinely settles.

## Resolution (2026-09-28)

Commented out (not deleted) `GENERATION_PROVIDER=openrouter` in the VM's `~/app/.env`,
restarted `rag-platform.service`. `GenerationSettings.provider` defaults to `"ollama"`, so no
code change was needed — this was a pure configuration revert. Live-verified with a real
generation query against a real ingested document: correct, grounded, cited answer, confirmed
routing through the Modal-hosted Ollama endpoint (not OpenRouter) via server logs.

To re-enable once the OpenRouter payment actually settles: uncomment `GENERATION_PROVIDER=
openrouter` (and confirm `GENERATION_OPENROUTER_API_KEY`/`GENERATION_OPENROUTER_MODEL` are
still correct) in `~/app/.env`, restart the service, and live-verify a real generation call
actually succeeds before considering ERP-106 done — do not assume success from a fast response
alone, since a short-circuited (greeting/no-context) request never reaches the LLM at all and
would look identical whether OpenRouter is working or still failing.

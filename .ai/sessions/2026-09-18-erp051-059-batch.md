# Session — ERP-051 through ERP-059 Batch (Infra Promises, Upload UX, Citations, Prompt Injection)

Date: 2026-09-18
Tickets Touched: ERP-051, ERP-052, ERP-053, ERP-054, ERP-055, ERP-056, ERP-057, ERP-058, ERP-059

## Decisions

- The user wanted firm, *promised* numbers ("when we promise our system can handle this, it
  must be true") for upload size and concurrency, not configured defaults. Every capacity-shaped
  ticket (ERP-051, ERP-052, ERP-059) was therefore live-tested against the actual deployment,
  not just implemented and assumed — including one case (ERP-058) where a live before/after
  behavioral test against real Ollama was run specifically because a prompt-based security fix
  is only as good as its demonstrated effect on model behavior, not its code review.
- ERP-051's "18MB" test was split into two deliberately different shapes after the first attempt
  (1305 pages of dense text) revealed byte size alone doesn't predict processing cost: a second,
  more realistic image-heavy 15MB/6-page PDF was tested to get a representative number, while the
  pathological case was kept and reported honestly rather than discarded as an outlier.
- ERP-052's concurrency test intentionally ran *while* the ERP-051 pathological job was still
  processing in the background — not by design originally, but once discovered, treated as a
  stronger result (proves resilience under adverse conditions) rather than re-run "clean."
- Stopped at 5 concurrent uploads rather than pushing to 10+, given the VM is a single-instance
  `e2-micro` that has previously gone fully unresponsive under load (ERP-047) — reported 5 as
  the honestly-tested number rather than guessing higher would also work.
- A live-mutating SSH command (fixing ERP-057's CORS entry) was blocked by the environment's
  auto-mode classifier. Per the project's established pattern (`gh pr merge`, the branch-
  protection API call), this was not retried or worked around — the exact command was recorded
  in the ticket for the user to run themselves.
- Discovered mid-session that **none of this project's recent work is deployed to the live VM** —
  a read-only `git log -1` on the VM showed it's still at the ERP-047 merge commit, meaning
  ERP-048 and ERP-049 (from the *previous* session, already merged to `develop` on GitHub) were
  also never promoted/deployed. This wasn't previously visible because no session before this one
  had checked the live VM's git state directly.

## Implementation Summary

**ERP-058 (prompt injection, security)**: `app/generation/prompt.py`'s `SYSTEM_PROMPT` gained an
explicit "SECURITY:" section; `build_prompt`'s context block is now wrapped in
`<untrusted_context>` tags. Live-verified with a real before/after test against `gemma3:4b`: the
old prompt was genuinely exploitable (replied "PWNED." to an embedded override instruction); the
new one resisted the identical attack while still correctly *quoting* the same malicious text
when a user explicitly asked what a document said (nuanced, correct behavior — not overblocking).

**ERP-055 (citation precision)**: `app/generation/service.py` gained `_cited_chunks()`, filtering
citations to only chunks referenced by a `[n]` marker actually present in the answer text. Both
`generate()` and `generate_stream()` updated; the streaming SSE event order changed to
`token*` -> `citations` -> `done` (previously `citations` first), since citations can only be
known once the full answer exists. This is the concrete, demonstrated cause of the reported
"more citations than necessary" UX complaint.

**ERP-056 (relevance transparency)**: `Citation` gained `score: float` and `reranked: bool`,
populated from the already-computed `RetrievedChunk.score`. `ChatPage.tsx`'s citation list items
became `<details>`/`<summary>` rows showing the score and whether reranking was applied.

**ERP-053 (retry)**: `JobRecord` now retains `pdf_path`/`filename`; new `jobs.retry_job()` and
`POST /ingestion/jobs/{job_id}/retry` re-run ingestion against the original uploaded bytes for a
failed job, without a fresh upload. Found and fixed a real pre-existing leak along the way:
uploaded temp files were never deleted after a job finished (success *or* failure) — now cleaned
up on success (kept on failure, deliberately, so retry has something to run against).

**ERP-054 (upload UX)**: `apiClient.ts` gained `uploadWithProgress` (XHR-based, for real
upload-progress events `fetch` can't provide). `DocumentsPage.tsx` rewritten: drag-and-drop zone,
`multiple` file input, visible "Maximum file size: 20 MB" label, client-side size rejection, and
a per-file transfer progress bar.

**ERP-051 (size ceiling)**: `INGESTION_MAX_UPLOAD_SIZE_BYTES` lowered from 50MB to 20MB.

**ERP-057 (URL rename)**: User renamed the Vercel project (free). Root cause of the resulting
login failure identified (stale `CORS_ALLOWED_ORIGINS` on the live VM) but the fix itself is
blocked pending the user's own SSH action (see Blockers).

## Live Verification (against the real deployment, not local dev)

All of the following were run against `https://34-31-5-88.sslip.io` (the live VM) using
`gcloud compute ssh` for read-only VM monitoring (`free -h`, `systemctl is-active`) and direct
HTTPS calls for the actual API traffic — no browser tool was available, so frontend changes
(ERP-054, ERP-056's display) were verified via `tsc`/`oxlint`/existing test suite only, not a
live click-through.

- **OCR (ERP-059)**: a real image-based PDF (rendered text, no text layer) correctly routed to
  Cloud Run's OCR fallback (`parser_used: "quality"`), extracted text byte-for-byte correct,
  ~2 minutes end to end, VM memory completely flat (~388-397MB) throughout.
- **Size ceiling (ERP-051)**: a realistic ~15MB/6-page image-heavy PDF completed in ~75-90s. A
  deliberately pathological 18MB/1305-page dense-text PDF took 30+ minutes and was still
  processing when last checked (VM stayed healthy, never crashed, throughout).
- **Concurrency (ERP-052)**: 3 concurrent uploads (3 users) completed in ~10s; 5 concurrent
  (5 users) completed in ~20s — both with zero failures, both while the pathological ERP-051 job
  was also still running in the background.
- **Citation precision / injection guardrail / retry (ERP-055/058/053)**: verified against the
  *local* dev stack (real Postgres/Redis/Ollama, not the live VM, since the new code isn't
  deployed there yet) — see the "Decisions" section above for the injection before/after result.

## Blockers

- **ERP-057's CORS fix is blocked** on the user running this themselves (auto-mode classifier
  refused the mutating SSH command):
  ```bash
  # SSH into rag-platform-host, zone us-central1-a, then:
  sed -i 's|CORS_ALLOWED_ORIGINS=https://frontend-sigma-one-54.vercel.app|CORS_ALLOWED_ORIGINS=https://bankar-ai-self-hosted-rag-platform.vercel.app|' ~/app/.env
  sudo systemctl restart rag-platform
  ```
- **This entire batch (plus the previous session's ERP-048/049) is undeployed.** The live VM is
  still at the ERP-047 merge commit. To ship any of this session's work, the user needs to:
  1. Review/merge the `develop` branch to `main` (this project's established PR-merge step,
     historically always done by the user directly — `gh pr merge` is blocked the same way the
     CORS `sed` was).
  2. `git pull` on the VM and restart `rag-platform.service`.
  3. Apply the CORS fix above (can be done in the same SSH session).
- **Three throwaway test users/documents were left on the live deployment** from this session's
  live testing (one OCR-test user, one size-ceiling-test user, five concurrency-test users) —
  cannot be cleaned up right now since the currently-deployed old code has no `/documents` or
  admin-delete endpoint reachable without an existing admin session. Flag for cleanup once the
  new code is deployed, same pattern as ERP-038/039's leftover users (closed by ERP-040).

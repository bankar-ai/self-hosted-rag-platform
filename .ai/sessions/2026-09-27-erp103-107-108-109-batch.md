# Session — ERP-103, ERP-107, ERP-108, ERP-109 batch (rate limiting, output guardrail, pagination, retrieval-settings persistence)

Date: 2026-09-27
Tickets Touched: ERP-103, ERP-107, ERP-108, ERP-109

## Decisions

- Worked through the four remaining open Backlog tickets in the order ERP-108's own notes
  recommended (cost-bounding first): ERP-108 -> ERP-109 -> ERP-103 -> ERP-107. ERP-106
  (OpenRouter) stayed untouched, paused on the user obtaining a real OpenRouter API key
  (payment approval pending) -- it already defaults to `provider="ollama"`, so leaving it
  alone changes nothing about current behavior.
- ERP-108: hand-rolled Redis-backed fixed-window counter, not `slowapi` -- the Dependency
  Policy check the ticket's own AC required found the existing Redis-client pattern already
  covers everything needed, so a new dependency would add nothing. Fails open on a Redis
  outage (logged), not closed -- a rate limiter going down must not take every user's requests
  down with it.
- ERP-109: a non-LLM, regex/substring check only, run after the answer is fully assembled
  (same point persistence already happens) -- per the ticket's own reasoning, a second judge-LLM
  call on every request would fight the exact latency problem ERP-097/106 just spent a session
  fixing.
- ERP-103: cap-with-"show more" over real cursor pagination, per the ticket's explicit steer
  ("likely simplest ... unless there's a reason a real cursor-paginated API is needed" --
  there wasn't one at this traffic scale).
- ERP-107: a JSONB column on `conversation_messages`, mirroring the existing `citations`
  column's pattern exactly, over a separate table -- nothing needs to query retrieval settings
  independently of the message.

## Implementation Summary

- **ERP-108**: new `app/core/rate_limit.py` (`RateLimitSettings`, `RateLimiter`,
  `get_default_rate_limiter`), new `rate_limited(scope)` dependency factory in
  `app/auth/dependencies.py`. `/generation/query`, `/generation/query/stream`, and
  `/retrieval/query` now depend on it instead of bare `get_current_user`. `RATE_LIMIT_
  REQUESTS_PER_MINUTE` (default 20), documented in `.env.example`.
- **ERP-109**: new `app/generation/guardrail.py`'s `check_output_guardrail`, wired into all
  four places an answer is finalized in `app/generation/service.py` (both branches of both
  `generate()` and `generate_stream()`/`_run_stateful_generation`). Logs (never blocks) a
  verbatim `SYSTEM_PROMPT` leak or a known injection-compliance marker.
- **ERP-103**: `GET /conversations`/`GET /documents` gained `limit`/`offset` query params and
  a `has_more` response field (fetch `limit + 1`, trim to `limit`). Frontend: `ChatPage.tsx`
  (sidebar conversations) and `DocumentsPage.tsx` (documents) both gained "Load more".
- **ERP-107**: new `conversation_messages.retrieval_settings` JSONB column (migration
  `77b31e276298`, alongside a matching `production_sample_scores.retrieval_settings` column)
  capturing `{"rerank", "expand_sections", "document_ids"}` per assistant turn, persisted in
  the same transaction as citations. Surfaced on `Message` and copied through into
  `ProductionSampleResult`/`ProductionSampleScoreRecord` for ERP-097's sampling harness.
